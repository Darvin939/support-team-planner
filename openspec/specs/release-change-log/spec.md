## Purpose

Даёт пользователям краткую историю значимых изменений приложения, показывает установленную версию и сборку и позволяет каждому пользователю самостоятельно отмечать новые релизы просмотренными.

## Requirements

### Requirement: Текущая версия приложения доступна пользователям
Система MUST хранить текущую версию релиза и идентификатор сборки приложения отдельно от версии схемы БД и предоставлять эти значения авторизованному клиенту. Интерфейс MUST показывать их внизу боковой панели; нажатие на отображение MUST открывать историю изменений.

#### Scenario: Пользователь открывает историю изменений
- **WHEN** авторизованный пользователь нажимает на отображаемые версию и сборку в боковой панели
- **THEN** система открывает историю изменений с записями, сгруппированными по дате и версии релиза

#### Scenario: Версия приложения не задана для разработки
- **WHEN** приложение запущено без явно заданной версии релиза или идентификатора сборки
- **THEN** API и интерфейс показывают документированные значения для dev-режима и не подменяют их версией схемы БД

### Requirement: Идентификатор сборки различает экземпляры приложения
Система MUST присваивать production-сборке отдельный идентификатор сборки, предоставлять его авторизованному клиенту и хранить текущий идентификатор в метаданных БД. Идентификатор сборки MUST NOT использоваться как версия релиза или ключ записи change log.

#### Scenario: Отдельная сборка того же релиза
- **WHEN** создаётся новая production-сборка с той же версией релиза
- **THEN** она получает идентификатор текущей сборки, который можно отличить от идентификатора другой сборки того же релиза

#### Scenario: Изменение build id без нового релиза
- **WHEN** приложение запускается с новым build id, но с той же версией релиза
- **THEN** метаданные текущей сборки обновляются, но пользователю не создаётся новый релизный пункт и не сбрасывается его отметка просмотра этого релиза

### Requirement: Значимые изменения публикуются редакционно по версии релиза
Система MUST предоставлять поставляемый с приложением источник записей change log. Каждая запись MUST содержать уникальную версию релиза, дату, заголовок и краткий список пользовательских изменений. Версия релиза является стабильным ключом записи и MUST NOT зависеть от идентификатора сборки. Наличие записи в источнике означает, что она опубликована; система MUST NOT создавать записи автоматически из каждого билда, исправления или внутреннего изменения.

#### Scenario: Опубликованная запись отображается в истории
- **WHEN** запись с версией релиза, датой, заголовком и кратким описанием включена в источник
- **THEN** она отображается в истории изменений в группе соответствующей версии и даты

#### Scenario: Изменение не включено в редакционный источник
- **WHEN** выпущен новый билд без новой записи с версией релиза в источнике change log
- **THEN** система обновляет отображаемый build id, но не создаёт пользовательское объявление и не считает релиз новым

### Requirement: Новые релизы показываются после обновления
Система MUST при первом входе пользователя после появления опубликованной версии релиза, ещё не просмотренной этим пользователем, открыть компактную сводку новых релизных записей. Сводка MUST объединять накопленные записи по датам и версиям, а не показывать отдельное окно для каждого пункта. Подтверждение «Понятно» или закрытие окна MUST отмечать все включённые версии релизов просмотренными для текущего пользователя.

#### Scenario: Пользователю доступны новые релизы
- **WHEN** пользователь входит в приложение и существуют опубликованные версии релиза, ещё не просмотренные этим пользователем
- **THEN** система показывает одну сводку новых релизов, сгруппированную по датам и версиям

#### Scenario: Пользователь подтверждает или закрывает сводку
- **WHEN** пользователь нажимает «Понятно» или закрывает сводку
- **THEN** все версии релизов, включённые в показанную сводку, сохраняются как просмотренные только для этого пользователя

#### Scenario: Нет новых релизов
- **WHEN** пользователь входит в приложение и все опубликованные версии релизов уже отмечены им просмотренными
- **THEN** автоматическая сводка не открывается, а история остаётся доступна по нажатию на версию в боковой панели

### Requirement: Просмотр релизов хранится отдельно для каждого пользователя
Система MUST сохранять в БД персональные отметки просмотра для пары «пользователь — версия релиза» и MUST NOT использовать общий для всех пользователей признак прочтения.

#### Scenario: Один пользователь прочитал релиз
- **WHEN** пользователь подтверждает просмотр нового релиза
- **THEN** этот релиз больше не показывается ему как новый, но остаётся доступным в истории

#### Scenario: Другой пользователь входит после публикации
- **WHEN** другой пользователь входит в приложение после публикации той же версии релиза и ещё не просматривал её
- **THEN** релиз считается новым для него независимо от отметки первого пользователя

### Requirement: Метаданные версии приложения сохраняются в БД
Система MUST сохранять текущую версию релиза и идентификатор сборки в отдельной записи метаданных БД, отличной от `PRAGMA user_version`. При запуске приложения система MUST идемпотентно обновлять эту запись значениями текущего экземпляра приложения.

#### Scenario: Приложение запускается с новой сборкой
- **WHEN** приложение запускается с версией релиза или идентификатором сборки, отличающимися от сохранённых
- **THEN** запись метаданных обновляется, и API возвращает новые значения

#### Scenario: Приложение перезапускается с той же сборкой
- **WHEN** приложение повторно запускается с теми же значениями версии и сборки
- **THEN** метаданные остаются корректными без дублирования записей о релизе или сброса отметок просмотра пользователей
