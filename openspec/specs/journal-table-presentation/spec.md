# Journal table presentation

## Purpose

Определяет табличное представление журнала изменений и истории работы, общую пагинацию основных страниц и поведение таблиц при прокрутке и на узких экранах.

## Requirements

### Requirement: API возвращает записи журнала с идентификатором логической операции
API SHALL возвращать для новых записей журнала и истории идентификатор логической операции, общей для всех изменений одного объекта, записанных одним сохранением. Пагинация истории и журнала SHALL выполняться по событиям; ответ включает все записи выбранного события, а total считает события.

#### Scenario: Сохранение изменяет несколько полей
- **WHEN** одна логическая операция сохраняет несколько изменений работы или назначения
- **THEN** соответствующие записи журнала и истории содержат общий идентификатор операции

#### Scenario: Пагинация события
- **WHEN** выбранная страница включает событие с несколькими записями
- **THEN** API возвращает все записи события на этой странице и учитывает его как одну единицу в total

#### Scenario: Старые записи истории
- **WHEN** API возвращает запись, созданную до добавления идентификатора операции
- **THEN** поле идентификатора может быть пустым, а запись остаётся доступной в прежнем порядке

### Requirement: Журнал отображается таблицей

После выбора команды frontend SHALL отображать записи журнала в таблице событий с выровненными колонками даты и времени, работы, типа объекта, описания изменений и автора. Все записи одной логической операции над одним объектом SHALL отображаться одной строкой.

#### Scenario: Событие содержит несколько изменений
- **WHEN** API возвращает несколько изменений одной логической операции над объектом
- **THEN** журнал отображает одну строку с контекстом объекта и всеми изменениями события

#### Scenario: Работа удалена
- **WHEN** запись относится к работе с признаком удаления
- **THEN** в ячейке работы рядом с названием отображается метка «удалена»

#### Scenario: Журнал загружается
- **WHEN** query журнала находится в состоянии загрузки
- **THEN** таблица показывает состояние загрузки

#### Scenario: Журнал загружается или пуст
- **WHEN** query журнала загружается либо API возвращает пустой список событий
- **THEN** таблица показывает соответственно состояние загрузки или пустое состояние «Изменений пока нет» без контейнера карточек

### Requirement: Строка журнала открывает историю работы

Frontend SHALL открывать историю объекта, к которому относится выбранное событие журнала: историю работы для события о работе и историю конкретного назначения для события о назначении.

#### Scenario: Выбрано событие об изменении работы
- **WHEN** пользователь активирует строку журнала, относящуюся к работе
- **THEN** открывается история соответствующей работы на вкладке «История»

#### Scenario: Выбрано событие об изменении назначения
- **WHEN** пользователь активирует строку журнала, относящуюся к назначению
- **THEN** открывается история соответствующего назначения на вкладке «История»

### Requirement: Модальное окно истории отображает записи таблицей

Frontend SHALL отображать историю выбранного объекта лентой событий с контекстом объекта и изменениями, сгруппированными по идентификатору логической операции, сохраняя серверный порядок и offset-пагинацию.

#### Scenario: Событие содержит несколько изменений
- **WHEN** API возвращает несколько записей истории с одним идентификатором логической операции
- **THEN** лента показывает одну карточку события с автором, временем и перечнем изменённых полей со старыми и новыми значениями

#### Scenario: Историческая запись не имеет идентификатора операции
- **WHEN** API возвращает запись, созданную до добавления идентификатора логической операции
- **THEN** лента показывает её отдельной карточкой и не объединяет с другими записями только по времени

#### Scenario: История загружается или пуста
- **WHEN** история загружается либо API возвращает пустой список событий
- **THEN** лента отображает соответственно loading или empty состояние внутри контекста истории

#### Scenario: Пользователь меняет страницу истории
- **WHEN** пользователь переходит через существующую offset-пагинацию истории
- **THEN** frontend запрашивает соответствующий offset и сохраняет серверный порядок событий

#### Scenario: История открыта на узком экране
- **WHEN** пользователь просматривает историю на узком экране
- **THEN** карточки ленты доступны без обязательной горизонтальной прокрутки

### Requirement: Таблица сохраняет серверную навигацию журнала

Таблица MUST сохранять действующие фильтры, порядок записей от backend, размер страницы и offset-пагинацию без локальной сортировки данных.

#### Scenario: Пользователь меняет страницу
- **WHEN** пользователь переходит через существующую offset-пагинацию
- **THEN** frontend запрашивает соответствующий offset и отображает полученную страницу в исходном серверном порядке

#### Scenario: Пользователь изменяет фильтр
- **WHEN** пользователь изменяет период, поиск по работе или автора
- **THEN** offset сбрасывается и таблица отображает результат существующего фильтрованного API-запроса

### Requirement: Журнал показывает краткую сводку события

Таблица журнала SHALL показывать компактную сводку типа события и количества изменённых непустых полей. Подробности SHALL открываться при выборе строки. Создание, удаление и восстановление MUST визуально отличаться от обычного изменения.

#### Scenario: Событие содержит несколько изменений
- **WHEN** пользователь просматривает журнал
- **THEN** строка показывает тип события и количество реально отображаемых полей с корректной формой слова «поле», а выбор строки открывает полный список значений

#### Scenario: Создание или удаление объекта
- **WHEN** пользователь просматривает событие создания, удаления или восстановления
- **THEN** тип события выделен отдельной цветной меткой и не выглядит как обычное изменение поля

### Requirement: Детали истории показывают только значимые значения

Подробная история SHALL показывать изменения в колонках объекта, поля, прежнего и нового значения. Для создания объекта SHALL показывать только новое значение, для удаления — тип события без пустых колонок. Строки, где оба значения пусты, MUST быть скрыты. История отдельного назначения MUST опускать колонку объекта, если тип объекта уже однозначен из контекста.

#### Scenario: Создание объекта
- **WHEN** пользователь открывает детали события создания
- **THEN** отображаются только поля с заданными значениями и для них показывается колонка нового значения без колонки прежнего значения

#### Scenario: История назначения открыта отдельно
- **WHEN** пользователь открывает историю конкретного назначения
- **THEN** повторяющаяся колонка объекта не отображается

### Requirement: Таблица адаптируется к узкой ширине

Frontend SHALL обеспечивать доступность ключевых данных таблицы на мобильной ширине посредством горизонтальной прокрутки и SHALL скрывать только избыточную отдельную колонку типа объекта.

#### Scenario: Журнал открыт на мобильной ширине
- **WHEN** viewport имеет мобильную ширину
- **THEN** таблица допускает горизонтальную прокрутку, а дата, работа, изменение и автор остаются доступны пользователю

### Requirement: Основные страницы используют единую пагинацию

Frontend SHALL отображать пагинацию таблиц планирования, статистики и журнала через единый общий компонент с одинаковыми стилем, набором размеров страницы и поведением при смене страницы или её размера.

#### Scenario: Пользователь сравнивает пагинацию основных страниц
- **WHEN** на страницах планирования, статистики и журнала доступно больше одной страницы данных
- **THEN** каждая страница отображает одинаково оформленную пагинацию с одинаковым переключателем размера страницы

#### Scenario: Пользователь меняет размер страницы журнала
- **WHEN** пользователь выбирает другой размер страницы в пагинации журнала
- **THEN** frontend сбрасывает журнал на первую страницу и запрашивает выбранный размер через существующие параметры limit и offset

### Requirement: Заголовок таблицы журнала остаётся видимым при прокрутке

Frontend SHALL закреплять заголовок таблицы журнала при вертикальной прокрутке страницы и SHALL учитывать высоту фиксированной мобильной верхней панели.

#### Scenario: Пользователь прокручивает длинный журнал
- **WHEN** пользователь прокручивает страницу журнала вниз, не покидая таблицу
- **THEN** заголовок таблицы остаётся видимым и не перекрывается верхней панелью приложения
