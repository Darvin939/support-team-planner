# task-psi-planning-gate Specification

## Purpose

Определяет состояния приёмо-сдаточных испытаний работы, управление ими и допуск работы к планированию назначений.

## Requirements

### Requirement: Работа имеет трёхсоставное состояние ПСИ
Система SHALL хранить для работы ровно одно состояние ПСИ: `not_required`, `required` или `passed`; существующие и новые работы без явного выбора SHALL иметь `not_required`.

#### Scenario: Создание без явного ПСИ
- **WHEN** создаётся работа без `psi_status`
- **THEN** система сохраняет `not_required`

#### Scenario: Недопустимое значение
- **WHEN** клиент передаёт неизвестный `psi_status`
- **THEN** backend отклоняет запрос с ошибкой валидации

### Requirement: Любая роль меняет ПСИ только у активной работы
Система SHALL разрешать ролям `user`, `editor` и `admin` менять требование и результат ПСИ доступной активной работы и SHALL запрещать это для завершённой, отменённой или удалённой работы. Требование ПСИ SHALL управляться чекбоксом в форме работы только при отсутствии назначений, а результат обязательного ПСИ SHALL изменяться отдельным действием контекстного меню с подтверждением.

#### Scenario: Пользователь отмечает прохождение ПСИ
- **WHEN** роль `user` подтверждает в контекстном меню перевод доступной активной работы из `required` в `passed`
- **THEN** система сохраняет состояние и автора изменения в истории работы

#### Scenario: Пользователь возвращает требование после прохождения
- **WHEN** роль `user` подтверждает в контекстном меню перевод доступной активной работы из `passed` в `required` и у работы нет назначений
- **THEN** система сохраняет состояние `required` и автора изменения в истории работы

#### Scenario: Отмена подтверждения результата
- **WHEN** пользователь отменяет подтверждение перехода между `required` и `passed`
- **THEN** система не изменяет состояние ПСИ

#### Scenario: Изменение терминальной работы
- **WHEN** любая роль пытается изменить ПСИ работы в статусе `done` или `cancelled`
- **THEN** backend отклоняет изменение по общей терминальной блокировке

#### Scenario: Изменение требования при существующем плане
- **WHEN** работа имеет назначения и клиент переводит её из `not_required` в `required` либо из `required`/`passed` в `not_required`
- **THEN** backend отклоняет изменение с сообщением о необходимости удалить назначения

### Requirement: Обязательные непройденные ПСИ блокируют планирование
Система SHALL запрещать создание, автоназначение и перенос назначений работы с `psi_status = required` как на backend, так и в интерфейсе.

#### Scenario: Создание назначения до прохождения ПСИ
- **WHEN** клиент создаёт назначение для работы с `psi_status = required`
- **THEN** backend отвечает HTTP 400 и не создаёт назначение

#### Scenario: Массовое автоназначение до прохождения ПСИ
- **WHEN** bulk upsert содержит новое назначение работы с `psi_status = required`
- **THEN** вся операция отклоняется без частичного сохранения

#### Scenario: Перенос назначения
- **WHEN** клиент переносит существующее назначение работы с `psi_status = required`
- **THEN** backend отклоняет перенос

#### Scenario: ПСИ не требуется или пройдено
- **WHEN** работа имеет `not_required` или `passed`
- **THEN** операции планирования продолжают проходить остальные штатные проверки

### Requirement: Состояние ПСИ заметно и управляемо в планировании
Frontend SHALL показывать в модальном окне работы чекбокс требования ПСИ, SHALL блокировать этот чекбокс при наличии назначений, SHALL предоставлять переходы результата `required` ↔ `passed` в контекстном меню строки работы с подтверждением и SHALL отображать состояние компактным маркером в строке метаданных работы рядом с сегментом согласно установленным подписям.

#### Scenario: Новая работа без требования ПСИ
- **WHEN** пользователь создаёт работу с выключенным чекбоксом «Требуется ПСИ»
- **THEN** frontend отправляет `not_required`

#### Scenario: Включение требования ПСИ
- **WHEN** пользователь сохраняет работу, ранее имевшую `not_required`, с включённым чекбоксом «Требуется ПСИ»
- **THEN** frontend отправляет `required`

#### Scenario: Редактирование работы с пройденным ПСИ
- **WHEN** пользователь сохраняет работу со статусом `passed`, не выключая чекбокс «Требуется ПСИ»
- **THEN** frontend сохраняет `passed`, не возвращая работу в `required`

#### Scenario: Отключение требования после прохождения
- **WHEN** работа со статусом `passed` не имеет назначений, пользователь выключает чекбокс и сохраняет форму
- **THEN** frontend отправляет `not_required`

#### Scenario: Работа с назначениями
- **WHEN** пользователь открывает форму работы, у которой есть хотя бы одно неудалённое назначение
- **THEN** checkbox «Требуется ПСИ» отображает текущее значение, но недоступен для изменения независимо от текущего `psi_status`

#### Scenario: Требуется ПСИ
- **WHEN** работа имеет `psi_status = required`
- **THEN** рядом с сегментом строка работы показывает текущий оранжевый маркер `Требуется ПСИ`, календарные действия планирования заблокированы, а контекстное меню предлагает отметить ПСИ пройденным

#### Scenario: ПСИ пройдено
- **WHEN** работа имеет `psi_status = passed`
- **THEN** рядом с сегментом строка работы показывает текущий зелёный маркер `ПСИ ✓`, а контекстное меню предлагает вернуть состояние `required`

#### Scenario: ПСИ не требуется
- **WHEN** работа имеет `psi_status = not_required`
- **THEN** строка работы не показывает бейдж ПСИ, разрешает планирование и не показывает действие изменения результата ПСИ
