## Requirements
### Requirement: Editing a task requires it to exist
`POST /api/task` SHALL return a 404 error when `task_id` is provided but does not refer to an existing,
non-deleted task, instead of creating a new task under a different id.

#### Scenario: Editing a deleted task
- **WHEN** a client submits `POST /api/task` with a `task_id` belonging to a soft-deleted task
- **THEN** the API responds `404 {'error': 'Задача не найдена'}` and no new task is created

#### Scenario: Editing a nonexistent task
- **WHEN** a client submits `POST /api/task` with a `task_id` that has never existed
- **THEN** the API responds `404 {'error': 'Задача не найдена'}` and no new task is created

#### Scenario: Creating a task (unchanged)
- **WHEN** a client submits `POST /api/task` with no `task_id`
- **THEN** the API creates a new task as before

### Requirement: Получение работы по идентификатору не зависит от списочных фильтров
`GET /api/task/{task_id}` SHALL возвращать одну существующую неудалённую работу после проверки доступа пользователя к её команде независимо от статуса и даты завершения работы.

#### Scenario: Получена старая завершённая работа
- **WHEN** авторизованный пользователь запрашивает доступную ему неудалённую работу в терминальном статусе, завершённую более 30 дней назад
- **THEN** API возвращает работу, даже если она отсутствует в основном списке планирования

#### Scenario: Работа не существует или удалена
- **WHEN** пользователь запрашивает отсутствующую либо soft-deleted работу
- **THEN** API отвечает статусом 404

#### Scenario: Команда работы недоступна пользователю
- **WHEN** пользователь запрашивает существующую работу команды, к которой у него нет доступа
- **THEN** API отклоняет запрос согласно действующим правилам контроля доступа

### Requirement: Работа хранит отдельную ссылку на инструкцию

Система SHALL хранить для работы одну необязательную абсолютную HTTP(S)-ссылку `instruction_url`, SHALL возвращать её в существующих read API работы и MUST атомарно сохранять её вместе с остальными полями и зависимостями.

#### Scenario: Создание работы со ссылкой
- **WHEN** клиент создаёт работу с валидным `instruction_url`
- **THEN** API сохраняет нормализованную ссылку, включает её в create-snapshot и возвращает в ответах работы

#### Scenario: Пустая ссылка
- **WHEN** клиент не передаёт `instruction_url` или передаёт строку из пробелов
- **THEN** работа сохраняется с `instruction_url = NULL`

#### Scenario: Изменение ссылки
- **WHEN** клиент меняет или очищает `instruction_url` существующей работы
- **THEN** система сохраняет новое значение и записывает изменение поля `instruction_url` в историю работы

#### Scenario: Невалидная ссылка
- **WHEN** клиент передаёт относительный URL, URL без hostname, URL со схемой не `http`/`https` или строку длиннее 2048 символов
- **THEN** API отклоняет сохранение с ошибкой в проектном JSON-формате и не изменяет работу или её зависимости

### Requirement: Миграция ссылки на инструкцию сохраняет существующие описания

Миграция SHALL идемпотентно добавлять nullable-колонку `instruction_url` в существующие SQLite-базы без изменения `description` и без автоматического извлечения ссылок.

#### Scenario: Миграция существующей работы со ссылкой в описании
- **WHEN** миграция обрабатывает работу, в `description` которой уже есть HTTP(S)-ссылка
- **THEN** `description` остаётся без изменений, а `instruction_url` равен `NULL`

#### Scenario: Повторный запуск миграции
- **WHEN** migration-step запускается после того, как колонка `instruction_url` уже создана
- **THEN** схема и данные остаются без изменений и ошибки не возникают

### Requirement: Работа определяет обязательный сегмент и шаблон раскатки
Система SHALL требовать при создании работы явный выбор существующего сегмента и существующего шаблона раскатки, разрешённого команде и принадлежащего этому сегменту. Форма MUST не подставлять первый сегмент или шаблон автоматически. Read API работы SHALL возвращать сохранённые идентификатор и название шаблона, а сохранение работы MUST атомарно включать шаблон и его историю вместе с остальными полями и зависимостями.

#### Scenario: Создание с корректным выбором
- **WHEN** пользователь выбирает сегмент и разрешённый команде шаблон этого сегмента и сохраняет работу
- **THEN** работа сохраняется с обоими значениями, история создания включает шаблон, а API возвращает идентификатор и название шаблона

#### Scenario: Выбор отсутствует или некорректен
- **WHEN** новая работа сохраняется без сегмента или шаблона, с несуществующим шаблоном, шаблоном другого сегмента либо не разрешённым команде
- **THEN** сохранение отклоняется без частичной записи работы и зависимостей

#### Scenario: Пользователь меняет сегмент до назначений
- **WHEN** пользователь меняет доступное для редактирования поле сегмента
- **THEN** форма очищает прежний шаблон и предлагает только разрешённые команде шаблоны нового сегмента

#### Scenario: Изменение шаблона отражается в истории
- **WHEN** пользователь допустимо заменяет шаблон работы
- **THEN** система записывает старое и новое значения в историю работы вместе с прочими изменениями сохранения

### Requirement: Существующие работы сохраняют выбор и допускают заполнение отсутствующего шаблона
Система SHALL сохранять существующие сегменты и ссылки на шаблоны при обновлении приложения без автоматического выбора. Старой нетерминальной работе без шаблона SHALL разрешаться первоначальное заполнение подходящим разрешённым шаблоном при неизменном сегменте даже при наличии назначений. Сохранение прочих полей старой работы без шаблона SHALL оставаться доступным. Очистка уже выбранного шаблона MUST отклоняться.

#### Scenario: Обновление существующих данных
- **WHEN** приложение обновляется для базы с заполненными и пустыми ссылками на шаблоны
- **THEN** сегменты и ссылки остаются прежними, NULL не заполняется автоматически

#### Scenario: Однократное заполнение с назначениями
- **WHEN** у старой нетерминальной работы есть назначения и нет шаблона, пользователь выбирает разрешённый шаблон текущего сегмента
- **THEN** система сохраняет шаблон, оставляет сегмент прежним и далее блокирует замену шаблона до удаления всех назначений

#### Scenario: Изменение описания старой работы
- **WHEN** пользователь меняет описание старой нетерминальной работы без шаблона и не меняет её сегмент
- **THEN** изменение сохраняется без автоматического заполнения шаблона

#### Scenario: Исторический шаблон больше не подходит
- **WHEN** сохранённый шаблон не соответствует сегменту работы или более не разрешён команде
- **THEN** система сохраняет и отображает прежнюю связь, допускает изменение несвязанных полей, а автопланирование объясняет недоступность шаблона

#### Scenario: Очистка выбранного шаблона
- **WHEN** клиент пытается явно очистить уже сохранённый шаблон
- **THEN** API отклоняет сохранение без изменения работы
