# task-lifecycle-visibility Specification

## Purpose

Определяет хранение даты завершения, видимость актуальных и архивных работ, отображение архива и восстановление терминальных работ.

## Requirements

### Requirement: Дата завершения отражает текущий жизненный цикл работы
Система SHALL хранить `completed_at` для неудалённой работы: устанавливать текущее время при переходе из активного статуса в `done` или `cancelled`, очищать при переходе обратно в активный статус и не изменять при переходе между терминальными статусами.

#### Scenario: Работа завершается
- **WHEN** активная работа переходит в статус `done` или `cancelled`
- **THEN** система сохраняет в `completed_at` время этого перехода

#### Scenario: Работа возобновляется
- **WHEN** работа из статуса `done` или `cancelled` переходит в активный статус
- **THEN** система очищает `completed_at`

#### Scenario: Терминальный статус уточняется
- **WHEN** работа переходит между `done` и `cancelled`
- **THEN** система сохраняет существующее значение `completed_at`

### Requirement: Основной список ограничивает завершённые работы недавним периодом
`GET /api/tasks/{team_id}` SHALL всегда возвращать подходящие под остальные фильтры активные работы и SHALL включать терминальные работы только при явном запросе недавних завершённых; недавними считаются работы с `completed_at` не старше 30 календарных дней на момент запроса.

#### Scenario: Запрошены только актуальные работы
- **WHEN** клиент запрашивает список без режима недавних завершённых
- **THEN** API возвращает активные работы и не возвращает работы в статусах `done` и `cancelled`

#### Scenario: Запрошены недавние завершённые
- **WHEN** клиент включает режим недавних завершённых
- **THEN** API возвращает все подходящие активные работы и терминальные работы с `completed_at` не старше 30 календарных дней

#### Scenario: Старая или недатированная работа не попадает в планирование
- **WHEN** режим недавних завершённых включён, но терминальная работа завершена более 30 дней назад либо имеет `completed_at=NULL`
- **THEN** эта работа не возвращается в основном списке

#### Scenario: Счётчик соответствует выборке
- **WHEN** основной список запрашивается с поиском и режимом недавних завершённых или без него
- **THEN** поле `total` вычисляется с теми же условиями видимости и поиска, что и возвращаемые элементы

### Requirement: Архив предоставляет полную историю терминальных работ
Система SHALL предоставлять отдельный командный API архива, который возвращает только неудалённые работы в статусах `done` и `cancelled`, поддерживает серверную пагинацию, нечёткий поиск и необязательный диапазон `completed_at`.

#### Scenario: Полный архив без периода
- **WHEN** клиент запрашивает архив без границ периода
- **THEN** API возвращает с пагинацией все подходящие терминальные работы, включая работы с неизвестным `completed_at`

#### Scenario: Архив отфильтрован по периоду
- **WHEN** клиент передаёт нижнюю и/или верхнюю границу даты завершения
- **THEN** API возвращает только терминальные работы с ненулевым `completed_at`, попадающим в заданные включительные границы

#### Scenario: Поиск и пагинация архива согласованы
- **WHEN** архив запрашивается с поиском, периодом, `offset` и `limit`
- **THEN** элементы и `total` используют одинаковые фильтры, а результаты упорядочены от более позднего `completed_at` к более раннему с детерминированным разрешением равенства

### Requirement: Пользователь может просматривать недавние завершённые и полный архив
Экран планирования SHALL по явному переключателю добавлять завершённые за последние 30 дней работы к активным, а отдельный интерфейс архива SHALL предоставлять поиск, период завершения и пагинацию по всей терминальной истории команды.

#### Scenario: Включение недавних завершённых
- **WHEN** пользователь включает переключатель «Завершённые за 30 дней»
- **THEN** таблица планирования перезапрашивается с первой страницы и показывает активные плюс недавние терминальные работы

#### Scenario: Открытие архива
- **WHEN** пользователь открывает архив выбранной команды
- **THEN** интерфейс показывает только завершённые и отменённые работы и позволяет искать их и ограничивать периодом завершения

#### Scenario: Цвета статусов согласованы с модалкой работы
- **WHEN** архив отображает работу в статусе `done` или `cancelled`
- **THEN** подпись статуса оформлена общей функцией `tintedStyle`: цветом success для `done` и error для `cancelled`, как в модалке работы

### Requirement: Терминальную работу можно восстановить из архива
Система SHALL позволять редактору или администратору восстановить неудалённую работу в статусе `done` или `cancelled` отдельной архивной операцией с подтверждением; восстановленная работа SHALL получить статус `new` и `completed_at=NULL`, сохранив остальные поля, зависимости и назначения.

#### Scenario: Редактор восстанавливает завершённую работу
- **WHEN** редактор подтверждает восстановление доступной ему работы в статусе `done` или `cancelled`
- **THEN** система атомарно переводит работу в `new`, очищает `completed_at`, записывает изменение статуса в историю, убирает работу из архива и делает её доступной в активном списке

#### Scenario: Администратор восстанавливает завершённую работу
- **WHEN** администратор подтверждает восстановление работы в статусе `done` или `cancelled`
- **THEN** система восстанавливает работу по тем же правилам, не изменяя её зависимости и назначения

#### Scenario: Обычный пользователь не может восстановить работу
- **WHEN** пользователь с ролью `user` пытается вызвать операцию восстановления
- **THEN** API отвечает статусом 403, а интерфейс архива не показывает ему действие восстановления

#### Scenario: Активная или удалённая работа не восстанавливается
- **WHEN** операция восстановления вызвана для активной, отсутствующей или soft-deleted работы
- **THEN** API отклоняет операцию, не изменяя данные

#### Scenario: Интерфейс подтверждает восстановление
- **WHEN** редактор или администратор нажимает «Восстановить» в строке архива
- **THEN** интерфейс запрашивает подтверждение и только после него вызывает API, затем обновляет архив и основной список без перезагрузки страницы

### Requirement: Миграция сохраняет доступ к существующей истории
При добавлении `completed_at` система SHALL попытаться восстановить дату существующих терминальных работ по последнему зафиксированному переходу `task_status` в `done` или `cancelled`, не назначая вымышленную дату при отсутствии достоверной записи.

#### Scenario: История содержит терминальный переход
- **WHEN** миграция обрабатывает терминальную работу и в `task_history` есть подходящий переход статуса
- **THEN** `completed_at` заполняется временем последнего такого перехода

#### Scenario: История не позволяет определить дату
- **WHEN** миграция обрабатывает терминальную работу без подходящей записи истории
- **THEN** `completed_at` остаётся `NULL`, работа доступна в полном архиве и не считается завершённой за последние 30 дней
