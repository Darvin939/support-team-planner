## Purpose

Определяет поддержку PostgreSQL 15 как рабочего хранилища приложения при сохранении SQLite, существующих контрактов и форматов данных.

## ADDED Requirements

### Requirement: СУБД выбирается конфигурацией экземпляра
Приложение SHALL использовать PostgreSQL при заданном `SUPPORT_PLANNER_DATABASE_URL`, иначе SQLite с существующим `SUPPORT_PLANNER_DB_PATH`. Настройки SHALL загружаться до выбора хранилища. Один экземпляр SHALL использовать одну СУБД без автоматической синхронизации между ними.

#### Scenario: Запуск без PostgreSQL URL
- **WHEN** URL PostgreSQL отсутствует
- **THEN** приложение использует заданный SQLite-путь либо прежний `database.db` по умолчанию

#### Scenario: URL имеет приоритет
- **WHEN** одновременно заданы PostgreSQL URL и SQLite-путь
- **THEN** приложение использует только PostgreSQL

#### Scenario: Ошибка PostgreSQL
- **WHEN** явно заданный URL некорректен или PostgreSQL недоступен
- **THEN** запуск завершается диагностируемой ошибкой без создания или открытия SQLite как fallback

#### Scenario: Подключение содержит пароль
- **WHEN** приложение или CLI сообщает ошибку настройки или подключения
- **THEN** пароль из URL не появляется в сообщении, traceback или логах приложения

### Requirement: Экземпляры SQLite и PostgreSQL работают независимо
Развёртывание SHALL поддерживать одновременно рабочий экземпляр SQLite и тестовый PostgreSQL с отдельными настройками, рабочими каталогами и адресами доступа. Конфигурация, сессии и запись тестового экземпляра SHALL быть изолированы от рабочего. До финального переключения SQLite SHALL оставаться источником рабочих данных; изменения PostgreSQL SHALL считаться временными.

#### Scenario: Тестовый экземпляр изменяет данные
- **WHEN** тестировщик создаёт, редактирует или удаляет данные в PostgreSQL
- **THEN** SQLite и результаты запросов рабочего экземпляра не меняются от этого действия

#### Scenario: Рабочие данные изменились после снимка
- **WHEN** рабочий экземпляр сохраняет новые изменения SQLite после переноса
- **THEN** PostgreSQL продолжает содержать прежний снимок с тестовыми изменениями до следующего явного переноса, без автоматической синхронизации

#### Scenario: Тестовый экземпляр перезапущен
- **WHEN** PostgreSQL-экземпляр остановлен или перезапускается для тестов либо повторной загрузки
- **THEN** рабочее приложение SQLite продолжает обслуживать пользователей

#### Scenario: Пользователь открывает оба экземпляра
- **WHEN** пользователь обращается к отдельно настроенным рабочему и тестовому адресам
- **THEN** вход, cookie и выход одного экземпляра не подменяют сессию другого

### Requirement: Поддерживается совместимая полная схема
PostgreSQL SHALL хранить все прикладные сущности итоговой SQLite-схемы версии 15, сохраняя ID, связи, ограничения уникальности, правила удаления, текстовые даты и время и целочисленные флаги 0/1. Новые генерируемые ID SHALL поддерживать диапазон BIGINT.

#### Scenario: Перенесены существующие сущности
- **WHEN** приложение читает назначения, задачи, историю, настройки, пользователей и состояния уведомлений
- **THEN** сохраняются все поля и связи, включая архивные и мягко удалённые записи

#### Scenario: Активное назначение конфликтует по дате
- **WHEN** создаётся второе неудалённое назначение для той же задачи и даты
- **THEN** ограничение уникальности предотвращает конфликт как в SQLite

#### Scenario: Удалён автор истории
- **WHEN** разрешённое удаление пользователя завершено
- **THEN** история сохраняется с пустой ссылкой на автора согласно прежнему правилу SET NULL

#### Scenario: Пустой курсор уведомлений
- **WHEN** в БД ещё нет истории создания задач
- **THEN** прежние пустая строка временной метки и нулевой ID корректно сохраняются и читаются

### Requirement: Контракты приложения одинаковы для двух СУБД
При одинаковых прикладных данных SQLite и PostgreSQL SHALL сохранять HTTP-статусы, формат JSON, правила доступа, результаты фильтрации, сортировки и пагинации существующего API. Ожидаемые ограничения данных SHALL отличаться от ошибок подключения и других неожиданных ошибок хранения.

#### Scenario: Сравнение ответов
- **WHEN** одинаковые запросы выполняются под пользователями одинаковых ролей на обеих СУБД
- **THEN** ответы эквивалентны, включая строки дат, значения флагов, total и пустые результаты

#### Scenario: Имена и NULL участвуют в сортировке
- **WHEN** список содержит кириллицу, латиницу, одинаковые значения и пустые поля
- **THEN** сравнение текста и размещение NULL соответствуют прежнему поведению SQLite

#### Scenario: Дубликат внутри диапазона заморозки
- **WHEN** часть добавляемых дат уже существует
- **THEN** существующие даты пропускаются, остальные сохраняются, транзакция остаётся работоспособной

#### Scenario: Нарушение внешнего ключа
- **WHEN** операция нарушает ожидаемое ограничение связи
- **THEN** API возвращает соответствующую доменную ошибку, а не ошибку дубликата или ложный успех

### Requirement: Поиск справочников и журнала сохраняет семантику
Поиск пользователей и команд SHALL сохранять прежнюю Unicode casefold-семантику и состав поискового текста. Поиск журнала SHALL сохранять нечёткое сравнение по текущему имени задачи. Поиск SHALL применяться до total и пагинации без скрытого ограничения кандидатов и без обязательных расширений PostgreSQL.

#### Scenario: Пользователь найден по роли
- **WHEN** запрос совпадает с русским названием роли или частью прежней составной строки пользователя
- **THEN** результаты совпадают на SQLite и PostgreSQL

#### Scenario: Поиск ограниченного пользователя
- **WHEN** пользователь ищет команды или историю
- **THEN** поиск не расширяет его доступ, а total учитывает только допустимые совпадения

#### Scenario: История архивной или удалённой задачи
- **WHEN** подходящая задача архивирована или мягко удалена
- **THEN** её доступная история остаётся в поиске, а страницы формируются по событиям истории

### Requirement: Время событий отражает запись после ожидания
Новые временные метки истории и завершения задач SHALL сохранять прежний UTC-формат и отражать время выполнения записи после ожидания блокировки. Формат метаданных релиза SHALL оставаться прежним.

#### Scenario: Запись ждала другую транзакцию
- **WHEN** операция записывает историю после ожидания предыдущего writer
- **THEN** её время не берётся из начала ожидавшей транзакции, и событие не пропускается из-за такого устаревшего времени watermark

### Requirement: Поддержка двух СУБД проверяется перед выпуском
При изменении доступа к данным проверки совместимости SHALL выполняться на SQLite и настоящем PostgreSQL 15 под поддерживаемым Python 3.9. Отсутствие PostgreSQL-прогона SHALL явно отражаться в отчёте и не считаться успешной полной приёмкой.

#### Scenario: PostgreSQL отсутствует в окружении проверки
- **WHEN** доступна только SQLite
- **THEN** отчёт указывает невыполненные PostgreSQL-проверки, а готовность к production-переключению не подтверждается
