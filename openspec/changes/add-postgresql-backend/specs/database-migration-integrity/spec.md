## MODIFIED Requirements

### Requirement: Миграции применяются атомарно
Система SHALL выполнять изменение схемы и данных, postcondition-проверки, запись журнала и обновление версии в одной транзакции каждого шага. SQLite SHALL сохранять `PRAGMA user_version`; PostgreSQL SHALL определять версию по собственному журналу. При ошибке весь шаг MUST откатываться с сохранением прежней версии.

#### Scenario: Postcondition шага не выполнен
- **WHEN** изменение миграции выполнено, но её обязательная проверка завершается ошибкой
- **THEN** система откатывает изменения шага, не создаёт запись журнала и не повышает версию выбранной БД

#### Scenario: Шаг завершился успешно
- **WHEN** изменение миграции и все её обязательные проверки завершились успешно
- **THEN** данные, запись журнала и новое значение версии фиксируются одним commit

### Requirement: История миграций контролируется журналом
Система SHALL хранить для каждой применённой миграции номер, стабильное имя, checksum и время применения и SHALL сверять журнал с manifest выбранной СУБД при каждом запуске. Уже опубликованные номера и checksum MUST оставаться неизменяемыми. Реестры SQLite и PostgreSQL SHALL быть независимыми.

#### Scenario: Код применённой миграции изменён
- **WHEN** checksum или имя зарегистрированной миграции не совпадает с записью в БД
- **THEN** система прекращает запуск до изменения схемы и сообщает номер конфликтующей миграции

#### Scenario: Существующая БД впервые получает журнал
- **WHEN** SQLite БД с историческими миграциями обновляется до версии, вводящей журнал
- **THEN** система записывает версионированный baseline шагов не выше текущего `user_version` и применяет следующий шаг в общей транзакции с журналом

#### Scenario: PostgreSQL создаётся из SQLite-источника
- **WHEN** создаётся PostgreSQL baseline для переноса
- **THEN** он регистрируется в собственном manifest, а SQLite-номера и checksum не выдаются за PostgreSQL-миграции

### Requirement: Реестр и версия БД строго проверяются
Система SHALL проверять уникальность и непрерывность всего реестра независимо от текущей версии. SQLite SHALL сопоставлять `user_version` с журналом; PostgreSQL SHALL проверять полный применённый префикс своего manifest. Система MUST отклонять неизвестную более новую версию и несовместимый журнал до изменений БД.

#### Scenario: В применённой части реестра есть пропуск
- **WHEN** в реестре выбранной СУБД отсутствует номер не выше текущей версии
- **THEN** система прекращает запуск с ошибкой целостности реестра

#### Scenario: БД создана более новой версией приложения
- **WHEN** версия SQLite или PostgreSQL больше максимального номера в соответствующем manifest
- **THEN** система прекращает запуск без изменения БД

### Requirement: Новые шаги проходят проверку внешних ключей
Каждый применяемый шаг SHALL подтверждать целостность внешних ключей до фиксации журнала и версии: SQLite через `PRAGMA foreign_key_check`, PostgreSQL через включённые и проверенные ограничения схемы. Нарушенные или непроверенные внешние ключи MUST препятствовать успешной фиксации шага.

#### Scenario: Новый шаг нарушает внешние ключи
- **WHEN** SQLite foreign_key_check обнаруживает нарушение либо PostgreSQL не может подтвердить ограничения
- **THEN** миграция откатывается и версия БД не повышается

### Requirement: Миграции доступны как pre-deploy операция
Система SHALL предоставлять CLI миграций с прежним SQLite `--database` и явным режимом PostgreSQL. SQLite startup SHALL сохранять автоматическое обновление; его CLI дополнительно выполняет quick_check. PostgreSQL startup SHALL только проверять актуальность схемы без DDL; отсутствующая или отстающая схема требует отдельной pre-deploy команды.

#### Scenario: Pre-deploy проверка успешна
- **WHEN** оператор запускает SQLite CLI для совместимой БД
- **THEN** команда применяет недостающие шаги, проверяет журнал и выполняет quick_check, после чего завершается с успешным кодом

#### Scenario: Pre-deploy проверка обнаружила несовместимость
- **WHEN** CLI выбранной СУБД обнаруживает checksum mismatch, неизвестную версию или ошибку проверки
- **THEN** команда завершается с ненулевым кодом и диагностикой без частично применённого шага

#### Scenario: Runtime PostgreSQL без DDL-прав
- **WHEN** приложение запускается с правами чтения и записи прикладных данных на актуальной схеме
- **THEN** проверка версии и запуск проходят без создания или изменения схемы

#### Scenario: Схема PostgreSQL отсутствует или отстаёт
- **WHEN** приложение обнаруживает отсутствие схемы или неприменённые известные миграции
- **THEN** оно прекращает запуск с указанием необходимости pre-deploy миграции, не пытаясь выполнить DDL

## ADDED Requirements

### Requirement: PostgreSQL миграции выполняются эксклюзивно
Одновременные запуски PostgreSQL-мигратора SHALL сериализоваться до проверки журнала и применения схемы. Повторный запуск актуального мигратора SHALL оставлять версию, данные и учётные записи неизменными.

#### Scenario: Два мигратора запущены одновременно
- **WHEN** оба процесса пытаются применить один шаг
- **THEN** шаг фиксируется единожды, а второй процесс проверяет уже обновлённый журнал

#### Scenario: Повторный pre-deploy запуск
- **WHEN** все миграции уже применены
- **THEN** команда подтверждает актуальность без повторного bootstrap и сброса паролей

### Requirement: Bootstrap отделён от подготовки схемы для импорта
Команда подготовки свежей PostgreSQL-установки SHALL создавать первоначального администратора. Подготовка пустой схемы для импорта SHALL предоставляться отдельно без администратора и других прикладных строк. Startup SHALL NOT выполнять bootstrap.

#### Scenario: Новая установка
- **WHEN** оператор применяет миграции в режиме свежей установки
- **THEN** первоначальный администратор позволяет войти после запуска приложения

#### Scenario: Подготовка к переносу
- **WHEN** схема подготавливается в режиме без bootstrap
- **THEN** она остаётся пустой для полного импорта существующих учётных записей
