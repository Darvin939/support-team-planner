# PostgreSQL 15 и SQLite: совместимое хранение и перенос

## Context

Мотивация и согласованные границы описаны в [proposal.md](proposal.md). Исследование выполнено через Explore и Grilling; пользователь выбрал сохранение обеих СУБД, PostgreSQL 15 на готовом сервере, существующий DBBackend, совместимые типы, общий lock, отдельные pre-deploy миграции и точный поиск. Уточнённый переход предусматривает параллельный рабочий SQLite и тестовый PostgreSQL с повторным полным переносом: каждый новый снимок заменяет все тестовые данные. Остановка рабочего SQLite нужна на финальный перенос; источник — SQLite этого проекта, не MySQL.

Текущий `backend/db/connection.py` выбирает SQLiteBackend при импорте; доменные модули сохраняют ссылку на этот объект. Соединение передаётся через ContextVar, middleware открывает его на запрос, декоратор фиксирует самостоятельные DAO-записи, а composite_transaction откладывает commit. Инициализация SQLite управляет собственными миграционными транзакциями.

Итоговая схема после 15 SQLite-миграций содержит 19 прикладных таблиц. Две таблицы метаданных релиза добавлены миграцией 14 и отсутствуют в исходном SCHEMA. DAO использует `?`, lastrowid, rowid, total_changes, INSERT OR IGNORE и SQLite UDF. Массовый перенос временно помещает служебные строки в поле даты. Состояние уведомлений допускает пустую строку временной метки. Результаты SQL читаются по индексу, имени и через dict(row).

## Goals / Non-Goals

**Goals:** общий слой DAO и проверяемая эквивалентность поведения; независимые миграционные истории и параллельные экземпляры; первичный и повторный перенос без изменения исходника; атомарная полная замена тестовых данных PostgreSQL; минимальные runtime-права; реализация и зависимости, совместимые с Python 3.9.

**Non-Goals:** ORM, async-драйвер, пул соединений, типизация дат как DATE/TIMESTAMP, повышение параллелизма записи и новый поисковый алгоритм. Ограничения эксплуатации и обратного переноса приведены в proposal.

## Decisions

### 1. Выбор backend и загрузка настроек

Загрузка `.env` без переопределения существующего окружения выполняется до импорта DAO и создания backend. Отсутствие `SUPPORT_PLANNER_DATABASE_URL` выбирает прежний SQLite-путь; явно пустой, некорректный или неподдерживаемый URL считается ошибкой. При наличии URL он имеет приоритет над `SUPPORT_PLANNER_DB_PATH`; поддерживаются PostgreSQL URI `postgresql://` и `postgres://` с параметрами libpq, включая TLS.

Backend выбирается один раз на процесс. Тесты получают отдельный процесс для каждой СУБД; изменения одного SQLite DB_PATH больше не считаются универсальным способом переключения хранилища. Никакого fallback при ошибке URL или подключения. Приложение, CLI и traceback верхнего уровня не печатают исходный DSN или секреты из ошибки драйвера; сохраняется безопасная диагностическая причина.

Во время перехода используются отдельные рабочие каталоги, окружения, логи и процессы перезапуска. Рабочий экземпляр продолжает использовать SQLite; PostgreSQL-экземпляр запускается по отдельному тестовому адресу. Для браузерного доступа используются разные hostname и отдельный SESSION_SECRET_KEY тестового экземпляра: одного различия портов недостаточно для изоляции одноимённой cookie. Независимые сетевые адреса предоставляет развёртывание; локальные production UI-прогоны сохраняют штатный запуск на 5093 и выполняются последовательно. Перезапуск тестового экземпляра не останавливает рабочий. При финальном переключении PostgreSQL получает прежний рабочий SESSION_SECRET_KEY и рабочий адрес; тестовый доступ на время переключения закрывается.

SQLite является единственным источником рабочих данных до финального переключения. PostgreSQL содержит снимок плюс временные результаты тестирования; изменения не синхронизируются в обе стороны. После повторной замены тестовые сущности, изменённые пароли, история и отметки прочтения исчезают либо возвращаются к значениям нового источника. Данные, которые нужно сохранить как рабочие, до переключения вносятся в SQLite.

В requirements добавляется `psycopg[binary]>=3.2,<3.3`. Ветка 3.3 не поддерживает Python 3.9 ([документация](https://www.psycopg.org/psycopg3/docs/basic/install.html#supported-systems)). Установка зависимостей остаётся общей для двух СУБД; SQLite не требует работающего PostgreSQL-сервера.

Альтернатива SQLAlchemy Core отклонена пользователем: уже существующая граница достаточна, а перевод всей модели запросов увеличивает объём этой миграции.

### 2. Граница диалекта и результата

DBBackend предоставляет явные операции для SQL placeholders, списка placeholders, вставки с возвращаемым ID, целевого conflict-ignore, текущего времени в прежнем формате и классификации ограничений. DAO формирует запросы с этими операциями; значения передаются драйверу параметрами. Нельзя реализовывать переносимость глобальной заменой `?`/SQL-фрагментов в произвольном тексте или интерполяцией значений.

Вставки с ID используют lastrowid внутри SQLite-адаптера и RETURNING id внутри PostgreSQL-адаптера. Результат предоставляет индекс, имя и keys для dict(row). PostgreSQL driver exceptions не выходят в публичные типы DAO. UNIQUE, FK и прочие integrity errors различаются по кодам драйвера; неожиданные ошибки не превращаются в False/None.

Удаление seen-events использует настоящий составной ключ `(user_id, task_history_id)`, счётчики изменений — rowcount. Conflict-ignore задаёт конкретные уникальные колонки и не подавляет остальные ограничения. Диапазон freeze_days не ловит duplicate с продолжением aborted PostgreSQL-транзакции. Границы календарных периодов рассчитываются в Python; SQL не зависит от SQLite datetime. Пустой ACL использует корректный логический предикат. Подзапросы получают обязательные в PostgreSQL 15 aliases, конкатенации числовых ID — явные текстовые преобразования. Сортировка сохраняет бинарное сравнение текста, положение NULL и устойчивый ID для равных ключей.

Прежние миграционные исходники SQLite не переписываются под общий диалект: это исторический путь подготовки SQLite. Генераторы данных и прикладные SQL-запросы переходят на новые операции.

### 3. Соединения и транзакции

Сохраняется одно соединение на HTTP-запрос без пула. Сетевое открытие/настройка и rollback/закрытие PostgreSQL выполняются через worker thread; ContextVar устанавливается и сбрасывается в контексте middleware. Соединение используется последовательно, без параллельных операций. При завершении откатывается оставшаяся транзакция, включая транзакцию чтения PostgreSQL.

DAO явно помечаются как читающие либо пишущие; признак записи не выводится из HTTP-метода или самого commit_on_success. GET уведомлений может писать, некоторые getters сейчас лишь исторически имеют committing decorator. Самостоятельный write DAO берёт lock до тела функции и делает один commit. Composite scope берёт lock до yield и откладывает все внутренние commit. Любое исключение приводит к rollback на внешней границе; подавление ошибки внутри composite не должно разрешать частичный commit. Мигратор не заворачивается в автоматический write-decorator, поскольку владеет своими транзакциями.

SQLite сохраняет BEGIN IMMEDIATE. PostgreSQL использует READ COMMITTED и один фиксированный transaction advisory key приложения на БД. Вызов begin_write должен быть безопасен повторно; уже открытая SELECT-транзакция не доказывает наличие write lock. Блокировка берётся до чтения состояния, определяющего допустимость изменения. Проверки standalone-зависимостей, статусов/ПСИ, удаления, шаблонов и bulk-операций перемещаются внутрь соответствующего composite scope, а необходимые ранее прочитанные данные повторно проверяются под lock.

Общий lock выбран вместо блокировок отдельных задач: цель первого этапа — инфраструктурная совместимость. Он применяется всеми пишущими инструментами приложения; произвольные внешние SQL-записи администратора должны быть исключены на время переноса. Lock освобождается commit/rollback ([PostgreSQL](https://www.postgresql.org/docs/15/explicit-locking.html#ADVISORY-LOCKS)).

История и completed_at в PostgreSQL получают текст UTC `YYYY-MM-DD HH:MM:SS` из времени выполнения записи, например `to_char(clock_timestamp() AT TIME ZONE 'UTC', 'YYYY-MM-DD HH24:MI:SS')`. CURRENT_TIMESTAMP — время начала транзакции, поэтому после ожидания lock оно непригодно для этих полей. Существующие ISO Z метки релизных метаданных сохраняются. Перенесённые временные метки не нормализуются повторно.

### 4. Схема и PostgreSQL-миграции

PostgreSQL baseline создаётся по полной итоговой схеме SQLite версии 15 с корректным порядком зависимостей таблиц. ID и ссылки — BIGINT, генерируемые ID — GENERATED BY DEFAULT AS IDENTITY, даты/время — TEXT, флаги — INTEGER 0/1. Текстовые колонки имеют COLLATE "C". Сохраняются FK delete actions, индексы и partial unique index активных назначений. Новые доменные ограничения сверх согласованной модели в рамках переезда не вводятся.

У PostgreSQL отдельный manifest начиная с baseline 1 и собственный schema_migrations. Для новых миграций checksum определяется неизменяемым поставляемым содержимым шага; изменения выпущенного шага запрещены. Проверяется полный упорядоченный префикс manifest, неизвестные версии, имена и checksum. Применение шага, postconditions и запись журнала атомарны. FK проверяются действующими валидированными ограничениями, без отключения triggers/constraints ради загрузки.

Мигратор удерживает отдельный session advisory lock на всём запуске, включая проверки между транзакциями шагов; при завершении соединение закрывается. Порядок получения блокировок всегда migration lock → write lock. PostgreSQL startup проверяет актуальность журнала и доступность ожидаемых таблиц, но не выполняет DDL или bootstrap. Runtime может записывать существующие application_metadata согласно текущему поведению приложения.

CLI `python -m scripts.migrate_database --postgresql` берёт целевой URL из окружения. Старый режим `--database PATH` остаётся SQLite и явно выбирает его независимо от PostgreSQL runtime-настройки. Флаги --postgresql и --database несовместимы. Дополнительный PostgreSQL-флаг `--schema-only` отключает bootstrap; обычная первоначальная подготовка создаёт администратора только на действительно новой пустой установке и не пересоздаёт его при повторном запуске. Импорт использует schema-only путь.

### 5. Поиск без PostgreSQL-расширений

Алгоритм fuzzy_word_in и построение поискового текста выносятся в общий чистый Python-модуль. SQLite регистрирует эти функции как UDF. PostgreSQL получает необходимые ID и текстовые поля кандидатов с SQL-ограничениями доступа, команды, статуса и периода, читает их пакетами и применяет те же Python lower/casefold и нечёткое сравнение. Сохраняются только найденные ID, передаваемые одним массивом в `id = ANY(parameter::bigint[])`; пустой массив соответствует отсутствию совпадений.

Фильтрация предшествует count/sort/limit/offset; число кандидатов не обрезается. Пользователи ищутся по прежней составной строке login/ФИО/роль/русская роль. Задачи проверяют каждое слово по имени ИЛИ описанию. Журнал ищет только по текущему имени, сохраняет архивные/мягко удалённые задачи и группировку страниц по событиям. Ветвь include_ids при выборе зависимостей по-прежнему обходит основной поиск и лимит, сохраняя ограничения команды.

READ COMMITTED остаётся общей моделью чтения: отдельные запросы списка и total не приобретают нового обещания единого snapshot при конкурентных изменениях. Эквивалентность проверяется на неизменных данных. Повышение этой гарантии потребовало бы отдельного изменения. Trigram, ILIKE и серверные расширения отвергнуты как меняющие результаты или требования к инфраструктуре.

### 6. CLI переноса и проверка

Новый CLI `python -m scripts.import_sqlite_to_postgres --source PATH [--replace-target] [--dry-run] [--report PATH]` получает PostgreSQL URL только из окружения. Источник открывается без создания отсутствующего файла. Каждый запуск создаёт новый уникальный backup и рабочую копию в каталоге источника; предыдущий снимок автоматически не переиспользуется и файлы не перезаписываются. Отчёт по умолчанию получает уникальное имя рядом с backup. Все текстовые файлы — UTF-8 без BOM, дочерние Python-процессы получают PYTHONUTF8=1 и PYTHONIOENCODING=utf-8.

Порядок: SQLite backup API → отдельная рабочая копия → существующие SQLite миграции → quick_check, FK/schema и проверка представимости значений → проверка PostgreSQL версии/назначения и прав выбранного режима. Источник и схема проверяются до очистки. В тестовых циклах SQLite продолжает работать: снимок согласован, а изменения после его создания попадут в следующий перенос. На финальном цикле все SQLite writers останавливаются до снимка.

Dry-run допускает локальные копии и отчёт, но не изменяет PostgreSQL даже с `--replace-target`. Без флага замены он проверяет пустоту; с флагом — пригодность актуальной схемы, точный список прикладных таблиц и предварительные количества строк, подлежащих удалению. Он не заменяет проверки под блокировкой и сверку импортной транзакции.

Обычный импорт без `--replace-target` подготавливает новую схему через schema-only мигратор либо принимает подготовленную актуальную схему. Все 19 прикладных таблиц должны быть пустыми; заполненный bootstrap означает отказ. В одной write-транзакции повторно проверяется пустота, загружаются таблицы в порядке FK и выполняется сверка. Подготовленная пустая схема может остаться после ошибки первоначального импорта; частичных прикладных данных не остаётся.

Режим `--replace-target` предназначен для повторных тестовых и финального переносов до перевода рабочей эксплуатации. Он требует уже подготовленной актуальной схемы PostgreSQL и не выполняет автоматических миграций или bootstrap; несовместимость означает отказ до очистки. Если перед очередным тестовым циклом изменился manifest, оператор отдельно применяет pre-deploy миграции. Это отделяет изменение схемы от гарантии атомарности замены данных.

Перед заменой оператор останавливает PostgreSQL-экземпляр, его автоперезапуск и остальные writers назначения; SQLite останавливается только на финальный перенос. CLI использует migration-роль с TRUNCATE на прикладных таблицах и владением их последовательностями; runtime-права не расширяются. CLI удерживает migration session lock, затем write transaction advisory lock, затем получает блокировки всех таблиц фиксированного manifest. После получения блокировок он повторно проверяет целевую схему и область очистки. Ошибка получения блокировки или изменения схемы приводит к отказу без частичной замены.

В одной транзакции выполняется `TRUNCATE` полного явного списка 19 прикладных таблиц с квалифицированными именами, `ONLY` для каждой таблицы и `RESTART IDENTITY RESTRICT`, затем загрузка по FK-порядку, сверка и настройка последовательностей. `CASCADE`, удаление БД/схемы и очистка schema_migrations запрещены. Посторонние таблицы сохраняются; внешние FK, требующие расширения очистки, приводят к ошибке. Пустая таблица источника становится пустой и в назначении. Само содержимое PostgreSQL перед заменой не используется для слияния с источником.

Очистка и restart последовательностей откатываются вместе с загрузкой при любой ошибке до commit; прежний PostgreSQL-набор остаётся доступен после rollback. Транзакционность `TRUNCATE ... RESTART IDENTITY` описана в [PostgreSQL 15](https://www.postgresql.org/docs/15/sql-truncate.html). Гарантия требует остановленного тестового экземпляра: TRUNCATE блокирует доступ к таблицам и не сохраняет обычную MVCC-семантику для старых snapshots. Автоматическая очистка при обычном импорте и отдельная очистка с commit перед загрузкой отклонены, поскольку первая неожиданно удаляет данные, а вторая оставляет пустое назначение при сбое переноса.

Сверка использует явный manifest таблиц/колонок и ключей. Строки сортируются по полному первичному ключу и хешируются как последовательность канонических UTF-8 JSON-строк с однозначным разделением; сохраняется различие null/пустой строки/числа/текста. Сравниваются количество, ключи и хеши всех колонок каждой таблицы. schema_migrations и sqlite_sequence не являются прикладными данными; application_metadata переносится и сверяется до первого startup, который закономерно обновит метаданные текущей сборки.

Последовательности ID восстанавливаются после явных вставок по новому импортированному набору, без сохранения высоких ID удалённых тестовых записей. Для атомарного отката использовать транзакционный ALTER SEQUENCE ... RESTART WITH max(id)+1 с безопасным quoting известных идентификаторов; пустые таблицы начинают с 1. RESTART, в отличие от setval, транзакционен ([PostgreSQL 15](https://www.postgresql.org/docs/15/sql-altersequence.html)). При rollback замены восстанавливается состояние последовательностей до очистки. Нетиповые значения, несовместимые с PostgreSQL, отклоняются с таблицей/ключом без раскрытия чувствительных полей. Нельзя обрезать, удалять NUL или пропускать строки молча.

Отчёт содержит режим обычного импорта/замены, версии, идентификацию целевой БД/схемы без секретов, пути и время создания новых локальных копий, количества строк до очистки, результаты проверки/сверки по таблицам, длительности и статус commit. Пароли, password_hash и сырые строки БД не включаются. При неизвестном исходе commit из-за потери соединения отчёт указывает неопределённость; повторная проверка назначения обязательна, автоматическое повторение загрузки или очистки запрещено.

### 7. Проверки, инструменты и эксплуатационная документация

Общие бизнес- и API-тесты переводятся на backend-aware fixtures и запускаются отдельными pytest-процессами для SQLite и PostgreSQL 15. SQLite-specific тесты исторических миграций остаются отдельными. В PostgreSQL используются настоящие драйвер, ограничения и транзакции; эмуляция PostgreSQL поверх SQLite не считается проверкой. Test URL задаётся отдельно от рабочего URL, тесты не используют production по умолчанию. Тестовые fixtures не выполняют DDL под runtime-ролью приложения; схема готовится migration-ролью.

Проверки конкурентности используют два реальных соединения и координацию событий без гонок на произвольных sleep. Покрываются блокировки до guard-проверок, rollback, notification timestamps после ожидания, обмен датами и conflict-ignore. Проверки переносимости SQL включают кавычки, вопросительные знаки и проценты в параметрах, пустые списки ID, Unicode, NULL ordering и все существующие API-ошибки.

Миграционные тесты проверяют checksum/номер/имя, пропуски manifest, две конкурирующие команды, postcondition rollback и повторный запуск. Импорт проверяется на полном наборе 19 таблиц, высоких/разреженных ID, пустых таблицах, soft-delete, паролях, FK, отказе без флага замены на заполненном назначении и искусственных сбоях до commit.

Обязателен двойной цикл: первый импорт → создание, изменение и удаление тестовых PostgreSQL-данных, продвижение sequences и изменения SQLite → новый снимок и --replace-target. После второго цикла проверяются точная сверка всех таблиц, отсутствие тестовых записей, восстановление изменённых тестами данных из SQLite, появление новых рабочих изменений, пустые таблицы и sequences по новому набору. Отдельные fault-тесты после очистки, частичной загрузки и restart проверяют восстановление старого PostgreSQL-набора и sequences. Проверяются --dry-run --replace-target, отказ на неактуальной схеме, сохранение migration journal и посторонних таблиц и отказ вместо каскадной очистки при внешних FK.

Проверки параллельных экземпляров подтверждают отдельные настройки и сессии, отсутствие записи тестового приложения в SQLite и доступность рабочего экземпляра при остановке тестового. UI-прогоны каждой СУБД остаются последовательными на штатном порту; проверка одновременной работы выполняется на независимых адресах развёртывания.

Production UI-тесты используют свежий frontend build и настоящий backend на 5093 с реальным входом; защищённые маршруты не мокаются. SQLite сохраняет backup/restore через API и checkpoint. PostgreSQL использует отдельную тестовую БД; восстановление выполняется после остановки запущенного тестом backend через pg_dump/pg_restore, включая проверку содержимого. Останавливаются только процессы, запущенные данным тестом. AGENTS дополняется правилами для PostgreSQL, существующие SQLite-правила сохраняются.

Оба demo-генератора используют выбранную СУБД и общие операции; SQL-only массовый генератор больше не зависит от sqlite3. В дистрибутив включаются адаптеры, migration manifest/DDL, CLI, README и инструкция переноса. .env, backup, dump и локальные отчёты исключаются. README описывает pytest как единый runner, два прогона, команды подготовки и минимальные права, независимые экземпляры, обычный импорт и --replace-target, остановку PostgreSQL перед каждой заменой и SQLite перед финальной.

## Risks / Trade-offs

- Передача поисковых кандидатов в Python увеличивает сетевой объём → пакетное чтение, узкие SQL-фильтры, замер на реальном снимке; оптимизация алгоритма не подменяет совместимость.
- Общая блокировка ограничивает параллелизм записи → осознанное сохранение модели первого этапа; независимые блокировки ресурсов не добавляются скрыто.
- Сходный SQL может отличаться сортировкой, ошибками и правилами транзакций → реальная PostgreSQL-матрица и сравнение контрактов, включая поведение после ошибок.
- Импорт может выявить значения, допускаемые SQLite, но не PostgreSQL → preflight и отказ без молчаливого исправления; исходник и снимок сохраняются.
- Тестовые данные можно принять за рабочие → отдельный тестовый адрес и сессии, SQLite остаётся единственным рабочим источником, весь PostgreSQL-набор заменяется свежим снимком без слияния.
- Замена может затронуть неверное назначение или прерваться после очистки → явный --replace-target, идентификация БД/схемы в отчёте, фиксированный список таблиц без CASCADE, остановленный тестовый backend и одна транзакция очистки/импорта/сверки.
- В рабочем окружении пока не предоставлены реквизиты PostgreSQL → реализацию можно завершать локально, но PostgreSQL-прогон, репетиция и фактическое переключение нельзя объявлять выполненными без реального назначения.
- PostgreSQL-ветка миграций требует отдельного сопровождения → неизменяемые manifests, общий контроль полноты прикладной схемы и обязательные тесты обеих СУБД.

## Migration Plan

1. После отдельного разрешения apply реализовать и проверить изменение; сохранить точные команды и результаты в verification.md. Данные рабочего SQLite во время разработки не мигрировать на месте.
2. Подготовить пустое назначение PostgreSQL 15 и отдельный тестовый экземпляр с независимыми настройками, каталогом и адресом. Выполнить первый полный импорт свежего снимка без остановки рабочего SQLite, затем открыть PostgreSQL только для тестирования.
3. Выполнить backend/UI матрицу, параллельное тестирование и минимум один повторный цикл: остановить только тестовый PostgreSQL-экземпляр и его автоперезапуск, создать новый снимок рабочего SQLite, выполнить --replace-target, сверку и перезапуск тестового экземпляра. Новые рабочие изменения берутся из SQLite; результаты прошлых тестов полностью удаляются. Повторять цикл при необходимости.
4. Проверить dump/restore на отдельном назначении и сохранить измерения переноса/поиска, включая очистку и повторную загрузку. До финального переключения подтвердить адрес назначения, актуальность его схемы, migration/runtime роли и окно обслуживания. Это может быть то же уже заполненное тестовое назначение; предварительная ручная очистка не нужна. Секреты передаются через окружение.
5. В финальное окно остановить запись обоих экземпляров и их автоматический перезапуск. Создать новый SQLite backup после остановки рабочих writers, подготовить рабочую копию и выполнить --replace-target с полной сверкой. Последний тестовый снимок не используется вместо финального.
6. Настроить PostgreSQL-экземпляр с прежним рабочим SESSION_SECRET_KEY, сохранить закрытым рабочий доступ и тестовый адрес, выполнить контрольный вход и проверки разделов. После успеха перевести рабочий адрес/пользователей на PostgreSQL; старый SQLite-экземпляр оставить остановленным, чтобы рабочие записи не расходились.
7. До перевода рабочей эксплуатации разрешён возврат прежней конфигурации и исходного SQLite, даже если тестировщики ранее изменяли PostgreSQL. После перевода и начала рабочей записи исправлять/восстанавливать PostgreSQL; --replace-target из устаревшего SQLite больше не использовать на рабочем назначении. Исходные снимки и финальный backup сохранять до приёмки. Регулярный backup/restore PostgreSQL выполняется штатными средствами инфраструктуры ([PostgreSQL](https://www.postgresql.org/docs/15/backup-dump.html)).
8. После завершения всех обязательных проверок и приёмки отдельно получить разрешения на sync основных спецификаций, archive и commit согласно AGENTS.md. Невыполненные операции и проверки оставлять явно отмеченными, не архивировать незавершённое изменение.

## Open Questions

Только эксплуатационные значения, не меняющие выбранный дизайн: независимые рабочий/тестовый адреса приложения, адрес и учётные данные PostgreSQL-назначения, способы отключения автоперезапуска обоих экземпляров и согласованное время окна. Их предоставляет оператор перед зависимыми проверками и переключением; секреты не сохраняются в OpenSpec.
