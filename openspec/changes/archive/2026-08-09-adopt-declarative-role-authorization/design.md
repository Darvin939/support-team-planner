## Context

Сейчас `access_control.require_login` одновременно проверяет session user, вычисляет минимальную роль по HTTP-методу и префиксу URL и формирует API-ошибку либо document redirect. Объектный доступ к командам, задачам и назначениям затем проверяется отдельными вызовами внутри handlers. Политика роли поэтому не видна в объявлении маршрута, зависит от порядка условий `required_rank()` и может не охватить новый путь.

Изменение затрагивает все backend routers и document handlers, но должно сохранить существующую матрицу доступа, включая доступ не-admin пользователей к `GET /api/users`, а также session-cookie и публичные API-контракты.

## Goals / Non-Goals

**Goals:**

- сделать минимальную роль явной на endpoint или `APIRouter`;
- разделить получение идентичности, проверку роли и проверку командного ресурса;
- сохранить действующее внешнее поведение и иерархию `user < editor < admin`;
- автоматически выявлять защищённые маршруты без декларации доступа.

**Non-Goals:**

- изменение состава ролей или выдаваемых им бизнес-прав;
- переход на JWT, OAuth2 scopes или внешний identity provider;
- внедрение Casbin, Oso либо другого policy engine;
- изменение frontend, URL, schemas или модели командного доступа.

## Decisions

### Использовать зависимости FastAPI как точку исполнения политики

Будут введены переиспользуемые зависимости получения текущего пользователя и проверки минимальной роли. Они назначаются через параметры handler, `dependencies=[Depends(...)]` или зависимости router. Это делает политику локальной объявлению маршрута и использует жизненный цикл dependency injection FastAPI.

Альтернативы: сохранить path middleware — не устраняет скрытую связь с URL; добавить policy engine — избыточно для трёх иерархических ролей и текущего набора правил.

### Сохранить иерархическую модель минимальной роли

Декларация endpoint задаёт минимальную роль, а централизованное сравнение допускает более высокую. Для исключений вроде чтения `/api/users` endpoint получает минимальную роль `user`, тогда как mutations получают `admin`. Конкретная матрица сначала фиксируется characterization-тестами и затем переносится без изменения.

Альтернатива — перечислять набор допустимых ролей на каждом endpoint. Она гибче, но дублирует текущую иерархию и повышает вероятность расхождений.

### Разделить API и document реакцию на отсутствие доступа

Общий загрузчик идентичности проверяет session user, но адаптеры защищённых API и document routes сохраняют разные ответы: JSON `401/403` для API и redirects для страниц. Публичные login/logout/static routes объявляются отдельно от защищённых групп.

Альтернатива — оставить общий authorization middleware только ради формата ответа. Это продолжило бы неявно защищать маршруты и мешало проверять полноту деклараций.

### Оставить ресурсную авторизацию отдельным слоем

Проверки команды, задачи и назначения остаются самостоятельными зависимостями/helpers поверх уже проверенного пользователя. Глобальная роль не заменяет объектный доступ. В ходе миграции handlers перестают напрямую извлекать роль из `request.state` или идентификатор из session там, где зависимость уже предоставляет текущего пользователя.

### Проверять полноту деклараций автоматически

Тесты инспектируют зарегистрированные FastAPI routes и сверяют каждый route с явной категорией: public, authenticated или minimum-role. Дополнительно параметризованная матрица вызывает репрезентативные и критичные endpoints под `user`, `editor`, `admin` и без сессии.

## Risks / Trade-offs

- [Пропущенная зависимость при миграции откроет endpoint] → сначала добавить проверку полноты деклараций и мигрировать маршруты группами, не удаляя старое enforcement до зелёной матрицы.
- [Одновременная работа middleware и dependencies даст другой ответ или двойную проверку] → выполнять поэтапный переход с characterization-тестами и удалить path-based роль только после полного покрытия.
- [FastAPI dependency может выполняться до ожидаемой request DB setup] → сохранить порядок SessionMiddleware и request-scoped DB connection и отдельно проверить запрос пользователя через dependency.
- [Групповая router-зависимость окажется слишком широкой для исключения] → задавать общее минимальное правило router и переопределять неоднородные группы отдельными routers либо endpoint-зависимостями.
- [Архитектурная декларация не отображается в OpenAPI как OAuth scope] → принять это ограничение; внутреннее приложение использует cookie-session, а проверяемость обеспечивается тестами и инспекцией routes.

## Migration Plan

1. Зафиксировать текущую матрицу ролей и ответы `401/403/redirect` characterization-тестами.
2. Ввести тип текущего пользователя и зависимости аутентификации/минимальной роли без изменения существующего enforcement.
3. Перенести API routers и document routes на явные зависимости, сохранив ресурсные проверки.
4. Добавить проверку полноты деклараций для всех зарегистрированных routes.
5. Удалить path-prefix таблицы и ролевую часть общего middleware после прохождения матрицы.
6. Запустить backend и UI regression tests. Изменений БД и отдельного deployment rollback не требуется; откат выполняется возвратом прежнего middleware и route declarations одной версией приложения.

## Open Questions

- Требуется ли в будущем перейти от минимальной иерархической роли к именованным permissions; в текущем изменении это не требуется и не должно расширять scope.
