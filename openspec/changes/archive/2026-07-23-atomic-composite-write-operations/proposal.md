## Why

Приложение уже переиспользует одно SQLite-соединение в рамках HTTP-запроса, но каждый записывающий DAO-вызов
по-прежнему коммитится независимо. Из-за этого составные команды, такие как сохранение задачи вместе с
зависимостями или создание команды вместе с выдачей доступа, могут сохраниться частично при ошибке второго шага.

## What Changes

- Добавить явную транзакционную область для составных записывающих бизнес-операций без изменения жизненного цикла
  request-scoped соединения.
- Обеспечить единый commit после успешного выполнения всех шагов и единый rollback при ошибке любого шага.
- Перевести сохранение задачи с зависимостями и создание команды с выдачей доступа на атомарное выполнение.
- Сохранить текущую самостоятельную commit-семантику для одиночных DAO-вызовов и вызовов вне явной транзакции.
- Добавить backend-тесты успешного commit и rollback частично выполненных составных операций.

## Capabilities

### New Capabilities

- `composite-write-atomicity`: атомарное выполнение составных записывающих операций на общем SQLite-соединении.

### Modified Capabilities

- `dao-commit-consistency`: декоратор DAO должен сохранять самостоятельный commit по умолчанию, но не коммитить
  отдельные шаги внутри явно открытой составной транзакции.

## Impact

- `db/__init__.py`: управление явной транзакционной областью и поведение `with_db_connection`.
- `support_planner.py`: объединение шагов сохранения задачи и создания команды в атомарные операции.
- `tests/`: проверки commit/rollback и отсутствия частично сохранённых данных.
- Публичные HTTP-маршруты и успешные форматы ответов не изменяются; новые зависимости не требуются.
