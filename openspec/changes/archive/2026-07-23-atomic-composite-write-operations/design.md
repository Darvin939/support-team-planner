## Context

Изменение `sqlite-connection-reuse` ввело одно SQLite-соединение на HTTP-запрос, намеренно сохранив независимые
commit/rollback каждого `with_db_connection`-вызова. Поэтому общий объект соединения уже доступен всем DAO-шагам,
но составная команда всё ещё разбивается на несколько транзакций.

Наиболее явные составные команды:

- сохранение задачи, запись истории и замена набора зависимостей;
- создание команды, привязка шаблонов и выдача создателю ограниченного доступа.

Существующие одиночные DAO-вызовы используются также из seed-скриптов и тестов, поэтому изменение их поведения по
умолчанию создало бы лишний риск.

## Goals / Non-Goals

**Goals:**

- дать backend-коду явный transaction scope поверх текущего request-scoped соединения;
- подавлять промежуточные commit внутри scope и выполнять один commit при успешном выходе;
- откатывать все шаги при любом исключении;
- сделать сохранение задачи с зависимостями и создание команды с доступом атомарными;
- сохранить прежнее поведение DAO вне явного scope.

**Non-Goals:**

- одна транзакция на каждый HTTP-запрос;
- изменение схемы SQLite или жизненного цикла соединения;
- переработка всех routers/services/repositories в рамках этого change;
- изменение HTTP-контрактов или frontend;
- автоматическая поддержка произвольных вложенных savepoint-транзакций.

## Decisions

### Явный transaction scope поверх ContextVar

DB-слой предоставит контекстный менеджер для составной операции. Он использует текущее request-scoped соединение,
отмечает активную внешнюю транзакцию в отдельном `ContextVar`, делает один `commit` при успешном выходе и
`rollback` при исключении. `with_db_connection` внутри этого scope не выполняет собственный commit.

Это выбрано вместо commit/rollback всего HTTP-запроса: GET-запросам транзакция не нужна, а некоторые handlers
содержат независимые действия и формирование ответа. Явная область показывает атомарную бизнес-границу непосредственно
в коде.

Вне HTTP-запроса контекстный менеджер при необходимости открывает и закрывает собственное соединение, чтобы механизм
оставался тестируемым и пригодным для script/service-вызовов.

### Сохранение commit-семантики DAO по умолчанию

`with_db_connection(commit_on_success=True)` продолжает коммитить сразу, если явная составная транзакция не активна.
Это сохраняет существующий контракт `dao-commit-consistency` для одиночных вызовов и минимизирует область изменения.

Вместо удаления commit из всех DAO-функций изменяется только условие в единой точке — декораторе.

### Ошибки внутри составной операции должны быть исключениями

После первого записывающего шага handler/service не должен выходить из transaction scope с обычным успешным
управлением и ошибочным `JSONResponse`, иначе контекстный менеджер воспримет выход как успешный и закоммитит данные.
Проверки по возможности выполняются до первой записи; проверки, которым нужен созданный идентификатор, при неуспехе
возбуждают типизированное исключение. HTTP-слой преобразует его в существующий формат ответа уже после rollback.

### Начальный охват ограничен двумя подтверждёнными операциями

В change входят только сохранение задачи с зависимостями и создание команды с выдачей доступа. Остальные записывающие
маршруты переводятся на новый scope отдельными изменениями, только если аудит подтвердит несколько независимых
commit-шагов.

## Risks / Trade-offs

- **[Risk] Вложенный transaction scope может преждевременно commit/rollback внешнюю операцию.**
  → На первом этапе вложенный scope явно запрещается понятным исключением и покрывается тестом.
- **[Risk] Перехваченное внутри scope DB-исключение позволит продолжить работу после rollback декоратора.**
  → Составные service-операции не используют `raise_on_error=False` для обязательных шагов; тесты проверяют ошибку
  второго шага и отсутствие результата первого.
- **[Risk] Долгая транзакция увеличит время удержания SQLite write lock.**
  → Scope охватывает только короткие последовательности локальных SQL-операций, без HTTP, файлового ввода-вывода
  и тяжёлых вычислений.
- **[Risk] Изменение декоратора повлияет на существующие одиночные DAO-вызовы.**
  → Поведение вне transaction scope фиксируется delta spec и regression-тестом с немедленной видимостью commit
  из другого соединения.
