## Context

Автоназначение группирует блоки выбранного шаблона по датам и сохраняет их названия в строковом поле `assignments.block`, но связь работы с выбранным шаблоном сейчас не сохраняется. Статусы назначений меняются позднее через одиночный `POST /api/assignment`, поэтому в момент успешного завершения последнего блока frontend уже не знает, какой шаблон был выбран.

## Goals / Non-Goals

**Goals:**

- Сохранить выбранный при автоназначении шаблон на работе.
- Надёжно определить, что каждый блок этого шаблона представлен активным назначением и все такие назначения имеют статус `success`.
- После успешной мутации последнего назначения предложить допустимый переход работы в `done`.
- Никогда не завершать работу без явного подтверждения.

**Non-Goals:**

- Автоматическое завершение без диалога.
- Изменение общей карты допустимых переходов статусов работ.
- Учёт удалённых назначений или назначений, не содержащих блоки выбранного шаблона.
- Поддержка нескольких одновременно выбранных шаблонов для одной работы.

## Decisions

1. В `tasks` добавляется nullable `completion_template_id` со ссылкой на `block_templates`. При подтверждении автоназначения bulk payload передаёт `template_id`, и backend сохраняет его на работе в той же составной транзакции, что и назначения. Повторное автоназначение по другому шаблону заменяет выбранный шаблон. Альтернатива — угадывать шаблон по названиям блоков — отклонена из-за неоднозначности пересекающихся шаблонов.
2. Backend вычисляет готовность, используя актуальный состав сохранённого шаблона. Назначение покрывает блок, если нормализованный список названий в `assignment.block` содержит имя блока. Готовность истинна, когда шаблон непуст, каждый его блок покрыт хотя бы одним активным назначением и каждое активное назначение, покрывающее хотя бы один блок шаблона, имеет статус `success`.
3. Ответ одиночного сохранения назначения расширяется необязательным объектом `task_completion_suggestion` с `task_id` и именем работы. Backend возвращает его только для нетерминальной работы, для которой переход в `done` разрешён общей картой переходов и выполнено условие шаблона.
4. Frontend после успешного изменения статуса назначения показывает `Modal.confirm`. Подтверждение вызывает существующий `PATCH /api/tasks/{id}/status` со статусом `done`; отмена не выполняет мутацию. Повторное предложение возможно после следующей релевантной мутации, что не требует хранения отдельного dismiss-состояния.
5. Проверка готовности реализуется чистой backend-функцией/DAO-запросом и покрывается матрицей: полное успешное покрытие, отсутствующий блок, неуспешный статус, лишнее нерелевантное назначение, пустой/удалённый шаблон. UI-диалог и подтверждение покрываются Vitest + React Testing Library, production-сценарий — Playwright.

## Risks / Trade-offs

- [Названия блоков в назначении денормализованы и могут устареть после переименования] → Выбранный шаблон хранится по ID, а проверка использует актуальные имена; при переименовании пользователь должен актуализировать назначения либо предложение не появится ложно.
- [Bulk-сохранение может записать шаблон, но не все назначения] → Сохранять связь и назначения в одной транзакции, откатывая её целиком при ошибке.
- [Ответ save API расширяется] → Добавить только необязательное поле, сохранив `success: true` и обратную совместимость клиентов.
- [Предложение может появляться повторно после отказа] → Показывать его только в ответ на успешную релевантную мутацию, не при каждом рендере или refetch.

## Migration Plan

Добавить nullable-колонку `completion_template_id` в `tasks` идемпотентной SQLite-миграцией и индекс/внешний ключ согласно принятому в проекте способу миграций. Существующие работы получают `NULL` и не вызывают предложения до следующего автоназначения. Откат приложения безопасен: старая версия игнорирует дополнительную колонку.
