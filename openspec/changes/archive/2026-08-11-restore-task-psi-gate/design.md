## Context

Legacy `assignments.is_psi` до сих пор присутствует в SQLite, но исторически моделировал ПСИ на уровне отдельного назначения и больше не используется API/UI. Новое требование относится к работе целиком и определяет допуск к планированию, поэтому legacy-колонка не подходит.

## Goals / Non-Goals

**Goals:**

- Представить состояния ПСИ без противоречивых комбинаций boolean-флагов.
- Разрешить любой роли менять ПСИ активной работы.
- Заблокировать планирование при обязательных непройденных ПСИ на UI и backend.
- Сделать блокирующее состояние заметным в таблице.

**Non-Goals:**

- Удаление legacy `assignments.is_psi`.
- Автоматическая смена состояния ПСИ или статуса работы.
- Изменение правил терминальной блокировки.

## Decisions

1. В `tasks` добавляется `psi_status TEXT NOT NULL DEFAULT 'not_required'` со значениями `not_required|required|passed`. Enum исключает невозможные сочетания двух флагов.
2. `TaskIn` принимает `psi_status`; backend валидирует enum. Создание по умолчанию использует `not_required`, редактирование записывает историю поля. Общий task endpoint уже доступен всем ролям с объектным контролем доступа.
3. Перевод в `required` при активных назначениях отклоняется HTTP 400. Иначе существующий план противоречил бы допуску.
4. Общая проверка допуска блокирует создание назначения, bulk upsert с новыми назначениями и переносы. Удаление и изменение статуса существующего назначения остаются доступны, чтобы можно было очистить/закрыть уже существующие записи; изменение даты/блоков/исполнителя при `required` блокируется как перепланирование.
5. Frontend показывает Select в TaskModal. В строке работы компактный маркер ПСИ располагается в строке метаданных рядом с `Сегмент: …`, чтобы не конкурировать с критичностью и названием: `required` — оранжевый `Требуется ПСИ`, `passed` — зелёный `ПСИ ✓`, `not_required` не визуализируется. Ячейки создания/drag блокируются с tooltip.

## Risks / Trade-offs

- [Один POST endpoint одновременно создаёт и обновляет назначения] → Сравнивать сохранённые поля и разрешать при `required` только изменения статуса/комментария/времени без перепланирования.
- [Legacy is_psi может вводить в заблуждение] → Явно не возвращать его в API; новая миграция не выполняет backfill, поскольку в текущей БД нет установленных значений.
- [Пользователь может случайно поставить required] → Запрет при активных назначениях и заметный бейдж делают последствия явными.

## Migration Plan

Идемпотентная SQLite migration добавляет `tasks.psi_status` с default `not_required`. Существующие работы остаются доступными для планирования. Откат приложения безопасен: старая версия игнорирует новую колонку.
