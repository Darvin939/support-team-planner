## Context

Текущая PSI-защита распределена между backend и frontend и применяется несимметрично. Backend полностью запрещает изменение плановых полей и перенос при `psi_status = required`, но при этом допускает editor/admin сменить статус существующего назначения. Frontend блокирует создание, автоназначение и drag, однако оставляет доступным выбор статуса у существующего назначения.

Новое правило должно разрешить подготовку расписания, не позволяя активировать его до прохождения ПСИ. Оно затрагивает одиночное и массовое сохранение, перенос, изменение требования ПСИ, календарные ячейки, модальную форму и drag-and-drop.

## Goals / Non-Goals

**Goals:**

- Разрешить полный жизненный цикл чернового назначения `new` при непройденном ПСИ.
- Запретить всем ролям создавать или получать через изменение назначение иного статуса до прохождения ПСИ.
- Сохранить атомарность bulk-операций и существующие ограничения ролей.
- Сделать frontend-доступность согласованной с backend-валидацией и явно объяснить правило.
- Разрешить менять требование ПСИ при наличии только черновых назначений.

**Non-Goals:**

- Изменение значений или переходов состояний ПСИ.
- Автоматическое изменение статусов существующих назначений.
- Расширение ролевых полномочий на назначения.
- Изменение терминальной блокировки завершённых, отменённых или удалённых работ.

## Decisions

### Backend проверяет итоговое состояние назначения

Для работы с `psi_status = required` сохранение разрешено, только если итоговый статус назначения равен `new`. Новое назначение с другим статусом и смена существующего `new` на другой статус отклоняются для любой роли. У legacy-назначения другого статуса разрешаются только поля, не относящиеся к плану: `comment` и `time_spent`; дата, работа, блок, исполнитель и статус остаются неизменяемыми.

Проверка итогового состояния предпочтительнее отдельных исключений по endpoint: она единообразно работает для одиночного и bulk upsert и не зависит от роли. Ролевая проверка выполняется дополнительно, а не заменяется.

### Перенос разрешён только для new

Одиночный и массовый перенос при непройденном ПСИ разрешён только назначениям со статусом `new`. Bulk-перенос остаётся атомарным: один неподходящий элемент отклоняет весь набор до изменения данных.

Удаление не получает новой PSI-проверки и продолжает подчиняться терминальной и ролевой политике. Это позволяет очищать черновой план, не расширяя права обычного пользователя на legacy-назначения других статусов.

### Наличие только new не блокирует изменение требования ПСИ

Проверка изменения `not_required` ↔ `required`/`passed` будет учитывать только неудалённые назначения со статусом, отличным от `new`. Черновики не мешают включить или снять требование. Переход результата `required` ↔ `passed` продолжает использовать существующий workflow контекстного меню.

### Frontend использует статусно-зависимую блокировку

Пустые ячейки и существующие назначения `new` остаются интерактивными при `required`. Форма разрешает плановые поля, автоназначение и удаление черновика, но фиксирует статус `new` и показывает предупреждение «До прохождения ПСИ доступны только назначения в статусе „Новый“». Для legacy-назначения другого статуса блокируются плановые поля и статус, но сохраняются комментарий и трудозатраты согласно backend.

Drag-and-drop проверяет одновременно PSI работы и статус назначения: `new` разрешён, остальные статусы заблокированы. Контекстное меню статусов не предлагает переходы до прохождения ПСИ.

### Тестирование разделяется по слоям

Backend-тесты проверяют одиночное и bulk-сохранение, перенос, атомарность, legacy-поля, роли и смену требования ПСИ. Vitest/React Testing Library проверяют вычисление блокировки, форму назначения, автоназначение, ячейки, меню статуса и drag. Playwright не требуется, поскольку изменение касается логики состояния без нового layout или production-интеграционного маршрута.

## Risks / Trade-offs

- [Разные операции могут реализовать правило неодинаково] → Вынести или унифицировать предикаты «разрешено при required» и покрыть каждый входной endpoint тестами.
- [Legacy-назначение другого статуса может остаться у required-работы] → Не менять данные автоматически; разрешить только неплановые поля и удаление по текущей ролевой политике.
- [Bulk-запрос может частично изменить данные до ошибки] → Сохранить предварительную валидацию внутри composite transaction и тест атомарного отката.
- [Frontend может показать действие, которое backend отклонит] → Использовать одинаковую комбинацию `psi_status` и `assignment.status` во всех UI-предикатах и оставить backend источником истины.

## Migration Plan

Миграция БД не требуется. Backend и frontend развёртываются вместе. Откат возвращает прежние предикаты полной PSI-блокировки; созданные назначения `new` остаются корректными данными, но снова становятся недоступными для планирования до прохождения ПСИ.
