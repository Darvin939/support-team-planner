## Context

В `support_planner.py` объявлены request-модели для назначений, задач, справочников, пользователей и календаря.
Эти классы не зависят от экземпляра FastAPI, middleware или DAO и образуют естественную первую границу
декомпозиции. При этом FastAPI использует сам объект класса в сигнатуре route handler для validation и генерации
OpenAPI, поэтому перенос должен сохранить не только поля, но и импортированные в entrypoint имена.

## Goals / Non-Goals

**Goals:**

- выделить все Pydantic request-модели в один модуль API-контрактов;
- сократить число обязанностей `support_planner.py`;
- сохранить route signatures, validation errors и OpenAPI request schemas;
- подготовить независимую основу для последующего переноса маршрутов в routers.

**Non-Goals:**

- переносить маршруты, middleware, access-control helpers или exception handlers;
- менять имена моделей, поля, типы, defaults либо validation;
- объединять похожие модели ценой изменения публичной схемы;
- менять frontend: публичный API-контракт в этом change остаётся прежним.

## Decisions

### Один модуль request-моделей

Все текущие наследники `BaseModel`, используемые как тела API-запросов, переносятся в `api_models.py`.
`support_planner.py` импортирует классы явно, чтобы сигнатуры handlers и генерируемые FastAPI component names
остались прежними.

Альтернатива — сразу создавать пакет `routers/` с отдельной моделью в каждом router-модуле. Она отклонена для
этого change: одновременный перенос routes, dependencies и моделей увеличит diff и усложнит локализацию регрессии.

### Исключение доменного исключения из модуля контрактов

`TaskDependencyCycleError` не является Pydantic request-моделью и остаётся рядом с логикой обработки зависимостей
до отдельного выделения service/domain слоя. Это не позволяет `api_models.py` превратиться в смешанный модуль.

### Совместимость проверяется через OpenAPI и validation

Тест фиксирует набор перенесённых schema names и ключевые свойства request schemas в `app.openapi()`. Существующие
backend tests дополнительно проверяют фактическое validation-поведение. Сравнение полного OpenAPI JSON snapshot не
используется: оно слишком чувствительно к несвязанным изменениям маршрутов.

### Правило синхронного изменения frontend/backend

Frontend не изменяется, потому что ни один публичный request/response контракт не меняется. Если при реализации
обнаружится необходимость изменить schema, change должен быть пересмотрен и включить соответствующее обновление
frontend в соответствии с `frontend-api-error-format`.

## Risks / Trade-offs

- **[Risk] Пропущенная модель останется в entrypoint и граница будет неполной.**
  → Перед переносом получить полный список наследников `BaseModel` и зафиксировать ожидаемые imports тестом.
- **[Risk] Циклический импорт при ссылках моделей на локальные классы.**
  → Переносить только декларативные модели и используемые ими стандартные типы; доменные исключения оставить.
- **[Risk] OpenAPI изменится из-за переименования или alias import.**
  → Сохранить исходные class names и проверить выбранные request schemas автоматическим тестом.
- **[Trade-off] Один файл моделей со временем может вырасти.**
  → Это промежуточная устойчивая граница; делить его по routers следует вместе с последующим переносом маршрутов.
