## Контекст

`useAssignmentDrag.ts` фиксирует все выбранные назначения и сдвигает их на одну общую разницу дат, но проверяет каждую целевую ячейку через `assignmentByKey.has(task-date)`. Такой поиск не отличает внешнее назначение от выбранного назначения, которое освободит ячейку в рамках той же операции. Затем `PlanningPage.tsx` сохраняет перенос последовательными запросами к `/api/assignment`; даже после исправления предварительной проверки первый запрос в цепочке может нарушить частичный уникальный индекс SQLite для активной пары `(task_id, date)` до того, как занимающее ячейку назначение будет перемещено.

Исправление затрагивает проверку перетаскивания, HTTP API, авторизацию, DAO-транзакции, соблюдение уникальности, аудит и отображение ошибок. Существующая схема данных, мягкое удаление, соединение на запрос и API одиночного назначения должны остаться без изменений.

## Цели и нецели

**Цели:**

- Проверять групповой перенос относительно итогового состояния всей группы.
- Атомарно сохранять допустимые цепочки и перестановки без временных конфликтов уникальности.
- Повторно проверять на сервере все правила безопасности и коллизий.
- Записывать для каждого назначения одно изменение исходной даты на итоговую с указанием пользователя сессии.
- Возвращать установленный JSON-формат `{"error": "..."}` и русскоязычные сообщения.

**Нецели:**

- Перенос назначений между задачами или изменение полей, кроме даты.
- Изменение жестов выделения, общей разницы дат или поведения одиночного переноса.
- Изменение схемы назначений, уникального индекса, правил перехода статусов или добавление общего механизма отмены.

## Решения

### Отдельный атомарный маршрут массового переноса

Добавить модель запроса с непустым списком элементов `{assignment_id, new_date}` и синхронный маршрут, например `POST /api/assignments/bulk-reschedule`. Сервер загружает актуальные активные назначения по идентификаторам, отклоняет отсутствующие и повторяющиеся идентификаторы, проверяет формат и границы дат, ограничения роли, статуса и блокировки задачи, а идентификаторы задач получает только из базы данных. Затем он проверяет повторяющиеся итоговые пары `(task_id, date)` и внешние назначения в целевых ячейках, исключая из коллизий идентификаторы переносимой группы.

Это решение предпочтительнее последовательного переиспользования `/api/assignment`, потому что отдельные запросы не обеспечивают принцип «всё или ничего» и не устраняют временные конфликты уникальности. Одного клиентского исправления недостаточно: состояние может измениться после предварительной проверки, а клиент не является доверенным источником данных.

### Временные даты внутри одной DAO-транзакции

После полной проверки DAO временно назначает каждой перемещаемой записи уникальный внутренний маркер даты, затем записывает итоговые даты, фиксирует в истории только логическое изменение исходной даты на итоговую и выполняет один commit. Маркеры должны быть уникальны для операции и назначения и не должны совпадать с датой, допустимой во внешнем API; они существуют только внутри транзакции. Любое исключение откатывает временные значения и историю.

Временные значения предпочтительнее многострочного `UPDATE ... CASE`: SQLite может проверять уникальность в процессе обновления отдельных строк, поэтому перестановка всё равно способна зависеть от порядка обработки. Временное физическое или мягкое удаление исказило бы семантику жизненного цикла и аудит.

Реализация должна соответствовать соглашению `@with_db_connection` и не выполнять промежуточных commit во вспомогательных функциях. Маршрут передаёт в DAO `changed_by=request.session.get('user_id')`.

### Общая семантика итоговых коллизий в обработчике перетаскивания

В начале перетаскивания сохраняется неизменяемый снимок группы. Для каждой позиции указателя вычисляются все итоговые ячейки, множество идентификаторов выбранных назначений и количество попаданий в каждую итоговую пару. Цели классифицируются следующим образом:

- текущее назначение в ячейке допустимо, только если его идентификатор входит в переносимый снимок;
- итоговая пара, в которую попадает более одного назначения, недопустима;
- дата вне разрешённого диапазона недопустима.

Чтобы проверка учитывала личность назначения, логический callback `isOccupied(taskId, date)` следует заменить или дополнить поиском назначения в ячейке. Видимые ячейки получают зелёную или красную рамку по результату классификации; `onDropMany` вызывается только тогда, когда допустимы все цели.

Так предварительная проверка остаётся рядом с состоянием перетаскивания, а сервер повторяет её как доверенную проверку. Вариант простого вычитания исходных ключей из набора занятых ячеек не выбран: идентификатор назначения делает правило явным и безопаснее при изменении загруженной карты во время перетаскивания.

### Единый результат операции вместо частичного успеха

`PlanningPage.tsx` отправляет один массовый запрос. При успехе обновляются запросы назначений и активных назначений, выделение очищается или согласованно обновляется, пользователю показывается количество перенесённых назначений. При ошибке обновляются те же данные и показывается серверная ошибка на русском; списка отдельных неудачных назначений нет, потому что частичный успех запрещён.

## Риски и компромиссы

- [Во время транзакции в поле даты временно записывается служебный текст] → Использовать уникальный префикс операции, который не может пройти публичную проверку даты, и проверить сценарии отката.
- [Клиентские данные могут устареть между предварительной проверкой и отпусканием мыши] → Считать серверную проверку окончательной и обновлять запросы как после успеха, так и после ошибки.
- [Правила авторизации могут разойтись с одиночным маршрутом] → Переиспользовать эквивалентные проверки либо проверить их совпадение сфокусированными серверными smoke-проверками.
- [Большая выборка создаст длинный список SQL-параметров] → Ввести разумное ограничение размера запроса либо разбивать операции чтения на части, сохраняя единую транзакцию; обычные выборки на странице планирования невелики.
- [В проекте нет автоматизированного набора тестов] → Добавлять исполняемые проверки только при наличии подходящего лёгкого шаблона; обязательно выполнить клиентские lint/build и smoke-сценарии для цепочек, внешних коллизий, авторизации, аудита и отката.

## План миграции

Изменение схемы и миграция данных не требуются. Сервер и пересобранный клиент разворачиваются вместе; прежний одиночный маршрут остаётся совместимым. Для отката достаточно вернуть прежние маршрут, DAO и клиентский вызов, преобразование сохранённых данных не требуется.

## Открытые вопросы

Нет. Точное имя маршрута и максимальный размер группы можно выбрать при реализации в соответствии с действующими соглашениями API.
