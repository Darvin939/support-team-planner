## Context

Ручные ошибки backend уже преимущественно используют плоский контракт `{"error": "сообщение"}`. Однако
`HTTPException` FastAPI сериализуется как `{"detail": "сообщение"}`, а validation errors — как структурированный
массив в `detail`. `apiGet` и `apiMutate` независимо разбирают ответ и учитывают только строковое поле `error`.

Расхождение особенно заметно на проверках доступа, отсутствующих сущностях, неверной пагинации и восстановлении
задач: backend формирует полезный `detail`, но UI показывает только технический fallback.

## Goals / Non-Goals

**Goals:**

- гарантировать строковое поле `error` для контролируемых ошибок всех `/api/*` маршрутов;
- сохранить исходные HTTP status codes;
- обеспечить одинаковый разбор ошибок GET и mutation helpers;
- сохранить понятное диагностическое сообщение при не-JSON/неожиданном ответе;
- покрыть контракт автоматическими backend и frontend unit-тестами.

**Non-Goals:**

- вводить каталог машинных error codes;
- менять тексты всех существующих сообщений или переводить оставшиеся английские строки;
- преобразовывать HTML/redirect ошибки маршрутов страниц;
- раскрывать текст необработанных исключений 500 клиенту;
- менять успешные response models.

## Decisions

### Плоский совместимый контракт

Публичной формой остаётся `{"error": "<строка>"}`. Она уже поддерживается frontend и большинством ручных ответов,
поэтому не требуется массово менять handlers или компоненты. Вложенная структура с `code/message/details` была
отклонена как преждевременная: приложение пока не принимает решений по машинным кодам ошибок.

### Exception handlers ограничиваются API-путями

FastAPI handlers для `HTTPException` и `RequestValidationError` проверяют путь запроса. Для `/api/*` они возвращают
единый JSON; для не-API запросов сохраняют стандартную семантику FastAPI/Starlette, включая страницы и redirects.

Строковый `HTTPException.detail` переносится в `error` без изменения. Для нестандартного detail используется
безопасное обобщённое сообщение, а validation error получает стабильное пользовательское сообщение без публикации
внутренней структуры Pydantic.

### Один frontend parser для GET и mutations

`apiGet` и `apiMutate` вызывают общую функцию чтения error response. Приоритет:

1. непустое строковое `error`;
2. fallback `<METHOD> <url> -> <status>`.

Frontend и backend обновляются вместе в рамках одного change. Раздельное развёртывание старой и новой версии не
поддерживается, поэтому frontend не сохраняет переходную совместимость с внутренним FastAPI-полем `detail`.
Будущие изменения публичного API-контракта также должны одновременно описывать и реализовывать обе стороны.

### Тестирование без UI-сценария

Backend contract проверяется через `TestClient`. Frontend parser является чистой функцией и покрывается TypeScript
unit-тестами; Playwright не используется, поскольку изменение не затрагивает DOM или пользовательский сценарий.
Если в проекте ещё нет frontend test runner, добавляется минимальный dev-only runner и script.

## Risks / Trade-offs

- **[Risk] Глобальный handler изменит ошибки страниц входа или SPA.**
  → Handler ветвится по `/api/`; non-API поведение фиксируется regression-тестом.
- **[Risk] Validation details могут содержать полезные сведения о конкретном поле.**
  → В этом change используется стабильное обобщённое сообщение; детализированный безопасный mapping полей можно
  добавить отдельно при реальной потребности UI.
- **[Risk] Несогласованное изменение одной стороны нарушит показ ошибок.**
  → Изменения публичного API-контракта планируются и реализуются одним change одновременно во frontend и backend.
- **[Risk] Дублирующая ручная генерация `JSONResponse` останется в routes.**
  → Она уже соответствует контракту; массовая замена на исключения не входит в этот change и может выполняться
  позже вместе с декомпозицией backend.
