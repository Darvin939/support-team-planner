## Context

История работы и назначения доступна из боковой панели, которая визуально отделена от формы и расширяет desktop-модалки. Журнал показывает записи таблицей, но любая строка открывает историю работы. Backend уже отдаёт историю работы с изменениями её назначений и отдельную историю назначения. Одна логическая операция записи может создавать несколько строк истории, но сейчас у строк нет надёжного идентификатора операции.

## Goals / Non-Goals

**Goals:**
- Сделать историю естественной частью модалок работы и назначения, не изменяя ширину формы при открытии.
- Сгруппировать изменения одной логической операции в одно событие с перечнем изменённых полей.
- Из журнала открывать историю работы или конкретного назначения в соответствии с записью.
- Сохранить существующие фильтры, серверный порядок и пагинацию журнала и историй.

**Non-Goals:**
- Менять правила аудита, доступность истории или редактирование записей.
- Перестраивать API журнала и фильтры.
- Менять историю релизов приложения.

## Decisions

1. **История работы — отдельная вкладка.** Добавить вкладку «История» к существующим «Основное» и «Зависимости». Для терминальной работы также оставить историю доступной отдельной вкладкой. Текущую боковую панель и расширение модалки убрать. При открытии модалки всегда выбирать основную вкладку.

2. **История назначения — отдельная вкладка в модалке назначения.** Для существующего назначения показывать «Назначение» и «История»; для нового назначения историю не показывать. Форму перегруппировать по смыслу: дата и время; блок и исполнитель; статус и комментарий. Автораспределение остаётся режимом вкладки «Назначение» и не меняет место истории.

3. **Устойчиво идентифицировать логические операции истории.** Добавить идентификатор группы события к строкам аудита, записываемым одной логической операцией. Передавать его в ответах API истории и журнала. Новые события отображать одной карточкой с общими автором и временем и списком полей; старые строки без идентификатора оставлять отдельными карточками. Не группировать только по секундному timestamp: отдельные сохранения могут иметь одинаковую секунду.

4. **Переход из журнала зависит от объекта записи.** Для изменения работы открыть вкладку истории работы; для изменения назначения — вкладку истории этого назначения. Сохранять строку журнала как точку входа и фильтры/пагинацию без изменений. Модальное представление использовать ту же ленту, что и вкладки объектов.

5. **Существующие API запросы остаются основой интерфейса.** Использовать эндпоинты истории работы и назначения; расширить их данные идентификатором события. Offset и total этих API считать по событиям, а endpoint возвращает все строки выбранных событий, чтобы событие не разрезалось между страницами. Новых экранов и внешних зависимостей не добавлять.

## Risks / Trade-offs

- [Добавление ключа группы затрагивает запись истории и миграцию SQLite] → добавить nullable-колонку без переписывания старых данных; покрыть все пути записи истории и проверить API обоих типов сущностей.
- [Вкладки могут сбрасывать локальное состояние формы при переключении] → не размонтировать форму при смене вкладки либо проверить сохранение введённых значений до общего сохранения.
- [Журнал может содержать запись об удалённом объекте] → историю по ID всё равно открывать через поддерживаемый API, а название/удалённое состояние сохранять в заголовке контекста.
- [Устаревшие события не имеют группового ключа] → не угадывать группы; показывать каждую старую запись отдельно.

## Migration Plan

1. Добавить nullable-идентификатор события для task/assignment history через штатную миграцию SQLite.
2. Прокинуть общий идентификатор в записи, создаваемые одной логической операцией, и в API-ответы истории/журнала.
3. Реализовать общую ленту и переходы из журнала, затем вкладки модалок.
4. При откате UI продолжает работать с nullable-полем; откат схемы не требуется для совместимости старых записей.

## Open Questions
