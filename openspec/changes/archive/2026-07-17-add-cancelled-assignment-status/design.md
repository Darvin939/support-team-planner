## Context

Статус назначения хранится в SQLite как `TEXT` и передаётся API как строка. Набор доступных пользователю статусов, их метки и TypeScript-union заданы в нескольких frontend-модулях. Статусы `new` и `planned` дополнительно считаются активными; новый `cancelled` в эту категорию не входит.

## Goals / Non-Goals

**Goals:**

- Добавить `cancelled` во все пользовательские точки выбора статуса назначения.
- Единообразно показывать его как «Отменено» в плане и истории.
- Сохранить существующие правила ролей: обычный `user` не может переводить существующее назначение из `new` в другой статус.

**Non-Goals:**

- Не менять статусы задач или логику активных назначений.
- Не вводить новую миграцию базы данных.

## Decisions

- Каноническое значение — `cancelled`, согласованное с терминальным статусом задачи. Альтернатива `canceled` отклонена из-за уже принятого в проекте написания.
- `cancelled` будет иметь нейтрально-вторичный цвет, чтобы не смешивать отмену с ошибкой/откатом (`rollback`).
- Backend-хранение остаётся без изменений: текущие API и схема уже принимают строку. Альтернатива с миграцией/check-constraint не даёт пользы в рамках этого изменения.

## Risks / Trade-offs

- [Risk] Списки статусов и TypeScript-union дублируются в нескольких модулях → Обновить все найденные точки и проверить TypeScript-сборкой.
- [Risk] Отменённое назначение остаётся в таблице планирования → Явная метка и отдельный цвет делают это состояние заметным, при этом сохраняется аудит.
