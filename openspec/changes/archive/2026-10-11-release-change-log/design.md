## Context

См. мотивацию в `proposal.md`. Приложение использует FastAPI, React + Ant Design и SQLite с forward-only миграциями. Боковая панель — общий интерфейсный каркас, а сведения о пользователе уже доступны после авторизации. `PRAGMA user_version` относится только к схеме БД и не может служить версией продукта.

## Goals / Non-Goals

**Goals:**
- Установить один источник текущих версии релиза и номера сборки для backend и frontend.
- Сохранять текущие метаданные приложения в БД при старте.
- Поддержать вручную подготовленные краткие release notes и персональные отметки чтения.
- Открывать историю по версии в сайдбаре и показывать непрочитанные записи один раз.

**Non-Goals:**
- Автоматически генерировать пользовательский changelog из Git-коммитов, миграций или каждого билда.
- Создавать интерфейс администрирования/редактирования релизных заметок.
- Использовать версию приложения вместо версии схемы БД или менять семантику миграций.

## Decisions

1. **Версия релиза и build id имеют разные источники.** Версия релиза задаётся явно в конфигурации приложения. `build-distribution.sh` автоматически формирует build id из UTC-времени сборки и короткого Git SHA (например, `20261011T143012Z-abc1234`); переменная `BUILD_ID` позволяет CI подставить собственный идентификатор запуска. Для разработки задаются документированные значения. Build id идентифицирует конкретную сборку, но не определяет порядок релизов и не используется как версия схемы БД.

2. **БД содержит singleton-метаданные только текущего экземпляра.** Startup upsert записывает текущие `release_version` и `build_id` в отдельную таблицу приложения. Это удовлетворяет требованию хранить версию в БД и не создаёт запись на каждый запуск. Редакционные заметки остаются в версионируемом исходном файле `changelog.json`, чтобы их можно было проверять вместе с релизом и включать в дистрибутив. История релизов не выводится из таблицы метаданных.

3. **Источник журнала — JSON, одна запись на релиз.** `changelog.json` содержит массив релизов; у каждой записи есть уникальная стабильная `version`, дата, заголовок и 1–5 кратких пункта `changes`. Наличие записи означает публикацию. Версия релиза служит стабильным ключом персонального состояния и не зависит от порядка элементов файла. JSON выбран вместо YAML из-за встроенной поддержки в Python и JavaScript и отсутствия необходимости в дополнительном парсере; в коротком редакционном файле отсутствие комментариев — приемлемый компромисс.

4. **Состояние просмотра хранится на пользователя и релиз.** Отдельная таблица связывает `user_id` и `release_version` с временем просмотра, с уникальностью пары. При загрузке новых записей backend возвращает только доступные пользователю непросмотренные релизы; подтверждение фиксирует все релизы конкретного показанного набора. Альтернатива с localStorage отклонена, поскольку отметка должна работать между браузерами и устройствами пользователя.

5. **Сайдбар ведёт к полной истории, а автоматическая сводка — только к новым релизам.** Сводка после входа группирует все накопившиеся непросмотренные релизы и закрытие эквивалентно подтверждению «Понятно», согласно согласованному поведению. Полная история всегда открывается кликом на текущую версию. Build id отображается как метаданные текущей сборки, но не включается в записи `changelog.json` и не является ключом уведомления. Сборка передаёт build id в backend и frontend и включает файл журнала в production-дистрибутив.

## Risks / Trade-offs

- **[Build id может оказаться неполным вне Git checkout]** → Сборка принимает `BUILD_ID` извне; при отсутствии override проверяет доступность Git и формирует понятную ошибку либо документированный fallback.
- **[Непрочитанные заметки могут накапливаться у давно не заходившего пользователя]** → Показывать их одним сворачиваемым/компактным списком с группировкой по дате и релизу, сохраняя полный архив в истории.
- **[Dev-сборки могут менять build id слишком часто]** → Не создавать записи журнала автоматически при смене build id; dev-значения не требуют редакционных записей.
- **[Несогласованность нового источника заметок и старой БД]** → Источник change log является read-only данными релиза; startup-обновление метаданных и миграция таблиц выполняются идемпотентно, отметки просмотра не сбрасываются.

## Migration Plan

1. Добавить forward-only миграцию для таблицы текущих метаданных и таблицы персонального просмотра; существующим пользователям не создавать ложные отметки просмотра.
2. Добавить конфигурацию release version, генерацию build id в `build-distribution.sh`, источник заметок `changelog.json` и startup upsert после миграций.
3. Добавить API для текущей версии, истории и получения/подтверждения непрочитанных записей с проверкой авторизации.
4. Подключить клиентское отображение и проверить production-путь сборки/дистрибутива.
5. При откате к старому приложению новые таблицы могут оставаться неиспользуемыми; destructive downgrade не выполнять.
