## Context

Общий `taskTransitions.json` уже описывает реальный автомат как `new → done/cancelled`. Однако параллельный словарь в `frontend/src/domain/types.ts` и оба demo seed-скрипта допускают `ready`/`in_progress`. Текущая БД является seeded-тестовой и не требует нормализации. Аудит остальных перечислений подтвердил актуальность их значений, но обнаружил широкие `str`-контракты, отсутствие backend-валидации статуса назначения и локальные дубли подписей.

## Goals / Non-Goals

**Goals:**

- Сделать `new`, `done`, `cancelled` единственным актуальным словарём статусов работы во всех слоях.
- Предотвратить появление legacy-значений в новых demo-данных и актуальном UI/API-контракте.
- Полностью удалить compatibility-слой `ready`/`in_progress` после исправления текущих тестовых данных.
- Согласовать типизацию и валидацию статуса назначения, критичности и роли без изменения их наборов.
- Покрыть перечисления контрактными, seed- и component-тестами.

**Non-Goals:**

- Изменение наборов статусов назначений, критичности, ПСИ или ролей: аудит подтвердил актуальность всех их значений.
- Любая новая SQLite migration или изменение схемы.
- Расширение карты допустимых переходов или изменение восстановления архивной работы.

## Decisions

1. Исправить оба seed-скрипта у источника: `TASK_STATUSES` содержит только актуальные значения, а специальный сценарий больше не назначает `in_progress`.
2. `TaskStatus`, `TASK_STATUS_OPTIONS` и `TASK_STATUS_LABELS` содержат только три актуальных значения. Отдельные legacy-карты и helper-функции не создаются.
3. Ввести переиспользуемые Python `Literal`-алиасы для текущего статуса работы, статуса назначения, критичности и роли. Использовать их в Pydantic input/output-моделях; route-правила доступа и карта переходов остаются дополнительными бизнес-проверками.
4. Типизировать frontend label/option-карты конкретными union-типами. `StatisticsPage` переиспользует общие подписи назначения, `historyFormat` — общие подписи ПСИ. Локальный `CRITICALITY_ORDER` заменяется данными из централизованного списка либо типизированной общей константой.
5. Текущий `task_status` типизируется строго во входных и выходных моделях; произвольными строками остаются только общие значения аудита.
6. Добавить контрактные тесты, сверяющие options/labels и `taskTransitions.json` с объявленными актуальными union/Literal-наборами.
7. Перед прямым исправлением текущей seeded-БД создать WAL-safe backup, заменить `tasks.task_status ready/in_progress → new` и такие же значения в полях аудита, затем проверить отсутствие legacy-кодов и `PRAGMA integrity_check`.

## Risks / Trade-offs

- [Прямая очистка тестовой БД затрагивает аудит] → сохранить WAL-safe backup и заменить только точные значения `ready`/`in_progress` в `task_status`-истории, не меняя остальные записи.
- [Seed-тест может стать тяжёлым] → тестировать словари/генератор статусов изолированно либо запускать seed на минимальной временной SQLite-БД, не используя рабочую БД.
- [Pydantic начнёт отклонять ранее принимавшийся произвольный статус назначения] → это целевое исправление контракта; добавить API-тесты всех пяти допустимых и неизвестного значения с форматом ошибки проекта.
- [Широкие `string` в отдельных presentation-моделях останутся] → сохранять ширину только там, где компонент обязан устойчиво показать неизвестное/историческое значение с fallback.

## Migration Plan

Версионная миграция и изменение схемы не требуются. Новые demo-наборы создаются только с актуальными статусами. Текущая локальная seeded-БД исправляется один раз вручную после WAL-safe backup; backup сохраняется до успешной проверки данных и целостности.
