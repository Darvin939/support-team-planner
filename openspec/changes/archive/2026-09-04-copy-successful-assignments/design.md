## Context

Таблица планирования загружает назначения только для текущей страницы работ и выбранного диапазона дат. Поэтому уже имеющиеся данные frontend не подходят для копирования полной истории одной работы. Назначение хранит дату, статус и строку `block`, которая может содержать несколько названий блоков через запятую; успешное назначение определяется значением `status = success`.

Действие относится к отдельной строке работы и естественно размещается в существующем контекстном меню. Оно является read-only и должно быть доступно независимо от права редактирования и терминального статуса работы.

## Goals / Non-Goals

**Goals:**

- Получать по требованию всю неудалённую историю успешных назначений одной работы с соблюдением доступа к её команде.
- Детерминированно преобразовывать историю в компактный текст: один блок присутствует только на своей последней успешной дате, а одинаковые даты объединяются.
- Копировать текст через Clipboard API и явно сообщать пользователю результат действия.
- Покрыть правила выборки, преобразования и пользовательского взаимодействия автоматическими тестами.

**Non-Goals:**

- Экспорт назначений нескольких работ одним действием.
- Учёт назначений со статусами, отличными от `success`.
- Изменение модели данных, справочника шаблонов блоков или правил создания назначений.
- Зависимость результата от выбранного на экране диапазона дат.

## Decisions

### Специализированный backend-запрос истории работы

Backend предоставит read-only endpoint для полной истории успешных назначений одной работы в контексте команды. Endpoint проверит доступ текущего пользователя к команде и принадлежность работы этой команде, исключит soft-deleted записи и вернёт успешные назначения в стабильном хронологическом порядке.

Это предпочтительнее расширения существующего диапазонного запроса необязательными датами: текущий контракт останется строгим для основного экрана, а потенциально большая выборка будет выполняться только после явного действия пользователя и только для одной работы.

### Преобразование выполняется чистой функцией frontend

Frontend разделит каждое непустое поле `block` по запятым и удалит окружающие пробелы. При последовательной обработке назначений для каждого канонического названия блока будет сохранена запись с максимальной датой. Затем оставшиеся блоки будут сгруппированы по дате, даты отсортированы по возрастанию, а названия внутри даты сохранят стабильный порядок исходных данных.

Чистая функция отделяет бизнес-правила представления от React-компонента и позволяет полноценно проверить крайние случаи Vitest-тестами. Backend при этом остаётся универсальным источником истории, а не формата буфера обмена.

### Запрос и копирование запускаются из контекстного меню

Пункт «Копировать назначения» будет присутствовать в меню каждой видимой работы, включая завершённые работы и пользователей без права редактирования. По нажатию frontend запросит историю, сформирует текст вида `Название работы\nБлок 1, Блок 2 - ДД.ММ.ГГГГ` и вызовет `navigator.clipboard.writeText`.

Если после фильтрации блоков нет, Clipboard API не вызывается и показывается «Нет успешных назначений». После записи показывается «Назначения скопированы», а ошибка запроса, преобразования или Clipboard API приводит к уведомлению «Не удалось скопировать назначения».

### Проверки распределяются по уровням

Выборка полной истории и правила авторизации проверяются backend-тестами. Дедупликация, разбор составных блоков, группировка, сортировка и формат проверяются Vitest-тестами чистой функции. Наличие пункта меню, вызов Clipboard API и три варианта уведомлений проверяются React Testing Library в существующем наборе тестов столбцов планирования. Полный Playwright-сценарий не требуется: изменение не добавляет сложного layout или межстраничного production-потока.

## Risks / Trade-offs

- [Большая история работы может увеличить размер ответа] → Запрос выполняется только по одной работе и только по явному действию; при необходимости позже можно добавить серверную агрегацию без изменения пользовательского формата.
- [Clipboard API может быть недоступен из-за контекста или разрешений браузера] → Ошибка перехватывается и отображается понятное уведомление без ложного сообщения об успехе.
- [Историческое поле `block` может быть пустым] → Пустые и состоящие из пробелов элементы игнорируются; при отсутствии остальных блоков применяется сценарий «Нет успешных назначений».
- [Повторное быстрое нажатие создаёт параллельные запросы] → На время операции действие блокируется или повторный запуск игнорируется на уровне обработчика.

## Migration Plan

Изменение схемы БД и миграция данных не нужны. Backend endpoint и frontend-действие развёртываются совместно. Откат состоит в удалении пункта меню и нового endpoint без преобразования сохранённых данных.
