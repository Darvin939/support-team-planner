## Context

Мотивация приведена в proposal.md. В `tasks` уже существует nullable `completion_template_id`, используемый предложением завершить работу. Сейчас bulk API может заменять его при автоназначении; read API работы его не возвращают. `has_assignments` учитывает все неудалённые назначения независимо от статуса, а `has_active_assignments` имеет другое назначение и не подходит для новой блокировки. Удаление шаблона сейчас обнуляет ссылку через FK.

## Goals / Non-Goals

**Goals:** единый источник шаблона в работе, атомарная защита согласованности сегмента/шаблона/назначений, доступный переход существующих данных и понятное состояние заблокированных полей.

**Non-Goals:** версии и снимки состава шаблона, изменение алгоритма раскладки и правил ПСИ, запрет ручных назначений вне шаблона, изменение прав пользователей или общего жизненного цикла работы.

## Decisions

### Использовать существующую связь работы

Переиспользовать `completion_template_id` в write/read API и TypeScript-моделях, добавить название шаблона для отображения. Отдельная колонка rollout-template создала бы две конкурирующие ссылки. Nullable-схема сохраняется для старых работ; новые работы обязаны передавать существующий разрешённый команде шаблон своего сегмента. Сохранение выбора отражается в create-snapshot и истории изменения поля с понятным названием.

### Проверять изменения в одной транзакции

Чтение текущей работы, проверку существования неудалённых назначений и запись сегмента, шаблона и остальных полей выполнять в одной согласованной транзакции DAO. Сравнивать фактические старые и новые значения: повторная отправка прежних значений допустима. Создание/восстановление назначения должно быть согласовано с этим ограничением; исключить гонку между первым назначением и изменением конфигурации, используя принятый в проекте механизм сериализации записи SQLite. UI использует `has_assignments`, но API самостоятельно пересчитывает состояние.

Старой работе с NULL-шаблоном разрешить заполнение при неизменном сегменте даже с назначениями. После заполнения действует обычная блокировка. Существующая работа без шаблона может сохранять прочие поля без принудительного заполнения; очистить уже выбранный шаблон нельзя. Исключение не снимает запреты редактирования терминальных работ. Автоматически угадывать шаблон по блокам нельзя: результат неоднозначен.

Сохранённые ссылки не менять при развёртывании, включая исторические несогласованные ссылки. Устаревший/более не разрешённый шаблон показывать как сохранённый, но запрещать новое автопланирование с понятным объяснением. Если назначений нет, пользователь может исправить выбор; при назначениях потребуется удалить их перед заменой. Изменение несвязанных полей не должно падать из-за неизменённого исторического выбора.

### Форма работы управляет выбором

При создании сегмент и шаблон пустые; шаблон выбирается явно после сегмента из разрешённых команде шаблонов. Смена сегмента очищает прежний выбор. Для старой работы без шаблона доступно первоначальное заполнение; для обычной работы с назначениями оба поля disabled без отдельного поясняющего блока. В просмотре терминальной работы отображать шаблон. Ошибки загрузки справочников не должны сбрасывать пользовательский ввод или выдавать их за отсутствие доступных вариантов.

### Автопланирование читает конфигурацию работы

Убрать Select шаблона и независимое состояние выбора из формы назначений; сетка и даты вычисляются по сохранённому шаблону. Над сеткой не показывать заголовок «Автораспределение по графику» и название шаблона. При отсутствующем, недоступном или пустом шаблоне автоназначение недоступно с объяснением, ручные операции сохраняются. После обновления работы инвалидировать зависимые запросы, чтобы модальное окно использовало свежий шаблон.

Frontend больше не посылает `template_id` в bulk API. Для совместимости backend может принять прежнее поле только если оно равно сохранённому шаблону единственной целевой работы; другое значение или отсутствие сохранённой связи отклоняется атомарно. Endpoint никогда не устанавливает шаблон. Обычный bulk без поля сохраняет текущую поддержку нескольких работ и общую атомарность.

### Защитить справочник от разрушения связи

Удаление шаблона и изменение его сегмента запрещены, пока на него ссылается хотя бы одна строка работы, включая терминальную и мягко удалённую: это сохраняет историю и возможность восстановления. Проверку и изменение делать атомарно. Название, блоки и смещения менять можно. Изменение разрешённых шаблонов команды не переписывает работы; недоступность обнаруживается при следующем автопланировании. Использовать существующий JSON-формат ошибок и показ сообщений backend.

### Компактная группировка параметров

Дополнение компоновки: короткие параметры отображаются в двух Ant Design Card размера small без заголовков. Первая содержит критичность и checkbox ПСИ, выровненный по контролу критичности; вторая — сегмент и шаблон. Внутренний padding 8 px, у Form.Item нет нижнего margin, промежуток между карточками 8 px. На мобильном каждая карточка содержит одну колонку с промежутком 12 px. Это сохраняет прежние две desktop-строки и не добавляет высоту заголовков.

Перед заполнением полей при открытии формы выполнять `form.resetFields()`: одной установки прежних значений через `setFieldsValue` недостаточно, чтобы убрать ошибки валидации полей с неизменившимися значениями. Повторный submit сохраняет обычную валидацию.

## Risks / Trade-offs

- Редактирование блоков/смещений справочника влияет на будущую раскладку и текущую проверку готовности → это согласованная текущая модель живой ссылки, без снимков; существующие назначения автоматически не перепланируются.
- Исторический NULL-шаблон и некорректные старые ссылки → сохранить данные, объяснять недоступность автопланирования, разрешать однократное заполнение NULL по правилам выше.
- Удаление всех назначений разблокирует поля → проверять только неудалённые строки; отменённое назначение остаётся блокирующим.
- Устаревший клиент или параллельное окно → backend проверяет блокировку и попытку замены через bulk независимо от UI, транзакция не допускает частичной записи.
- Защита ссылок удалённых работ удерживает шаблоны в справочнике → явная ошибка объясняет наличие связей; автоматического удаления исторических данных нет.

## Migration Plan

Структурная миграция не требуется, существующая колонка nullable сохраняется. Не выполнять backfill выбора и не переписывать сегменты. Развернуть backend и свежую production-сборку frontend совместно. Проверить существующие NULL и заполненные ссылки, историю, rollback bulk и запреты справочника. Для отката вернуть прежний код и сборку; сохранённые значения совместимы с прежней схемой, однако старый backend снова допускает замену шаблона через bulk.
