## Context

Основная выборка работ сейчас управляется булевым `show_completed`: `false` исключает `done/cancelled`, а `true` полностью снимает ограничение статуса. Таблица `tasks` не хранит временные метки жизненного цикла, хотя `task_history.changed_at` фиксирует смены статуса. Frontend использует тот же списочный endpoint и для страницы планирования, и для получения отдельной работы при переходе по зависимости.

Изменение затрагивает схему SQLite, DAO, FastAPI и React UI. Основной экран должен оставаться ограниченной рабочей выборкой, а вся история должна быть доступна через серверно-пагинируемый архив.

## Goals / Non-Goals

**Goals:**

- отделить актуальное планирование от неограниченной истории;
- хранить индексируемую дату завершения текущего жизненного цикла;
- показывать в планировании активные работы и опционально терминальные за последние 30 дней;
- предоставить полный архив с поиском, периодом и пагинацией;
- исключить зависимость прямого открытия работы от списочных фильтров;
- безопасно мигрировать существующие данные.

**Non-Goals:**

- физическое удаление или перенос старых строк в отдельную таблицу;
- настраиваемый командой срок «недавних» работ в первом релизе;
- изменение карты допустимых переходов статусов;
- восстановление неизвестных дат на основании дат назначений или текущего времени.

## Decisions

### 1. Материализованное поле `tasks.completed_at`

В `tasks` добавляется nullable UTC timestamp `completed_at` и индекс `(team_id, completed_at)`. Поле обновляется атомарно вместе с `task_status`: активный → терминальный устанавливает текущее время, терминальный → активный очищает его, переход внутри одной группы сохраняет значение.

Вычисление даты через подзапрос к `task_history` при каждом чтении отклонено: оно усложняет запросы, индексацию и согласованную пагинацию архива. Даты назначений отклонены, потому что описывают планирование, а не фактическое завершение работы.

### 2. Отдельные контракты для планирования, архива и одной работы

- `GET /api/tasks/{team_id}` сохраняет поиск и пагинацию, но вместо `show_completed` принимает явный булев режим `include_recent_completed`; окно фиксировано сервером в 30 календарных дней.
- `GET /api/tasks/{team_id}/archive` возвращает только `done/cancelled`, принимает `offset`, `limit`, `search`, `completed_from`, `completed_to` и возвращает `{tasks, total}`.
- `GET /api/task/{task_id}` возвращает одну работу независимо от её статуса и `completed_at`.
- `POST /api/task/{task_id}/restore` восстанавливает терминальную работу в `new`; endpoint доступен только ролям `editor` и `admin` и повторно проверяет доступ к команде работы.

Для архива отсутствие периода означает всю историю, включая `completed_at IS NULL`. При наличии хотя бы одной границы строки с неизвестной датой исключаются. Границы задаются календарными датами; нижняя граница включительна с начала дня, верхняя — включительна до конца дня. Backend нормализует сравнение, чтобы frontend не формировал временные смещения.

Один универсальный endpoint с `scope=active|recent|archive|id` отклонён: он объединяет выборки с разными правилами сортировки, параметрами и назначением, повышая риск случайного снятия ограничений.

Восстановление оформляется отдельным endpoint, а не новым переходом в общей карте `taskTransitions.json`. Обычная смена статуса и архивное восстановление имеют разные права и UX: восстановление требует роли не ниже editor и явного подтверждения. DAO выполняет смену `done/cancelled → new`, очистку `completed_at` и запись `task_history` в одной транзакции; зависимости, назначения, приоритет и остальные поля не изменяются. Активная работа даёт конфликт операции, отсутствующая или soft-deleted — 404.

### 3. Стабильная сортировка для разных режимов

Основной список сохраняет текущую сортировку по критичности и ручному приоритету. Архив сортируется по `completed_at DESC`, затем `id DESC`; строки с неизвестной датой идут после датированных. Это делает страницы архива детерминированными.

### 4. Backfill только из достоверной истории

Одноразовая идемпотентная миграция добавляет колонку и заполняет её для текущих терминальных работ значением `MAX(task_history.changed_at)` среди записей `field_name='task_status'` с `new_value IN ('done','cancelled')`. Если записи нет, остаётся `NULL`.

Присваивание времени миграции отклонено: оно ошибочно сделало бы всю старую историю «недавней». Исторические недатированные работы остаются видимыми в полном архиве.

### 5. Архив как отдельный UI-контекст

На странице планирования существующий checkbox переименовывается в «Завершённые за 30 дней». Рядом добавляется действие «Архив», открывающее отдельный интерфейс выбранной команды (страницу либо крупную modal/drawer — конкретная композиция выбирается при реализации по существующим паттернам). Архив имеет собственные query key, поиск, диапазон дат и offset-pagination и не подмешивает назначения в планировочную сетку.

`useTaskById` переводится на `GET /api/task/{task_id}`, поэтому переход по зависимости продолжает открывать старую завершённую работу без расширения основной выборки.

В таблице архивной модалки для editor/admin добавляется колонка действий с `Popconfirm` и кнопкой «Восстановить». После успеха frontend инвалидирует общий task query key, включая основной список, архив и прямую выборку; строка исчезает из текущего архива после refetch. Для роли `user` колонка действий не отображается.

Статусы в архиве отображаются тем же badge-паттерном, что и терминальный статус в модалке работы: общий `tintedStyle` с `token.colorSuccess` для `done` и `token.colorError` для `cancelled`. Отдельные цвета или стандартный Ant Design `Tag` для этой колонки не вводятся.

## Risks / Trade-offs

- **Существующие терминальные работы могут не иметь записи истории** → сохранять `NULL`, явно поддерживать их в полном архиве и не выдавать за недавние.
- **Граница 30 дней зависит от времени и timezone** → хранить UTC timestamp и вычислять cutoff на backend в одном месте; UI отображает локальную дату.
- **Старые клиенты используют `show_completed`** → выполнить frontend и backend в одном поставляемом изменении; неизвестный параметр больше не влияет на выдачу. При необходимости краткой совместимости параметр можно принять, но не трактовать как снятие всех ограничений.
- **Повторное завершение меняет архивную позицию** → это ожидаемая семантика текущего жизненного цикла; полная история переходов остаётся в `task_history`.
- **Архив увеличивает число запросов и UI-состояний** → изолировать query keys и пагинацию архива от планирования, загружать архив только при открытии.
- **Двойной клик или устаревшая строка может повторить восстановление** → endpoint проверяет текущий терминальный статус и отклоняет повторную операцию без дополнительных изменений истории.

## Migration Plan

1. Добавить nullable `completed_at`, индекс и идемпотентный backfill.
2. Атомарно обновлять `completed_at` в операции смены статуса и покрыть переходы DAO/API-тестами.
3. Добавить прямой endpoint одной работы и перевести `useTaskById`.
4. Заменить списочную семантику на активные плюс опциональные 30 дней, сохранив согласованность `items/total`.
5. Добавить архивный DAO/API, затем архивный UI.
6. Собрать production frontend и проверить оба пользовательских сценария через Python + Playwright с WAL-safe backup/restore БД.
7. Добавить отдельную операцию восстановления, действие с подтверждением в архиве и проверить права, сохранность связанных данных и обновление обеих выборок.

Rollback к версии без колонки безопасен: SQLite допускает лишнюю неиспользуемую колонку и индекс. Перед откатом приложения данные сохраняются; повторное развёртывание новой версии повторно не перезаписывает заполненные значения.

## Open Questions
