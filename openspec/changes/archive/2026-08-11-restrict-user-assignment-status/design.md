## Context

Маршрут `POST /api/assignment` одновременно создаёт и обновляет назначение. Backend уже не разрешает роли `user` передавать статус, отличный от `new`, но интерфейс планирования всё ещё формирует контекстное меню смены статуса для назначения в статусе `new`. Ограничение является правилом авторизации и не может полагаться только на UI.

## Goals / Non-Goals

**Goals:**

- Однозначно запретить роли `user` менять статус любого существующего назначения.
- Разрешить роли `user` создавать назначение только с начальным статусом `new`.
- Убрать из frontend недоступные пользователю действия смены статуса.
- Сохранить текущие полномочия ролей `editor` и `admin`.

**Non-Goals:**

- Запрет редактирования пользователем остальных полей назначения в статусе `new`.
- Изменение набора статусов или правил для редактора и администратора.
- Изменение схемы БД или публичной структуры payload.

## Decisions

1. Backend различает создание и обновление по `assignment_id`. Для роли `user` создание допускается только при `status == 'new'`, а обновление должно сохранять прежний статус; попытка передать иной статус отклоняется с HTTP 403. Проверка выполняется до записи в БД. Альтернатива — молча заменять статус на `new` — отклонена, потому что она скрывает ошибочный или злоумышленный запрос.
2. Массовое сохранение применяет ту же проверку к каждому элементу до фиксации транзакции, чтобы пакет не мог частично обойти политику.
3. Frontend для роли `user` не создаёт контекстное меню статуса ни для одного назначения. В модальном окне поле статуса остаётся недоступным и при создании получает `new`; это улучшает UX, но не заменяет backend-проверку.
4. Backend-тесты проверяют создание, попытку смены статуса одиночным и массовым запросом и неизменность поведения повышенных ролей. Компонентные тесты Vitest + React Testing Library проверяют отсутствие действия смены статуса и payload создания.

## Risks / Trade-offs

- [Общий create/update endpoint затрудняет различение смены статуса и редактирования прочих полей] → Загружать существующее назначение и сравнивать сохранённый статус с входным до записи.
- [Разные одиночный и массовый пути могут разойтись] → Использовать общую доменную проверку либо тестировать оба пути одной матрицей ролей.
- [Скрытие меню может изменить обработку клика по chip] → Компонентным тестом проверить, что назначение по-прежнему открывается для разрешённого редактирования других полей.

## Migration Plan

Изменение не требует миграции данных. Развернуть backend и frontend вместе; откат выполняется возвратом к предыдущей версии приложения.
