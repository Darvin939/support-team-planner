## Context

`PlanningPage` напрямую владеет `pendingCenterRef` и меняет его из обработчиков команды, периода, завершённости, пагинации, status mutation и удаления. Клиентские фильтры живут в `usePlanningFilters` и не включены в эту схему. Добавление нового способа изменить представление требует помнить о независимом побочном эффекте, поэтому покрытие уже стало неполным.

После предыдущего изменения grid монтируется только при `planningDataReady`. Это позволяет отделить два решения: изменение представления только запрашивает центрирование, а hook выполняет DOM-прокрутку после готовности окончательного рендера.

## Goals / Non-Goals

**Goals:**

- Сосредоточить ref, DOM-поиск и жизненный цикл центрирования в одном hook.
- Покрыть все серверные и клиентские параметры представления.
- Автоматически учитывать добавление, удаление и выпадение работы из серверной выборки.
- Не возвращать прокрутку при refetch того же набора или reorder.

**Non-Goals:**

- Центрирование после каждого изменения назначения или зависимости.
- Изменение loading-барьера planning grid.
- Сохранение пользовательской позиции прокрутки между разными представлениями.

## Decisions

1. Создать `usePlanningGridTodayCenter` в `pages/planning`. Hook принимает `today`, `isReady`, ключ представления и ключ отрисованных строк; внутри хранит pending-ref и вызывает DOM-функцию центрирования. `PlanningPage` не получает ref и не управляет им напрямую.

2. Ключ представления формируется из команды, границ периода, debounced search, `showCompleted`, страницы, размера страницы, отсортированных значений четырёх клиентских фильтров и отсортированной сигнатуры ID работ текущей серверной страницы. Сортировка ID отличает изменение состава от reorder.

3. Изменение ключа представления устанавливает pending до эффекта выполнения центрирования. Эффект выполнения зависит от готовности и ключа актуального рендера строк, поэтому при серверном переходе ждёт загрузку, а при клиентском фильтре работает после commit нового DOM.

4. Фоновые refetch с прежними параметрами и тем же составом ID не меняют ключ представления. Изменения assignments/deps/freeze days могут повторно запустить эффект выполнения из-за рендера, но pending уже false, поэтому пользовательская прокрутка сохраняется.

5. Прямые присваивания из обработчиков и callbacks mutations удаляются. Структурные status/delete операции покрываются изменением сигнатуры состава работ после обновления tasks-query.

## Risks / Trade-offs

- [Risk] Сериализованный ключ трудно читать при отладке. → Формировать его рядом с вызовом hook из именованных нормализованных частей и покрыть UI-сценариями каждого класса триггеров.
- [Risk] Клиентский фильтр может скрыть все строки, поэтому DOM для прокрутки отсутствует. → Pending не считается успешно выполненным; при следующем представлении с grid hook снова сможет центрировать.
- [Risk] Добавление ID-сигнатуры может повторно запросить центрирование после первой загрузки. → До готовности grid выполнение невозможно, а после готовности происходит один успешный сброс pending.
