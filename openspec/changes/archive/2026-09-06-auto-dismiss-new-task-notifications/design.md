## Context

Новые работы сейчас определяются единым персональным watermark в `user_new_task_notification_state`: все события создания после курсора считаются новыми, а «Отметить все просмотренными» монотонно продвигает курсор. Такой курсор удобен для глобального действия, но не способен отметить одну увиденную работу, не скрыв более старые непросмотренные события.

Основная таблица уже размечает строки атрибутом `data-task-row-id`. Уведомления загружаются через React Query, обновляются раз в пять минут и открывают работу существующим task-only переходом.

## Goals / Non-Goals

**Goals:**

- Автоматически и персонально скрывать новую работу после реального просмотра строки.
- Считать открытие работы из уведомления просмотром.
- Ограничить новизну семью сутками и сохранить существующий watermark для «Отметить все просмотренными».
- Сделать массовое сохранение идемпотентным, безопасным по доступу и экономным по числу запросов.
- Согласовать optimistic UI, повторный фокус вкладки и несколько клиентских сессий.

**Non-Goals:**

- Не менять название и глобальную семантику кнопки «Отметить все просмотренными».
- Не возвращать новизну после редактирования существующей работы.
- Не считать просмотром архив, журнал или граф зависимостей.
- Не добавлять настройку длительности срока и realtime/WebSocket-синхронизацию.
- Не считать обычную загрузку строки вне viewport просмотром.

## Decisions

### Точечные отметки дополняют watermark

Добавляется таблица `user_new_task_notification_seen_events` с составным первичным ключом `(user_id, task_history_id)` и временем просмотра. Запрос новых работ продолжает применять глобальный watermark, а затем исключает события, присутствующие в таблице точечных отметок.

Это сохраняет дешёвое глобальное подтверждение и позволяет независимо скрывать строки в произвольном порядке. Продвижение watermark при просмотре отдельной строки отклонено: оно ошибочно скрыло бы более старые, но ещё не увиденные работы.

### Backend сам проверяет допустимость bulk-отметки

Новый аутентифицированный bulk endpoint принимает уникальные `task_id` с ограничением размера пакета. Backend сопоставляет их единственным событиям создания, проверяет текущий доступ пользователя, исключает удалённые, собственные и уже устаревшие работы и выполняет идемпотентный `INSERT OR IGNORE` в транзакции. Клиент не передаёт автора, дату или history id как доверенные данные.

### Срок новизны применяется в серверной выборке

Все preview, count и пагинируемые запросы включают нижнюю границу `changed_at > now - 7 days`, вычисленную сервером в UTC. Поэтому старые накопленные уведомления исчезнут сразу после развёртывания без миграции пользовательских курсоров. Обычные изменения работы не создают новое событие `create` и не возвращают её в список.

Записи точечных просмотров старше срока больше не влияют на выдачу. Их удаление выполняется ограниченной идемпотентной очисткой вне read-path либо вместе с редкой обслуживающей операцией, а не при каждом открытии колокольчика.

### Новые работы совпадают с активным набором планировщика

Серверная выборка preview, count и пагинируемого списка применяет общий `terminal_task_status_sql` с отрицанием и исключает текущие статусы `done` и `cancelled`. Опция планировщика для показа недавно завершённых не расширяет центр новых работ. Если непросмотренная работа в пределах семисуточного срока возвращается в `new`, исходное событие создания снова удовлетворяет выборке и работа возвращается в уведомления.

Отдельный список статусов в SQL уведомлений отклонён: общий helper сохраняет согласованность с основной таблицей и правилами домена при дальнейшем изменении набора терминальных статусов.

### Просмотр определяется устойчивой видимостью строки

Frontend hook использует `IntersectionObserver` для узкого вертикального маркера внутри фиксированной первой ячейки каждой строки основной таблицы: порог 50%, непрерывная выдержка 1000 мс. Наблюдение всей строки отклонено, поскольку стандартный `intersectionRatio` рассчитывается по площади и у широкой таблицы может никогда не достичь 50%, даже когда строка полностью видима по высоте. Размер маркера повторяет высоту строки, поэтому пересечение порога отражает только вертикальную видимость и порождает события при обычной прокрутке страницы. Падение видимости ниже порога до истечения таймера отменяет отметку. Hook работает после фильтрации, поиска и пагинации, поскольку наблюдает фактически отрисованные строки.

Завершённые ID накапливаются 500 мс и отправляются одним bulk-запросом. Открытие элемента уведомления ставит тот же ID в очередь непосредственно перед навигацией. Архив, журнал и граф наблюдатель не подключают.

### Optimistic cache с откатом

Перед bulk-запросом соответствующие элементы удаляются из preview и страниц React Query, а total корректируется без ухода ниже нуля. При ошибке восстанавливается снимок cache и показывается стандартное сообщение. После успеха запросы инвалидируются для подтверждения серверного состояния.

Возврат вкладки в фокус использует стандартный refetch React Query; периодическое обновление сохраняется. Отдельный канал синхронизации между вкладками не вводится.

## Risks / Trade-offs

- **Много строк одновременно достигают порога** → очередь дедуплицирует ID и отправляет ограниченные bulk-пакеты.
- **Строка исчезает из-за фильтра или виртуализации** → индивидуальный таймер отменяется при `unobserve`/cleanup.
- **Широкая строка имеет малую видимую площадь** → observer следит за узким вертикальным маркером в фиксированной первой ячейке, а не за площадью всей строки.
- **Optimistic total расходится с сервером** → успешная мутация всегда завершает invalidation; ошибка восстанавливает полный снимок.
- **Клиент пытается отметить недоступную работу** → backend повторно проверяет доступ и безопасно игнорирует неподходящий ID без раскрытия данных.
- **Статусы активной таблицы меняются** → выборка уведомлений переиспользует общий доменный helper терминальных статусов вместо собственной копии списка.
- **Граница времени меняется между страницами Drawer** → watermark фиксирует верхнюю границу, а семисуточная нижняя граница вычисляется сервером для каждого запроса; элемент может естественно исчезнуть при достижении срока.
- **Рост таблицы точечных отметок** → индексированная связь и периодическая пакетная очистка записей старше срока.

## Migration Plan

1. Добавить идемпотентную миграцию таблицы точечных просмотров и индексов.
2. Развернуть backend-фильтрацию срока и bulk endpoint; старые клиенты продолжат работать через прежний watermark endpoint.
3. Развернуть frontend-наблюдатель и optimistic cache.
4. После стабилизации включить безопасную пакетную очистку устаревших точечных записей.

При откате frontend перестанет создавать новые отметки, а прежний watermark продолжит работать. Новую таблицу можно оставить без влияния на старую версию; удаление данных для отката не требуется.
