## Context

Команда сейчас является основным контекстом планирования, задач, зависимостей, назначений, статистики и журнала. UI получает общий `/api/teams`, но большинство endpoints также принимают `team_id`, `task_id` или `assignment_id` напрямую, поэтому фильтрация только списка команд не обеспечивает безопасность.

Требуется сохранить обратную совместимость: существующие пользователи не имеют записей ограничений и после миграции должны продолжить видеть все команды. Администратор всегда имеет полный доступ. Ограничение пользователя одновременно определяет доступ к данным и возможность выбрать его исполнителем задачи.

## Goals / Non-Goals

**Goals:**

- Единая модель эффективного доступа к командам.
- Backend-авторизация всех прямых и косвенных операций с командными данными.
- Фильтрация навигации, статистики, журнала и списка исполнителей.
- Настройка разрешённых команд в форме пользователя.
- Безопасная миграция существующей SQLite БД без изменения текущих прав.

**Non-Goals:**

- Отдельные права чтения и записи внутри одной команды.
- Ограничение администратора.
- Иерархия команд или наследование разрешений.
- Изменение текущей ролевой модели `admin/editor/user` вне командного ограничения.

## Decisions

### Таблица разрешений с семантикой «нет строк — все команды»

Добавляется таблица `user_team_access(user_id, team_id)` с составным первичным ключом и каскадным удалением. Непустой набор строк ограничивает пользователя перечисленными командами; отсутствие строк означает все команды. Это не требует backfill и сохраняет права существующих пользователей.

Альтернатива — хранить флаг `all_teams` — делает состояние явнее, но требует миграции и синхронизации флага со связями. Для заданной пользователем семантики пустого выбора отдельный флаг избыточен.

### Централизованные проверки на уровне API

DAO предоставляет операции получения разрешённых ID, проверки эффективного доступа и определения команды по `task_id`/`assignment_id`. В FastAPI используются общие helpers: проверка одного team ID, набора team IDs и связанных сущностей. UI-фильтрация служит только удобству; источником безопасности остаётся backend.

Для явного запроса недоступной команды возвращается `403`. Статистика с явно переданным смешанным списком также получает `403`, чтобы ошибка клиента не маскировалась частичным результатом. Если список не передан, backend сам ограничивает агрегат эффективным набором пользователя.

### Отдельный endpoint исполнителей команды

Модальное окно назначения получает кандидатов из `/api/teams/{team_id}/assignees`. Endpoint возвращает только пользователей с `is_assignee=true`, которым эффективно доступна команда. Пользовательские CRUD-запросы сохраняют текущие форматы и не смешиваются с контекстной выборкой исполнителей.

Backend повторяет ту же проверку при сохранении назначения, поэтому подмена `user_id` не обходит ограничение.

### Сохранение связей в транзакции пользовательского CRUD

`team_ids` добавляется в payload создания/редактирования пользователя. Сохранение пользователя и замена его связей выполняются в одной транзакции. Для роли `admin` связи очищаются или игнорируются, поскольку эффективный доступ администратора всегда полный.

### Создание команды ограниченным редактором

Текущая ролевая модель позволяет редактору создавать команды. Если у редактора уже есть явные ограничения, новая команда автоматически добавляется в его набор; иначе отсутствие строк продолжает означать полный доступ. Изменение и удаление существующих команд требует обычной проверки эффективного доступа.

## Risks / Trade-offs

- [Пропущенный endpoint позволит обход авторизации] → Инвентаризировать все маршруты с `team_id`, `task_id`, `assignment_id` и покрыть прямые/косвенные запросы backend-тестами.
- [Семантика пустого набора не позволяет выразить «нет доступа ни к одной команде»] → Это осознанно соответствует требованию; при необходимости позже добавить явный режим доступа.
- [Удаление последней связи неожиданно расширяет доступ до всех команд] → UI явно поясняет семантику и требует подтверждение при переходе от ограниченного набора к пустому.
- [Дополнительные проверки увеличат число SQL-запросов] → Использовать request-scoped соединение и проверки через `EXISTS`; для агрегатов передавать вычисленный набор разрешённых IDs в существующие DAO-фильтры.
- [Сохранённые в localStorage недоступные team ID] → Planning и Journal проверяют полученный `/api/teams`, очищают недоступное сохранённое значение и переводят пользователя на выбор доступной команды.

## Migration Plan

1. Создать `user_team_access` и индексы идемпотентной миграцией; данные существующих пользователей не добавлять.
2. Добавить DAO и backend helpers, затем закрыть командные endpoints проверками.
3. Расширить пользовательский CRUD и форму настроек.
4. Перевести выбор исполнителя на контекстный endpoint.
5. Проверить роли и обходы прямыми API-запросами, затем production UI.

Rollback: удалить использование таблицы и проверок в коде; сама дополнительная таблица может остаться без влияния на старую версию или быть удалена отдельной миграцией.
