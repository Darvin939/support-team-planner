## Context

Backend запускается непосредственно из каталога приложения, использует относительный путь `database.db`, раздаёт `frontend/dist` и при импорте читает `frontend/src/data/taskTransitions.json`. Сейчас эти зависимости собираются и переносятся вручную. Целевой сценарий — подготовка каталога для копирования на другую машину, где Python-зависимости затем устанавливаются из `requirements.txt`.

## Goals / Non-Goals

**Goals:**

- Одной командой Linux shell получить воспроизводимый каталог дистрибутива.
- Всегда собирать актуальный production frontend перед копированием.
- Копировать явный allowlist runtime-файлов и проверять полноту результата.
- Позволить переопределить выходной каталог, сохранив безопасное значение по умолчанию.

**Non-Goals:**

- Создание standalone executable или включение интерпретатора Python, `node_modules` и Python virtualenv.
- Упаковка пользовательской `database.db`, `.env`, сертификатов или иных локальных данных.
- Поддержка инкрементального обновления уже развёрнутой установки.

## Decisions

1. Добавить корневой исполняемый `build-distribution.sh` для Linux с параметром `--output`, по умолчанию `build/support-team-planner`. Bash доступен в целевом окружении и позволяет прозрачно оркестрировать npm и файловые операции с немедленной остановкой при ошибке. Альтернатива — Python-скрипт — потребовала бы оркестрировать npm через subprocess и не соответствовала требованию shell-скрипта для Linux.
2. Скрипт использует строгий режим Bash, определяет корень проекта независимо от текущего рабочего каталога, сначала выполняет `npm run build` в `frontend`, затем формирует результат во временном соседнем каталоге и только после успешного копирования заменяет целевой каталог. Это не оставляет частично собранный дистрибутив при ошибке. Скрипт откажется использовать корень репозитория как выходной каталог.
3. Использовать явный allowlist: корневые runtime Python-модули, каталог `db`, `requirements.txt`, production launch-скрипты, `frontend/dist` и `frontend/src/data/taskTransitions.json`. Такой подход надёжнее blacklist-копирования всего репозитория и гарантированно исключает БД, секреты, кэши и материалы разработки.
4. Сохранять ожидаемую проектом относительную структуру каталогов, чтобы не менять runtime-код только ради упаковки.
5. Добавить `build/` в `.gitignore` и описать сборку/запуск результата в README.

## Risks / Trade-offs

- [Risk] Новый runtime-файл будет добавлен в код, но не в allowlist → проверка smoke-тестом запуска из собранного каталога и поддержка списка вместе с runtime-зависимостями.
- [Risk] Замена существующего выходного каталога удаляет его прежнее содержимое → разрешать замену только точного нормализованного пути, явно запрещать корень проекта и сначала полностью готовить staging-каталог.
- [Trade-off] Дистрибутив требует установленный Python и установку зависимостей → это намеренно сохраняет простой, прозрачный формат вместо platform-specific executable.

## Migration Plan

После добавления скрипта существующий способ запуска из рабочего дерева останется рабочим. Откат состоит в удалении скрипта и документации; runtime приложения и данные не мигрируются.
