## Context

`AuthenticatedLayout` вызывает `useMe()` и не монтирует вложенный route до завершения запроса. После получения профиля `PlanningPage` и другие потребители монтируют второй observer того же query. При стандартном `staleTime: 0` React Query считает только что полученные данные устаревшими и запускает второй `/api/me`.

## Goals / Non-Goals

**Goals:**

- исключить немедленный повторный `/api/me` при последовательном монтировании потребителей;
- сохранить единый query key и автоматическую фоновую актуализацию после истечения короткого интервала;
- ограничить изменение только query текущего пользователя.

**Non-Goals:**

- глобальная перенастройка React Query;
- передача профиля через новый React context;
- изменение backend endpoint или session-механизма;
- бессрочное кеширование роли пользователя.

## Decisions

### Установить `staleTime` 60 секунд в `useMe`

Минутный интервал значительно длиннее последовательного монтирования layout и страницы, но ограничивает время, в течение которого внешнее изменение роли может оставаться незамеченным открытой вкладкой. Все потребители сохраняют общий query key и получают одни данные из QueryClient.

Альтернативы: пять минут уменьшают запросы сильнее, но дольше скрывают изменение роли; `Infinity` требует явной инвалидации во всех случаях; outlet context устраняет повторный observer ценой дополнительной связности компонентов.

### Не отключать `refetchOnMount` глобально

После истечения `staleTime` стандартное поведение React Query остаётся полезным: новый observer может актуализировать профиль. Другие queries продолжают использовать прежние настройки.

## Risks / Trade-offs

- [Роль пользователя изменена во внешней сессии] → открытая вкладка может показывать старую роль до 60 секунд или следующего штатного refetch; backend всё равно проверяет актуальную роль на каждом запросе.
- [Тест проверяет внутреннюю реализацию вместо поведения] → тест должен монтировать последовательных потребителей с общим QueryClient и считать вызовы query function.
