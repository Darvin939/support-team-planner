## Context

В доменной модели ПСИ уже представлено тремя значениями: `not_required`, `required`, `passed`. Сейчас тот же enum напрямую показан в форме работы, хотя форма одновременно редактирует постоянные свойства работы, а `passed` является результатом отдельного рабочего действия. Маркеры в строке планировщика и серверная блокировка назначений уже опираются на три состояния и менять их не требуется.

Изменение затрагивает форму, контекстное меню, клиентскую мутацию и серверную проверку, поэтому поведение фиксируется сквозным дизайном.

## Goals / Non-Goals

**Goals:**

- Разделить настройку требования ПСИ и фиксацию его результата.
- Не допустить случайного сброса `passed` при обычном сохранении формы.
- Сделать оба перехода результата явными и подтверждаемыми.
- Сохранить существующие бейджи, блокировку планирования, права и аудит.

**Non-Goals:**

- Изменение enum `psi_status`, схемы БД или внешнего вида бейджей.
- Разрешение назначений для `required`.
- Обход ограничения на включение `required` при существующих назначениях.

## Decisions

### Чекбокс является представлением требования, а не нового булевого поля

В форму вводится булево значение уровня представления. При открытии оно включено для `required` и `passed`. При сохранении применяются правила:

- выключен — отправить `not_required`;
- включён после исходного `not_required` — отправить `required`;
- включён при исходном `required` или `passed` — сохранить исходное состояние.

Если у работы есть хотя бы одно неудалённое назначение, checkbox блокируется и форма обязана сохранить исходный `psi_status`. Признак наличия назначений передаётся в `TaskOut`; frontend использует его для немедленной блокировки, а backend повторяет проверку для защиты от устаревших данных и прямых запросов.

Это сохраняет трёхсоставную доменную модель и не требует миграции. Альтернатива с отдельным булевым полем требования создала бы две потенциально противоречащие друг другу характеристики.

### Результат меняется узкой мутацией из контекстного меню

Для активных `required` и `passed` работ контекстное меню показывает одно релевантное действие. Оно открывает `Modal.confirm`; после подтверждения клиент отправляет только новый `psi_status`, затем инвалидирует данные работ, назначений и зависимых представлений так же, как другие мутации работы.

Предпочтительна отдельная операция изменения ПСИ, которая принимает идентификатор работы и целевое состояние `required` либо `passed`. Она не заставляет контекстное меню собирать и повторно отправлять всю форму работы и уменьшает риск перезаписи параллельно изменённых полей. Альтернатива — переиспользовать полное обновление работы — оставляет лишнюю связанность и риск устаревшего payload.

### Сервер остаётся источником истины для ограничений

Операция использует те же проверки доступности команды, активности работы и запрета `passed` → `required` при любых назначениях, а успешное изменение попадает в историю. Полное обновление работы дополнительно запрещает менять само требование в обе стороны при назначениях: как `not_required` → `required`, так и `required`/`passed` → `not_required`. Пункт возврата `passed` → `required` можно показывать, но окончательное решение принимает backend, поскольку данные видимого диапазона планировщика не доказывают отсутствие назначений на других датах.

### Отображение не меняется

`PsiStatusBadge`, его подписи, цвета и расположение рядом с сегментом остаются без изменений. Меняется только элемент управления в форме и состав контекстного меню.

## Risks / Trade-offs

- [Пользователь подтверждает `passed` → `required`, но у работы есть невидимое назначение] → backend отклоняет запрос штатным сообщением; frontend показывает ошибку и обновляет данные без оптимистической подмены.
- [Сохранение формы с исходным `passed`] → преобразование checkbox-to-enum обязательно покрывается component-тестом для всех исходных состояний.
- [Клиент использует устаревший признак назначений] → backend запрещает двустороннее изменение требования и возвращает понятную ошибку.
- [Дублирование проверок между полным обновлением и узкой операцией] → вынести общую серверную валидацию перехода ПСИ в одну функцию либо вызвать существующий общий путь обновления без повторения правил.

## Migration Plan

Миграция данных не требуется. Изменение разворачивается совместно для backend и собранного frontend. Откат возвращает прежний Select и удаляет узкую клиентскую операцию; сохранённые значения остаются совместимыми.
