## Context

Мотивация описана в proposal.md. Текущий DAO уже читает `tasks.completion_template_id`, но собирает статусы всех затрагивающих шаблон назначений. Router проверяет его только при переходе одного назначения в `success`; bulk игнорирует результат. Frontend хранит предложение в локальном состоянии страницы и не получает готовность через чтение работ. Данные назначений планирования ограничены диапазоном дат и не подходят для полной проверки.

## Goals / Non-Goals

**Goals:** один backend-расчёт готовности для чтения и изменений, устойчивое действие строки, предложения по окончательному результату операции, отсутствие потерь в bulk и повторных окон при фоновом чтении.

**Non-Goals:** нормализация хранения блоков назначений, версии шаблонов, автоматическое завершение, изменение общего ручного перехода статуса и прав, автоматическое заполнение старых NULL-шаблонов.

## Decisions

### Вычислять успешное покрытие на backend

Источник требований — текущий состав шаблона, связанного с работой. Источник выполнения — все неудалённые назначения этой работы со статусом `success`. Разбирать существующее строковое поле блоков с удалением пробелов и пустых токенов. Готовность означает непустой набор требований, полностью покрытый успешными блоками, и допустимый переход в `done`. Дубли и остальные статусы не участвуют в покрытии и не блокируют его. Отсутствующая/пустая связь и терминальная/удалённая работа не дают готовности.

Проверку всех релевантных статусов удалить; отдельный поиск/выбор шаблона для завершения не вводить. Сопоставление по названиям сохраняется, поскольку назначения не хранят идентификаторы блоков. Смещения и даты не влияют на готовность.

### Возвращать готовность вместе с работами

Добавить булево поле готовности в API-модель работы и TypeScript-модель. Общий backend-расчёт использовать при чтении списков и отдельных работ; для списков получать данные пакетно, без запроса на каждую строку. Не хранить вычисляемое состояние в БД: изменение живого шаблона должно отражаться после нового чтения. Альтернатива — frontend-расчёт по видимым назначениям — теряет историю за пределами диапазона.

### Разделить чтение готовности и предложение после операции

Чтение страницы только обновляет доступное действие. Успешные операции с назначениями и выбором шаблона повторно оценивают затронутые работы по окончательному состоянию; переход из неготовности в готовность возвращает предложение. Одиночные и массовые сохранения, удаления и отмены используют одинаковое правило. В bulk оценивать результат всей транзакции, а не промежуточные состояния отдельных записей; ошибки и rollback не создают предложений. При переносе назначения между работами учитывать обе работы.

Существующее одиночное поле ответа можно сохранить для совместимости; массовые операции должны доставлять предложения для всех затронутых работ. Frontend-hooks не должны выбрасывать тело ответа. Несколько предложений показывать последовательно, без потери работ. Инвалидация назначений должна обновлять и готовность работ; проверить также изменения шаблонов и сохранение самой работы.

### Сохранить подтверждение и доступное действие

В строке готовой работы редактору/администратору показывать явное действие «Завершить работу», открывающее существующий диалог подтверждения. Уточнить текст диалога: выполнены блоки шаблона, а не все назначения. Подтверждение использует существующий переход в `done` с общей картой переходов, не создавая отдельного способа изменения статуса. Обычному пользователю недоступное действие и предложение не показывать.

После отказа действие остаётся; фоновое обновление, повторное открытие страницы и правка комментария уже готовой работы не открывают окно автоматически. Если покрытие потеряно, действие исчезает и устаревшее предложение снимается. Возвращение готовности после нового изменения может вновь вызвать предложение. Существующий общий ручной переход в `done` сохраняет свои правила и не становится зависимым от шаблона.

## Risks / Trade-offs

- Сопоставление по строковым названиям ограничено текущим форматом хранения → использовать единый разбор; не расширять задачу миграцией связей блоков.
- Чтение всей истории может удорожить список работ → пакетная выборка по ID возвращаемых работ, выбор только нужных полей.
- Живой шаблон и параллельные изменения могут сделать окно устаревшим → обновлять готовность после изменений и снимать предложение при потере готовности; стандартные права и переходы проверяет backend.
- Обновление invalidation может открыть повторные окна → предложения только из результата пользовательской операции, чтение лишь управляет доступным действием.

## Migration Plan

Миграция БД не нужна. Развернуть backend и свежую production-сборку frontend совместно. Старые ссылки и NULL сохранить. Backend- и component-тестами проверить покрытие и доставку предложений; production UI проверить с реальной авторизацией, резервированием/восстановлением БД через SQLite backup API и остановкой только запущенных для теста процессов. Откатить код и frontend-сборку без преобразования данных.
