## Context

SQLite-хранилище использовало только `PRAGMA user_version` и пропускало все шаги с номером не выше записанной версии. Опубликованная миграция 11 первоначально создавала `user_notification_state`, затем её тело было изменено на `user_new_task_notification_state` без нового номера. Реальная предоставленная БД осталась на версии 11 со старой таблицей; также возможна версия 12 без канонической таблицы. Прежний runner не обнаруживал изменение уже опубликованной истории.

Рабочая БД должна исправляться автоматически версионированным шагом, без уменьшения `user_version` и без ручного SQL. Изменения должны работать как при отдельном pre-deploy запуске, так и при штатной инициализации backend.

## Goals / Non-Goals

**Goals:**

- Без потери прогресса просмотра исправить варианты схемы уведомлений, встречающиеся при `user_version = 11` и `user_version = 12`.
- Гарантировать, что ошибочный шаг не повышает версию и не оставляет частичных изменений.
- Обнаруживать некорректные данные в repair-операции, неизвестную будущую версию и расхождение журнала с manifest миграций.
- Предоставить отдельный pre-deploy способ применения тех же миграций и проверок.
- Покрыть исторические состояния изолированными backend-тестами.

**Non-Goals:**

- Изменение поведения HTTP API или frontend уведомлений.
- Универсальное автоматическое исправление произвольной повреждённой БД.
- Восстановление физически повреждённого файла SQLite.
- Редактирование или повторный запуск миграции 11 на production-БД.

## Decisions

### 1. Исправление выполняется новой миграцией 13

Миграция определяет наличие таблиц через `sqlite_master`, проверяет их столбцы через SQLite metadata и обрабатывает четыре случая:

- только `user_notification_state`: после проверки совместимости переименовывает её в `user_new_task_notification_state`;
- обе таблицы: переносит в каноническую таблицу по одной записи на пользователя с максимальным лексикографическим курсором `(new_tasks_seen_at, new_tasks_seen_history_id)`, проверяет результат и удаляет legacy-таблицу;
- только каноническая таблица: проверяет её и не меняет данные;
- ни одной таблицы: создаёт каноническую таблицу и инициализирует существующих пользователей текущим максимальным курсором истории, чтобы старые работы не стали новыми.

Пустое время нормализуется теми же правилами сравнения, что использует доменный запрос уведомлений. Строки отсутствующих пользователей не переносятся: наличие таких строк считается нарушением целостности и останавливает миграцию. Альтернатива — исправить миграцию 11 или снизить `user_version` — отклонена, потому что повторный запуск исторических шагов недетерминирован и может затронуть уже применённые изменения.

### 2. Исправление ограничено известными состояниями

Перед переносом миграция проверяет обязательные столбцы, первичный и внешний ключи. Неизвестная форма одноимённой таблицы приводит к ошибке с диагностикой, а не к эвристическому преобразованию. Это отделяет безопасный repair от попытки автоматически чинить произвольные повреждения.

### 3. Шаг и встроенные проверки составляют одну транзакцию

Runner открывает явную write-транзакцию для каждого шага. В неё входят изменение схемы и данных, встроенные в операцию локальные проверки, запись журнала и `PRAGMA user_version`. Commit выполняется только после успеха всех операций; исключение приводит к rollback. Использование `executescript`, способного нарушить границы транзакции Python sqlite3, заменяется транзакционно безопасным выполнением statements там, где это необходимо.

Миграция 13 до преобразования проверяет структуру участвующих таблиц и отсутствие orphan-ссылок, а при объединении повторно проверяет ссылки до удаления legacy-таблицы. Runner после применяемого шага требует пустой результат `PRAGMA foreign_key_check`.

### 4. Реестр неизменяемых миграций дополняется журналом checksum

Создаётся служебная таблица журнала с номером, стабильным именем, SHA-256 checksum канонического описания миграции и временем применения. Для существующей БД следующий применяемый шаг фиксирует baseline ранее записанных в `user_version` версий из поставляемого manifest. Для новых применений запись создаётся вместе с шагом.

При последующих запусках несовпадение имени/checksum, пропуск или лишняя запись является ошибкой. `user_version` сохраняется для совместимости, но сверяется с журналом. Альтернатива — полагаться только на номер — отклонена, поскольку номер не обнаруживает изменение кода.

### 5. Runner проверяет историю и новые шаги без общего schema audit

До запуска проверяются уникальность и непрерывность всего реестра, даже если БД уже актуальна, условие `user_version <= latest` и соответствие существующего журнала manifest. При применении нового шага runner выполняет `PRAGMA foreign_key_check`; ошибки шага или проверки откатывают его целиком. Общий audit всех таблиц и доменных инвариантов при актуальном `user_version` не выполняется: исправлять данные вправе только явно зарегистрированная миграция.

`PRAGMA foreign_key_check` выполняется после каждого изменяющего шага. `PRAGMA quick_check` выполняется pre-deploy командой, но не при штатном startup.

### 6. Один движок для pre-deploy и startup

Отдельная CLI-команда открывает БД тем же backend-кодом, выполняет миграции и `quick_check`, после чего завершается. Инициализация приложения вызывает тот же идемпотентный runner без дополнительного полного schema audit. Перед production-запуском CLI оператор создаёт WAL-безопасную резервную копию через SQLite backup API.

## Risks / Trade-offs

- [Две таблицы содержат расходящиеся курсоры] → Выбирается максимальная пара, что сохраняет наиболее продвинутую отметку и не показывает уже просмотренные работы повторно.
- [Ручной schema drift при актуальной версии не обнаруживается общим startup audit] → Production pre-deploy выполняет `quick_check`, а необходимые структурные гарантии оформляются целевыми проверками новых миграций.
- [Checksum нельзя достоверно восстановить для шагов, применённых до появления журнала] → Ранее записанные в `user_version` шаги получают явно версионированный baseline manifest; последующие запуски обнаруживают расхождения журнала.
- [Длительная write-транзакция задержит конкурирующие записи] → Repair выполняется pre-deploy до обслуживания трафика; операции ограничены небольшими таблицами состояния.
- [Удаление legacy-таблицы усложняет откат приложения] → Перед rollout обязательна backup-копия; откат выполняется восстановлением backup вместе с предыдущей версией приложения.

## Migration Plan

1. До остановки старой версии создать уникальную WAL-безопасную backup-копию SQLite через backup API и проверить её открытие.
2. Остановить экземпляры backend, выполняющие запись.
3. Запустить новую pre-deploy CLI-команду. Она применит миграцию 13, проверит журнал, встроенные условия repair-операции, внешние ключи и `quick_check`.
4. Проверить `user_version = 13`, наличие канонической таблицы, отсутствие legacy-таблицы и успешный итог команды.
5. Запустить backend; startup повторит идемпотентную проверку без изменения данных.
6. При неуспешной миграции устранить диагностированную причину: транзакция оставит БД на исходной версии 11 или 12. При необходимости отката после успешного deploy остановить backend и восстановить проверенную backup-копию через SQLite backup API вместе со старой версией приложения.
