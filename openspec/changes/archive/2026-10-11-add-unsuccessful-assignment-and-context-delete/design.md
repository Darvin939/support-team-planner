## Context

См. мотивацию в `proposal.md` и поведенческие контракты в delta-spec. Статусы назначений продублированы в Python `Literal`, TypeScript union и общих справочниках UI. SQLite хранит статус текстом без ограничивающего CHECK. Признак активных назначений сейчас вычисляется SQL-условием, исключающим только `cancelled`.

Контекстное меню календарной ячейки создаётся внутри колонок планирования. Сейчас оно целиком отсутствует у роли `user`, при обязательном непройденном ПСИ и у терминальной работы, поскольку содержит только смену статуса. Одиночное мягкое удаление и инвалидирующая frontend-мутация уже существуют и используются модальным окном назначения.

## Goals / Non-Goals

**Goals:**

- Сохранить единый перечень статусов между backend и frontend.
- Явно отделить доступность контекстного меню от доступности смены статуса, чтобы удаление оставалось возможным в заблокированных состояниях.
- Повторно использовать существующие endpoint, мутацию, cache invalidation и тематизированное программное подтверждение.
- Обеспечить совместимость Python 3.9.

**Non-Goals:**

- Не заменять и не переопределять статус `rollback`.
- Не менять физическую модель мягкого удаления и не добавлять миграцию БД.
- Не давать роли `user` права удаления или смены статуса.
- Не менять правила копирования успешных назначений: `unsuccessful` не является успешным.

## Decisions

### 1. Каноническое значение статуса — `unsuccessful`

Значение добавляется в backend-модель и frontend-тип/справочники, а подпись остаётся локализованной как «Неуспешно». Это сохраняет англоязычный стиль существующих кодовых значений и не связывает новый исход с `rollback`.

Альтернатива `failed` короче, но хуже совпадает с согласованным предметным термином и может ошибочно восприниматься как техническая ошибка выполнения.

### 2. Неактивность задаётся явным множеством завершённых исходов

SQL-правило активного назначения должно исключать как `cancelled`, так и `unsuccessful`. Тесты закрепят оба значения, чтобы новый статус не начал блокировать управление ПСИ или другие действия, использующие `has_active_assignments`.

Альтернатива — считать активными только заранее перечисленные рабочие статусы. Это масштабнее и может непреднамеренно изменить семантику `success` и `rollback`, поэтому не входит в данное изменение.

### 3. Меню строится из независимых секций действий

Для `editor` и `admin` оболочка контекстного меню присутствует у любого назначения. Секция смены статуса добавляется только при действующих правилах редактирования; отделённое опасное удаление добавляется всегда. Для `user` контекстное меню назначения не создаётся.

Это позволяет удалить назначение при терминальной работе или непройденном ПСИ, не ослабляя запрет изменения статуса.

### 4. Удаление использует программное тематизированное подтверждение

Выбор пункта закрывает меню и открывает подтверждение через контекстный Ant Design modal API. После подтверждения вызывается существующая одиночная delete mutation с теми же инвалидируемыми запросами и сообщением об успехе, что и при удалении из формы.

Программное подтверждение предпочтительнее вложенного `Popconfirm`: пункт Dropdown исчезает после выбора, а modal стабильно переживает закрытие меню и соответствует существующей спецификации темы.

### 5. Проверки распределяются по слоям

Backend-тесты закрепляют допустимый enum и неактивность `unsuccessful`. Vitest + React Testing Library проверяют наличие статуса, права и заблокированные состояния меню, подтверждение/отмену и вызов удаления. Production Playwright-сценарий проверяет реальное контекстное меню, модальное подтверждение и исчезновение назначения после backend-операции с обязательным backup/restore БД.

## Risks / Trade-offs

- [Статус может быть добавлен не во все локальные union/справочники] → проверить типы, OpenAPI enum, фильтры, статистику, историю и визуальные компоненты отдельными тестами и TypeScript-сборкой.
- [Общая красная семантика с `rollback`] → различать состояния текстовой подписью и отдельной иконкой в меню; цвет сам по себе не является единственным сигналом.
- [Удаление из заблокированной ячейки может случайно вернуть редактирование] → строить удаление независимо, но сохранять прежние guards для секции статусов и открытия формы.
- [UI-тест изменяет рабочую SQLite БД] → использовать SQLite backup API, остановить запущенный тестом backend и восстановить БД с WAL checkpoint согласно правилам проекта.

## Migration Plan

Миграция схемы и существующих строк не требуется. Развёртывание backend и собранного frontend должно выполняться одной версией, чтобы новый enum принимался API и корректно отображался клиентом. Откат к предыдущей версии безопасен только если до отката в БД нет строк `unsuccessful`; иначе сначала следует преобразовать такие строки в выбранный поддерживаемый старой версией статус.
