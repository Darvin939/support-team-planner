## Context

Страница статистики получает пагинированный список активных назначений и общие агрегаты, но не агрегаты по датам. Группировка пагинированных `items` дала бы заниженные счётчики. RangePicker показывает две панели и также отображает в их сетках даты соседних месяцев.

## Goals / Non-Goals

**Goals:**

- Получать точные подневные счётчики одним агрегированным запросом за полный видимый диапазон календарных сеток.
- Повторно использовать семантику активности и правила доступа текущей статистики.
- Встроить компактный бейдж без подмены стандартного DOM-узла даты.
- Не блокировать стандартные взаимодействия календаря во время загрузки или ошибки счётчиков.

**Non-Goals:**

- Считать завершённые или отменённые работы.
- Делать бейдж отдельным фильтром или ссылкой.
- Раскрывать точное значение, если количество равно `10` или больше.
- Менять схему БД, лимит выбора периода или стандартное начальное позиционирование панелей RangePicker.

## Decisions

### Отдельная API-выборка для счётчиков

Backend предоставляет лёгкую выборку `date/count` с параметрами начала, конца и команд. SQL переиспользует общий WHERE активных назначений и добавляет `GROUP BY a.date`. Активными считаются работы, у которых назначение на дату имеет статус `new` или `planned`; исключаются soft-deleted назначения, soft-deleted задачи и задачи в терминальном статусе. Ограничение уникальности `(task_id, date)` гарантирует, что одна работа учитывается на дате не более одного раза.

Endpoint применяет тот же effective team access, что и текущая статистика: выбранные команды проверяются на доступность, а отсутствие явного фильтра ограничивается доступными пользователю командами. Начальная и конечная даты валидируются, начало не может быть позже конца.

### Диапазон запроса определяется полной видимой сеткой

Frontend хранит базовый видимый месяц и вычисляет непрерывное окно, покрывающее все ячейки обеих панелей, включая spillover-даты соседних месяцев. RangePicker сообщает каждое изменение видимого месяца через `onPickerValueChange`; обработчик обновляет базовый месяц, query key меняется и React Query выполняет запрос для нового окна. `onPanelChange` для этой цели не используется, поскольку в текущем rc-picker это legacy-событие смены режима панели и оно не гарантирует уведомление о каждом перелистывании. Стандартная логика Ant Design определяет начальное положение панелей при открытии.

Старые данные не используются как placeholder между разными командами или видимыми диапазонами, чтобы календарь кратковременно не показывал неверные количества.

### Расширение исходной ячейки

`cellRender` оборачивает `originNode` и добавляет неинтерактивный бейдж только для типа `date` и ненулевого count. Это сохраняет встроенные ARIA-атрибуты, обработчики и классы состояний.

Бейдж размещается в правом верхнем углу ячейки и остаётся визуально вторичным относительно номера дня. Значения `1–9` показываются точно, значения `10+` — как `9+`. Tooltip и иной способ раскрыть точное значение не добавляются.

Бейдж получает слой выше фоновых псевдоэлементов выбранного диапазона, поэтому не обрезается и остаётся читаемым на всех датах между началом и концом. Для начальной и конечной даты используется контрастное оформление относительно основной заливки. На ячейке непосредственно под курсором бейдж целиком и плавно скрывается, вместо частичного перекрытия стандартным hover-состоянием.

### Загрузка и ошибки

До завершения запроса календарь отображается без счётчиков и остаётся полностью доступным для выбора дат. При ошибке календарь также остаётся рабочим, а пользователь получает одно общее неблокирующее уведомление. Ошибка не отображается отдельно в каждой ячейке.

## Risks / Trade-offs

- Частая навигация может порождать лишние запросы → React Query кэширует каждый диапазон; обновление привязано к изменению месяца, а не к hover.
- Бейдж может перегрузить ячейку на узком экране → используется максимум два символа `9+`, абсолютное позиционирование и production-проверка desktop/mobile.
- Псевдоэлементы hover и выбранного диапазона могут частично перекрывать бейдж → бейдж располагается выше слоя диапазона, получает контраст на его границах и целиком исчезает только у hovered-ячейки.
- Spillover-даты расширяют API-окно относительно двух календарных месяцев → диапазон всё равно ограничен двумя стандартными календарными сетками и агрегируется на стороне БД.
- Отсутствие счётчиков можно принять за нулевые значения при ошибке → показывается одно общее уведомление.

## Test Strategy

- DAO/API: группировка разных работ по дате без удвоения одной работы; статусы назначения; soft-delete назначения и задачи; терминальные статусы задачи; фильтрация команд; effective team access; недоступная команда; границы и порядок дат.
- Vitest + React Testing Library: точные значения `1–9`; `9+` для `10+`; отсутствие нуля; spillover-даты; `onPickerValueChange`; loading/error; сохранение `originNode` и взаимодействий RangePicker; CSS-состояния диапазона и hover.
- Production Playwright: реальная авторизация и backend, обе панели, desktop/mobile layout, выбор диапазона, визуальные слои бейджей, перелистывание с фактическим новым HTTP-запросом и общее уведомление при ошибке, если оно воспроизводимо без изменения production-кода.

## Migration Plan

Изменение аддитивно: схема БД не меняется, новый API не ломает текущих клиентов. Откат состоит в удалении frontend-вызова/бейджа и нового endpoint/DAO-метода.
