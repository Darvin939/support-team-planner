## Context

Пять связанных endpoints зависимостей задач и локальная функция `_validate_task_dependency_edit` находятся в `support_planner.py`. Сигнал `TaskDependencyCycleError` также объявлен в entrypoint, хотя используется как часть атомарного сохранения задачи. Уже выделенные routers используют общие `access_control`, `api_models` и `query_parsing`, поэтому новый срез может следовать тому же шаблону без изменения публичного API.

## Goals / Non-Goals

**Goals:**

- Сгруппировать чтение графа, список кандидатов и точечные mutation зависимостей в отдельном `APIRouter`.
- Оставить общее правило проверки пары задач в одном переиспользуемом backend-модуле.
- Сохранить порядок регистрации и точные FastAPI/OpenAPI-контракты.
- Закрепить поведение unit/API/OpenAPI regression tests.

**Non-Goals:**

- Изменение модели хранения или алгоритма поиска циклов.
- Изменение frontend, URL, payload или текстов ошибок.
- Перенос основного CRUD задач, который останется отдельным следующим срезом.
- Добавление WebSocket или нового transport-протокола.

## Decisions

### 1. Один router для чтения и точечных mutation зависимостей

Будет создан `routers/task_dependencies.py` с пятью существующими маршрутами. Они образуют одну предметную группу и используют одинаковые access-control и query parsing зависимости.

Альтернатива — разделить graph/read и mutation routers — создаёт лишние модули при малом объёме и усложняет порядок подключения.

### 2. Доменная проверка пары задач не будет возвращать HTTP response

Общий модуль правил зависимостей будет получать две задачи через существующий DAO и возвращать структурированный результат либо поднимать узкое доменное исключение с сохранёнными status/message. Router преобразует его в текущий `JSONResponse`. `TaskDependencyCycleError` также будет находиться в этом модуле, чтобы сохранение основной задачи не зависело от router.

Альтернатива — перенести `_validate_task_dependency_edit` в router как есть — оставляет HTTP-деталь внутри общей доменной проверки и затрудняет её unit-тестирование.

### 3. Router подключается до оставшихся task catch-all маршрутов

`include_router` будет расположен так, чтобы `/api/tasks/{team_id}/deps`, `/dependency-graph` и `/active-list` сохраняли приоритет и прежние operation paths. OpenAPI regression test сравнит методы, параметры и request schema.

### 4. Существующие общие модули переиспользуются

Router импортирует `TaskDependencyIn` из `api_models`, entity checks из `access_control` и `parse_int_csv` из `query_parsing`. Дублирующие реализации не создаются.

## Risks / Trade-offs

- [Risk] Изменение порядка route registration может направить специфичный URL в параметризованный handler → подключить router в прежней логической позиции и проверить все пять путей API-тестами.
- [Risk] Новый формат доменного исключения может изменить status или текст ошибки → зафиксировать точные 404/400 ответы тестами до удаления старой реализации.
- [Risk] Проверка доступа только к одной стороне связи ослабит изоляцию команд → сохранить вызов `require_task_access` для `task_id` и `depends_on_task_id` и покрыть отказ тестом.
- [Trade-off] Entry point продолжит импортировать cycle exception до будущего переноса основного task router; это осознанная временная зависимость между модулями.
