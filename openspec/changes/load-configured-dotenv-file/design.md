# Design

## Context

Мотивация — в [proposal.md](proposal.md). `backend/__init__.py` импортирует settings до прикладных модулей; CLI миграции и переноса также используют этот загрузчик. Сейчас settings выполняет `load_dotenv(override=False)`, а TLS-модуль повторяет автоматический поиск `.env`. Пользователь предоставил dotenv-шаблон Vault KV v1 без `export`, с каталогом `/config/secret/planner-env`.

## Goals / Non-Goals

**Goals:** один путь к dotenv-файлу для приложения и CLI, приоритет окружения, точные значения секретов и отказ при недоступном явно настроенном файле.

**Non-Goals:** Vault-клиент, исполнение shell-файлов, несколько конфигурационных файлов, автоматическое обновление окружения, автоматические миграции и развёртывание Kubernetes.

## Decisions

### 1. Один параметр существующего загрузчика

`SUPPORT_PLANNER_ENV_FILE` задаётся в окружении до запуска Python. Settings читает файл через UTF-8 поток и `load_dotenv` с `override=False, interpolate=False`. Указанный файл заменяет автоматический поиск `.env`; путь с пробелами поддерживается. Без переменной стандартный поиск и dotenv-интерполяция сохраняются. `SUPPORT_PLANNER_SKIP_DOTENV=1` отключает оба режима.

Окружение имеет приоритет, включая пустые строки. Файл не исполняется как shell. Внешний файл сохраняет `${...}` и `$()` буквально. Проверка PostgreSQL URL остаётся в существующем модуле подключения.

### 2. Ошибка чтения останавливает запуск

Ошибка открытия или UTF-8 декодирования выбранного файла превращается в понятную ошибку `SUPPORT_PLANNER_ENV_FILE`, без содержимого файла и цепочки исходной ошибки. Пустое заданное имя также ошибочно. Нет перехода к автоматическому `.env` при ошибке или дополнения из него после успешного чтения. Пустой читаемый файл допустим; проверка прикладных значений остаётся прежней.

### 3. Единая загрузка

Удалить импорт и вызов `load_dotenv` из TLS-модуля. При импорте модуля через пакет backend settings уже загружен. Это исключает дополнение настроек из другого `.env` и сохраняет тестовое отключение dotenv.

### 4. Прямой запуск контейнера

Удалить добавленные `docker-entrypoint.sh` и его тесты, а также только связанные с ними правки Dockerfile, `.dockerignore` и `build-distribution.sh`. Сохранить исходные ENTRYPOINT/CMD и остальные настройки образа. Settings уже входит в дистрибутив через существующий backend allowlist.

### 5. Пример пользователя

Пример Vault KV v1 создаёт один файл `env` в `/config/secret/planner-env` с URL PostgreSQL, схемой, session secret и `PGPASSWORD`. Значения экранируются по правилам dotenv. `agent-inject-secret-env` содержит путь к секрету, глобальная `agent-inject` включает инжекцию. Deployment задаёт `SUPPORT_PLANNER_ENV_FILE`; CLI используют тот же механизм со своими migration-реквизитами. Изменение секретов требует перезапуска процесса.

## Risks / Trade-offs

- Файл не подготовлен → запуск завершается до выбора хранилища.
- Секрет содержит `${...}` → интерполяция внешнего файла отключена.
- Файл изменился после startup → требуется перезапуск.

## Verification

Unit-тесты исполняют копию settings во временном каталоге, не читая рабочий `.env`: явный файл, приоритет окружения, стандартный поиск, skip-флаг, ошибки чтения и точность секретов. Subprocess-тесты проверяют выбор PostgreSQL без подключения и отказ до открытия БД. Python-процессы получают UTF-8 окружение и завершаются по timeout/finally; код совместим с 3.9.

Выполняются существующие тесты схемы и конфигурации хранилища. Свежий дистрибутив проверяется на отсутствие wrapper, наличие обновлённого settings и работу CLI `--help`. Реальные Vault, Kubernetes и корпоративный Docker при недоступности не считаются проверенными; другие изменения сохраняют свою приёмку.
