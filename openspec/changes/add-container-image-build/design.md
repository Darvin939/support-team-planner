# Сборка образа из дистрибутива

## Context

Мотивация описана в [proposal.md](proposal.md). `build-distribution.sh` уже вызывает `npm run build`, проверяет `index.html` и `taskTransitions.json`, формирует каталог по allowlist и ZIP без внешнего каталога-обёртки. Он генерирует `app_build_metadata.json`, поэтому дополнительный механизм версии образу не нужен.

Backend раздаёт frontend из `frontend/dist`, читает JSON переходов статусов и файлы версии. `python support_planner.py` запускает приложение на `0.0.0.0:5093`, использует существующий выбор HTTP/TLS и пишет ротируемый `application.log` в рабочий каталог. PostgreSQL требует отдельно подготовленной схемы.

## Goals / Non-Goals

**Цель:** распакованный артефакт первой job содержит весь проектный ввод для Docker-сборки; пользователь добавляет только свою конфигурацию pip. Образ сохраняет существующие runtime-пути и поведение приложения.

**Границы:** конфигурацию job 2 пользователь создаёт самостоятельно. Для этого изменения достаточно файлов упаковки и документации; код приложения, логирование, health endpoints и схема БД не меняются. Образ рассчитан на согласованные доступные для записи `/app` и `/tmp`; поддержка случайного UID и файловой системы только для чтения не заявляется.

## Decisions

### 1. Docker-контекст — корень распакованного ZIP

Первая job устанавливает npm-зависимости в `frontend`, затем вызывает `./build-distribution.sh`. Скрипт выполняет единственную frontend-сборку и создаёт `build/support-team-planner.zip` либо архив по `--output`. Вторая job получает архив, распаковывает его, добавляет `pip.conf` и запускает сборку в этом каталоге.

Dockerfile и `.dockerignore` хранятся в корне исходников и добавляются в `runtime_files` существующего скрипта. `pip.conf` в этот список не включается. Подготовка дистрибутива остаётся независимой от Docker и конфигурации pip.

Альтернативы — сборка frontend в Docker или Docker-сборка из checkout с отдельным `frontend/dist` — отклонены пользователем в пользу существующего дистрибутива.

### 2. Одна стадия Python на согласованной базе

Используется точный базовый образ из примера: `docker-dev.registry-ci.delta.mysecure_57117ba4eem0.ru/ubi8/python-312:latest`. Порядок установки повторяет пример: `WORKDIR /app`, копирование `pip.conf`, `ENV PIP_CONFIG_FILE=./pip.conf`, копирование `requirements.txt`, обновление pip и установка зависимостей с `--no-cache-dir`. Runtime-файлы копируются после зависимостей, чтобы изменение приложения не требовало повторной установки пакетов при доступном Docker-кэше.

Содержимое `pip.conf` поставляет пользователь. Его источник не заменяется и файл сохраняется в образе согласно выбранному `COPY`. BuildKit secrets и иная схема конфигурации не вводятся. Node и npm в образ не устанавливаются.

### 3. Явный состав runtime

Dockerfile копирует `support_planner.py`, `backend/` с SQL-файлами, `frontend/dist/`, `application_version.json`, `changelog.json`, `app_build_metadata.json`, а также `scripts/__init__.py`, `scripts/migrate_database.py` и `scripts/import_sqlite_to_postgres.py`. Копирование всего контекста через `COPY . .` не используется. Demo-генераторы и host launch-скрипты для запуска контейнера не требуются.

Проверка обязательных `frontend/dist/index.html` и `frontend/dist/taskTransitions.json` входит и в Docker-сборку: артефакт мог быть неполным после передачи. Отсутствие обязательных копируемых файлов также приводит к ошибке сборки. `app_build_metadata.json` сохраняется из архива; Docker-сборка не генерирует новый ID и не требует `.git`.

`.dockerignore` исключает посторонние локальные данные и development-файлы, сохраняя доступность runtime, готового frontend, метаданных и добавленного пользователем `pip.conf`.

### 4. Права и точка запуска

Подготовка каталогов и установка зависимостей выполняются с необходимыми build-правами. Итоговый Dockerfile явно выбирает непривилегированный числовой UID `1001` и группу `0`; `/app` принадлежит этому пользователю. `/tmp` должен оставаться доступным для временных TLS-файлов. Работу под этим UID проверяют на настоящем базовом образе; наличие именованного пользователя не предполагается.

Образ задаёт `PYTHONUNBUFFERED=1`, `PYTHONDONTWRITEBYTECODE=1`, `PYTHONPATH=/app`, объявляет `EXPOSE 5093` и использует exec-форму `CMD ["python", "support_planner.py"]`. Это сохраняет выбранный запуск и позволяет передавать сигнал остановки процессу приложения напрямую.

Логи продолжают записываться в `/app/application.log`; `PYTHONUNBUFFERED` не превращает файловое логирование в stdout. Требование записи относится и к каталогу, поскольку используется ротация. Документация явно описывает это поведение.

### 5. PostgreSQL настраивается при запуске

Документация использует существующие `SUPPORT_PLANNER_DATABASE_URL`, libpq-параметры и `SESSION_SECRET_KEY`. До запуска приложения оператор отдельно выполняет `python -m scripts.migrate_database --postgresql` из того же образа с migration-ролью, затем запускает приложение с runtime-ролью. В образ не включаются БД, значения подключения или session secret.

Dockerfile не меняет SQLite-default приложения: для Kubernetes инструкция задаёт PostgreSQL явно. Выполнение миграций не добавляется в CMD или build-слои. Запуск с неподготовленной схемой сохраняет текущий отказ startup.

### 6. Отдельное изменение без перезаписи PostgreSQL-плана

Дополнение `application-distribution-build` оформляется новыми требованиями. Это сохраняет требования и незавершённые проверки `add-postgresql-backend`. Сборка контейнера сама по себе не закрывает приёмку PostgreSQL и не подтверждает развёртывание в Kubernetes.

## Risks / Trade-offs

- Доступ к корпоративному образу и package index может отсутствовать в локальном окружении → отдельно фиксировать результат сборки дистрибутива и реальной Docker-сборки; недоступную проверку оставить невыполненной. Публичная база не заменяет проверку согласованного образа.
- Тег `latest` и текущие незакреплённые Python-зависимости могут менять результат установки → сохранить выбранный контракт и зафиксировать использованный image ID и версии в отчёте фактической проверки без содержимого `pip.conf`.
- Копируемый `pip.conf` остаётся частью образа → это прямо отражается в документации; проект не читает и не создаёт пользовательское содержимое файла.
- Запись логов в контейнере требует места и сохраняется только в пределах его файловой системы → указать пути и существующую ротацию; управление хранением остаётся инфраструктурной задачей.
- Реальная PostgreSQL-приёмка открыта → проверять образ с отдельной тестовой PostgreSQL при наличии назначения и не отмечать зависимые проверки пройденными при его отсутствии.

## Migration Plan

После разрешения на apply добавить файлы упаковки и документацию. Проверить shell-синтаксис, собрать свежий дистрибутив, распаковать ZIP в отдельный каталог и проверить его состав. Проверить, что локальные исключённые файлы и `pip.conf` не попадают в артефакт, а Dockerfile и `.dockerignore` присутствуют также при `--output`.

При доступе к корпоративным источникам выполнить Docker-сборку только из распакованного артефакта с предоставленным `pip.conf`, проверить состав образа, метаданные, UID, запись логов и временных файлов, CLI миграции и штатную остановку. Ошибки отсутствующего `pip.conf` и обязательного frontend проверять в отдельных временных копиях артефакта.

При наличии отдельного тестового PostgreSQL выполнить pre-deploy и smoke-проверку реального входа, frontend-ресурсов и API с runtime-ролью. Для сценариев, изменяющих БД, соблюдать backup/restore и остановку только созданных тестовых процессов/контейнеров по `AGENTS.md`. Новые frontend-тесты не требуются: UI-код не меняется.

Создание CI-job 2, публикация и применение образа в кластере остаются действиями пользователя. Проектные изменения обратимы удалением файлов упаковки и дополнений allowlist/документации; схема и данные не меняются.
