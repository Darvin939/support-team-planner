## Purpose

Определяет сборку и запуск контейнерного образа приложения из готового Linux-дистрибутива, передаваемого между независимыми сборочными job.

## ADDED Requirements

### Requirement: Сборка из готового артефакта
Система MUST предоставлять Dockerfile для сборки образа из корня распакованного дистрибутива без checkout репозитория. Базовый образ MUST быть `docker-dev.registry-ci.delta.mysecure_57117ba4eem0.ru/ubi8/python-312:latest`. Docker-сборка MUST использовать готовый frontend и MUST NOT выполнять его сборку или устанавливать Node.js.

#### Scenario: Отдельная job получает ZIP
- **WHEN** оператор распаковал дистрибутив, добавил свой `pip.conf` и запустил Docker-сборку из распакованного каталога с доступом к корпоративным источникам
- **THEN** образ собирается из этого каталога без дополнительных исходников или инструментов frontend

#### Scenario: Frontend отсутствует или неполон
- **WHEN** в контексте нет `frontend/dist/index.html` или `frontend/dist/taskTransitions.json`
- **THEN** Docker-сборка завершается с ненулевым кодом

### Requirement: Пользовательская конфигурация pip
Docker-сборка MUST принимать предоставленный пользователем `pip.conf` из корня контекста, копировать его в `/app/pip.conf` и устанавливать `PIP_CONFIG_FILE=./pip.conf` при рабочем каталоге `/app`. Обновление pip и установка `requirements.txt` MUST использовать эту конфигурацию без кэша pip. Проект MUST NOT создавать содержимое `pip.conf` или подменять выбранный пользователем источник пакетов.

#### Scenario: Конфигурация предоставлена
- **WHEN** пользователь добавил `pip.conf` в контекст перед сборкой
- **THEN** установка Python-зависимостей использует этот файл, который присутствует в образе по согласованному пути

#### Scenario: Конфигурация не предоставлена
- **WHEN** пользователь запустил сборку без `pip.conf`
- **THEN** сборка завершается с ненулевым кодом, а проект не генерирует замену

### Requirement: Полный runtime-состав
Образ MUST содержать точку запуска приложения, backend с PostgreSQL SQL-миграциями, готовый frontend, CLI миграции и переноса, файлы версии, журнала изменений и `app_build_metadata.json` из дистрибутива. Относительные пути MUST сохраняться. Идентификатор сборки MUST совпадать с идентификатором полученного дистрибутива при отсутствии runtime-переопределений.

#### Scenario: Запуск упакованного приложения
- **WHEN** приложение запускается из образа с подготовленной БД
- **THEN** доступны форма входа и frontend-ресурсы, backend читает `taskTransitions.json`, а приложение использует версию и ID сборки дистрибутива

#### Scenario: Доступность мигратора
- **WHEN** оператор запускает образ с командой `python -m scripts.migrate_database --help`
- **THEN** команда завершается успешно без необходимости checkout репозитория

### Requirement: Изоляция состава образа
Docker-контекст MUST исключать локальные БД, WAL/SHM, резервные копии, dumps, `.env`, логи, кэши, virtualenv, `node_modules`, frontend-исходники, тесты, Git и OpenSpec. Dockerfile MUST копировать runtime-файлы явно. `.dockerignore` MUST пропускать обязательные runtime-файлы, готовый `frontend/dist`, метаданные сборки и предоставленный пользователем `pip.conf`.

#### Scenario: Посторонние файлы рядом с дистрибутивом
- **WHEN** в распакованном каталоге дополнительно присутствуют локальная БД, `.env`, логи и тестовые файлы
- **THEN** они не попадают в образ, а готовый frontend и `pip.conf` остаются доступны сборке

### Requirement: Совместимый запуск контейнера
Образ MUST по умолчанию выполнять `python support_planner.py` в `/app`, объявлять порт `5093` и использовать непривилегированного пользователя с записью в `/app` и `/tmp`. Окружение MUST задавать `PYTHONUNBUFFERED=1`, `PYTHONDONTWRITEBYTECODE=1` и `PYTHONPATH=/app`. Существующие HTTP/TLS-режимы и файловое логирование приложения MUST сохраняться.

#### Scenario: Запуск от непривилегированного пользователя
- **WHEN** оператор запускает контейнер с подготовленной БД и согласованной доступной для записи файловой системой
- **THEN** приложение слушает `0.0.0.0:5093`, создаёт `application.log` и может создавать временные файлы без прав root

#### Scenario: Остановка контейнера
- **WHEN** оператор отправляет штатную команду остановки контейнера
- **THEN** сигнал завершения поступает процессу приложения напрямую и оно останавливается в пределах заданного таймаута

### Requirement: Внешняя конфигурация PostgreSQL
Образ MUST поддерживать существующие переменные подключения внешнего PostgreSQL и `SESSION_SECRET_KEY`, задаваемые при запуске. Установка PostgreSQL и выполнение миграций MUST NOT происходить во время Docker-сборки. Команда запуска приложения MUST NOT добавлять автоматические PostgreSQL-миграции; оператор выполняет существующую pre-deploy команду отдельно.

#### Scenario: Подготовленная PostgreSQL-схема
- **WHEN** оператор отдельно применил миграции и запустил образ с окружением runtime-роли и session secret
- **THEN** приложение использует внешний PostgreSQL и обслуживает запросы в рамках существующих контрактов backend

#### Scenario: PostgreSQL-схема не подготовлена
- **WHEN** оператор запускает приложение с отсутствующей или отстающей PostgreSQL-схемой
- **THEN** сохраняется существующий отказ startup, без автоматической миграции или переключения на SQLite
