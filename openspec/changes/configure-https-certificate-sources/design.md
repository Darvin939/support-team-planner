# Design

## Context

Мотивация — в [proposal.md](proposal.md). `backend.application.main()` всегда вызывает `get_cert()`, который обращается в Vault, пишет `portal.crt`/`portal.key` во временный каталог и при любой ошибке возвращает `(None, None)`. Main после этого запускает HTTP. Settings уже загружает внешний dotenv до прикладных модулей.

Vite, общий UI-harness и AGENTS.md предполагают локальный HTTP. Пользователь выбрал HTTPS в Python при доступном сертификате и сохранил HTTP как третий вариант после файлов Deployment и старого Vault-способа.

## Goals / Non-Goals

**Goals:** файлы Deployment имеют приоритет; отсутствие пары включает прежний Vault AppRole; недоступность обоих источников сохраняет HTTP; найденная некорректная смонтированная пара вызывает ошибку запуска.

**Non-Goals:** TLS termination на Ingress, новый Vault-клиент, изменение AppRole-протокола и пространства имён, автоматическое перечитывание сертификатов, mTLS, изменение API или данных, перевод существующих dev/UI-инструментов на обязательный HTTPS. In-process ASGI-тесты остаются тестами без сетевого TLS-listener.

## Decisions

### 1. Источники выбираются в существующем TLS-модуле

Сохранить интерфейс `get_cert()` с парой путей. Добавить две переменные окружения `SUPPORT_PLANNER_TLS_CERT_FILE` и `SUPPORT_PLANNER_TLS_KEY_FILE`; не фиксировать расположение Deployment-файлов в Python. Settings уже позволяет задавать эти переменные во внешнем dotenv. Пример расположения: `/config/secret/planner-tls/tls.crt` и `/config/secret/planner-tls/tls.key`.

Полная найденная пара используется напрямую. Если пути не заданы, пусты, заданы неполностью либо хотя бы один файл отсутствует, файловый источник считается недоступным и применяется существующий Vault-способ. У найденной пары ошибки доступа, неправильный тип пути и некорректный PEM являются ошибкой конфигурации, а не отсутствием источника. Поведение проверяется отдельно для каждого случая.

### 2. Сохраняется совместимость Vault AppRole

Сохранить `VAULT_TENANT`, `VAULT_ADDR`, `VAULT_KV_PATH`, `ROLE_ID`, `SECRET_ID`, существующие запросы аутентификации/чтения и поля `portal_chain`/`portal_key`. Сохранить создание и очистку временного каталога для полученных значений. Смонтированные файлы не переписываются и не удаляются приложением.

При ошибке получения, записи или проверки резервной пары `get_cert()` возвращает `(None, None)`, сохраняя существующий HTTP-путь main. Диагностика сообщает о переходе на HTTP без печати ответа Vault, секретов и цепочки исключений с чувствительными данными. Существующие зависимости requests/urllib3 сохраняются; изменение клиента Vault сверх выбора источника не входит в работу.

### 3. HTTPS при рабочей паре, HTTP при недоступности обоих источников

Проверять выбранную пару средствами стандартного SSL-модуля. Поддерживается обычная PEM-цепочка сертификата и соответствующий приватный ключ без пароля. Проверка не должна запрашивать пароль интерактивно. Некорректная найденная смонтированная пара завершает запуск без резервного запроса или HTTP. Некорректная пара из резервного Vault означает, что резервный способ не дал рабочий сертификат, и приводит к HTTP.

Сохранить две существующие ветки main: рабочая пара передаётся Uvicorn для HTTPS, `(None, None)` запускает HTTP на том же `0.0.0.0:5093`. Исключение при проверке найденной смонтированной пары прерывает запуск. Выбор протокола происходит один раз при старте; ошибка загрузки уже выбранной пары в Uvicorn не включает автоматический HTTP.

### 4. Локальный HTTP и отдельная проверка HTTPS

Сохранить HTTP по умолчанию у Vite, UI-harness и существующих UI-сценариев. При отсутствии смонтированной пары и доступного Vault локальный запуск продолжает работать без сертификата. AGENTS.md и frontend/README.md не требуют изменения из-за этого решения.

Для TLS-тестов использовать отдельную тестовую PEM-пару с SAN для loopback, не содержащую рабочих секретов и не входящую в дистрибутив/образ. Отдельный smoke задаёт пути дочернему процессу, проверяет HTTPS с доверием тестовому сертификату и настоящий вход. Отдельный запуск без обоих источников проверяет HTTP.

Тестовые процессы используют изолированную SQLite БД и UTF-8 логи; backup/restore выполняется через SQLite backup API с проверкой восстановления после остановки только созданного backend. При проверке через браузер используется свежая production-сборка, без dev-server. Рабочая БД и Vault не используются.

### 5. Ротация применяется перезапуском

Оба источника выбираются при запуске. Vault Agent может обновить смонтированные файлы, но процесс должен быть перезапущен для применения новой пары. Автоматический watcher и hot reload не добавляются.

## Risks / Trade-offs

- Ошибка резервного Vault включает HTTP → это сохранённое по решению пользователя поведение; документировать порядок и явно сообщать выбранный протокол в журнале.
- Отсутствующий файл приводит к Vault-запросу → сохранить существующие таймауты; сообщать выбранный источник без секретов.
- Файлы меняются между проверкой и загрузкой Uvicorn → ошибка загрузки прерывает запуск, HTTP не запускается.
- Тестовая TLS-пара попадёт в поставку → использовать только test-fixtures и проверить ZIP/allowlist.
- Реальный Vault/Kubernetes или отдельная PostgreSQL test-БД недоступны → отразить ограничения, не подменять ими успешную интеграционную приёмку других изменений.

## Verification

Unit-тесты проверяют приоритет источников, все варианты отсутствия пары, ошибки доступа/формата, совместимость старых полей, переход на HTTP после ошибки резервного способа и отсутствие секретов в диагностике. Main проверяется для HTTPS, HTTP и ошибки найденной смонтированной пары без запуска listener. Прямой Vault в этих проверках подменяется на границе запросов.

Отдельный HTTPS smoke запускает настоящее приложение с локальной тестовой парой и изолированными данными, проверяет TLS-handshake, `/login`, настоящий вход и отказ обычного HTTP в этом режиме. Отдельный HTTP smoke проверяет сохранённый третий вариант без сетевых обращений в рабочий Vault. Правила WAL-safe backup/restore и остановки созданных процессов сохраняются. Полный перевод UI-матрицы и PostgreSQL UI не требуется: frontend и хранилище не меняются.

Свежий дистрибутив проверяется на обновлённые runtime-модули и отсутствие сертификатов/ключей/fixtures. Python-код и тесты сохраняют совместимость с 3.9.

## Migration Plan

После разрешения на apply реализовать и проверить изменение. В Deployment настроить оба пути и подготовку PEM-файлов до старта; старые AppRole-реквизиты сохраняются там, где требуется резервный источник. При настроенной рабочей паре проверки Service/Ingress используют HTTPS. При отсутствии файлов и рабочей резервной пары сохраняется прежний HTTP. Для возврата к прежнему выбору источника достаточно убрать новые переменные путей и перезапустить процесс. Sync и архивирование требуют отдельных разрешений.
