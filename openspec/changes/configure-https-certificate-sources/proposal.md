# Proposal

## Why

Deployment будет получать сертификат и ключ из Vault и монтировать их в контейнер. Приложение должно использовать эти файлы в первую очередь, сохраняя существующее получение через Vault AppRole и запуск HTTP при недоступности сертификата.

## What Changes

- Добавляются пути `SUPPORT_PLANNER_TLS_CERT_FILE` и `SUPPORT_PLANNER_TLS_KEY_FILE`, задаваемые окружением или уже поддерживаемым dotenv-файлом.
- При наличии обоих файлов приложение использует их напрямую. Если файловая пара не задана или отсутствует хотя бы один файл, применяется прежний Vault AppRole с полями `portal_chain` и `portal_key`.
- Найденная, но нечитаемая или некорректная смонтированная PEM-пара вызывает ошибку запуска. Содержимое секретов не выводится.
- Сохраняется HTTP на 5093 как третий вариант: если смонтированная пара отсутствует и резервный Vault-способ не дал рабочую пару, приложение запускается по HTTP с понятным сообщением в журнале.
- Документация описывает порядок «файлы Deployment → Vault AppRole → HTTP» и перезапуск при ротации. Локальный HTTP, dev-прокси и существующие production UI-сценарии сохраняются; HTTPS проверяется отдельным тестовым запуском.

## Capabilities

### New Capabilities

- `https-startup`: приоритет файлов сертификата и ключа, резервный Vault AppRole, HTTP при недоступности обоих источников и ошибки найденной TLS-конфигурации.

### Modified Capabilities

Нет. API, схема БД и формат поставки не меняются.

## Impact

Изменяются `backend/ssl_context.py`, при необходимости запуск в `backend/application.py`, `.env.example` и README. Добавляются тесты выбора источника и запуска HTTPS/HTTP с отдельной тестовой TLS-парой. Существующий Vault-клиент, его зависимости, dev-прокси и UI-harness сохраняются. Python-код совместим с 3.9.

Изменение не завершает приёмку других открытых изменений и не выполняет развёртывание в Kubernetes.
