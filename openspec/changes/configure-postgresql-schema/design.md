# Единая конфигурация схемы PostgreSQL

## Context

Мотивация и согласованные границы — в [proposal.md](proposal.md). Пользователь подтвердил окружение/`.env`, default `planner`, предварительное создание схемы администратором и сохранение переноса SQLite. Данных в PostgreSQL `public` у пользователя нет.

`backend/settings.py` уже загружает `.env` без переопределения окружения. `PostgreSQLBackend.setup_connection()` устанавливает `search_path=public`, а migration runner, baseline, импорт, fixtures и integration-тесты дополнительно квалифицируют объекты через `public`. Одной смены `search_path` недостаточно.

Baseline хранится в SQL-файле, checksum считается по его исходному содержимому. PostgreSQL runtime проверяет схему без DDL; таблицы подготавливает отдельная команда миграции. Основные PostgreSQL-спецификации пока находятся в активном `add-postgresql-backend`, поэтому новый контракт выбора схемы оформляется отдельно.

## Goals / Non-Goals

**Goals:** хранить выбор схемы рядом с PostgreSQL-подключением; исключить расхождение runtime, мигратора и импорта; сохранить границы транзакций, существующий журнал миграций, контракт SQLite и Python 3.9.

**Non-Goals:** изменение DAO API, выбор схемы на HTTP-запрос, объединение нескольких схем, переработка advisory locks, автоматическое создание схемы или перенос PostgreSQL-объектов между схемами.

## Decisions

### 1. Выбор схемы фиксируется при создании PostgreSQL backend

Backend читает `SUPPORT_PLANNER_DATABASE_SCHEMA` после существующей загрузки `.env`, применяя `planner` только при отсутствии переменной. Выбранное имя передаётся созданным соединениям, чтобы функции миграции и импорта, получающие только соединение, использовали ту же конфигурацию. SQLite не читает и не проверяет PostgreSQL-схему.

Параметр является одним идентификатором. Проверяются пустое/пробельное значение, NUL и превышение поддерживаемой длины идентификатора; регистр и допустимые специальные символы сохраняются. SQL-имена формируются через `psycopg.sql.Identifier`, значения каталоговых запросов передаются параметрами. Для текстового `regclass` формируется корректное квалифицированное имя.

Альтернатива — повторно читать окружение в каждой функции. Она допускает разные значения внутри одного процесса и усложняет тесты, поэтому выбор хранится в backend/соединении.

### 2. Подготовка соединения проверяет существование и доступ

До прикладных запросов проверяются наличие именно выбранной схемы и USAGE текущей роли. Отсутствие схемы диагностируется как необходимость предварительного создания администратором, а отсутствие таблиц внутри существующей схемы — как необходимость pre-deploy миграции. Ни runtime, ни мигратор, ни импорт не выполняют `CREATE SCHEMA`.

`search_path` содержит выбранную прикладную схему без добавления `public` как резервного назначения. Общие неквалифицированные DAO-запросы работают через этот путь; служебные операции и импорт используют квалифицированные имена. Ошибка подготовки соединения должна сохранять существующее гарантированное закрытие соединений.

Альтернатива — создание схемы мигратором — отклонена пользователем: инфраструктурой и правами управляет администратор БД.

### 3. Проверки и журнал всегда относятся к выбранной схеме

Убирается жёсткая привязка к `public` при обнаружении и чтении журнала, проверке колонок, индексов, ключей, FK и triggers, bootstrap и запросе версии в migration CLI. Проверка внешних ключей учитывает схему целевой таблицы, чтобы совпадение имён в другой схеме не считалось корректной связью.

Исходный `postgresql_baseline.sql`, номер, имя и checksum baseline сохраняются. Только при исполнении baseline 1 отдельный renderer адаптирует известные квалификаторы объектов этого поставляемого SQL к выбранному имени с корректным экранированием. Он не применяется к произвольному пользовательскому SQL и последующим миграциям. Новые миграции должны сразу учитывать выбранную схему.

Альтернатива — заменить `public` непосредственно в опубликованном baseline — меняет checksum. Даже при отсутствии пользовательских данных в `public` это нарушило бы существующий контракт проверки журнала и потому не требуется.

### 4. Перенос SQLite сохраняет всю последовательность операций

Параметр используется для discovery назначения, counts, проверки внешних зависимостей, `LOCK TABLE`, `TRUNCATE ONLY ... RESTART IDENTITY RESTRICT`, вставок, сверки и поиска/restart identity-последовательностей. В отчёт попадает выбранная фактическая схема. Обычный импорт может подготовить прикладные таблицы без bootstrap внутри существующей схемы; `--replace-target` требует готовую актуальную структуру.

WAL-safe снимок источника, отдельная рабочая SQLite-копия, проверка пустоты, транзакционная замена, откат и отсутствие изменений назначения в `--dry-run` сохраняются. Нет отдельного параметра схемы у импортера: он использует ту же конфигурацию, что приложение и мигратор.

### 5. Проверки используют отдельную тестовую БД

Unit-тесты проверяют выбор default/override, приоритет окружения, некорректные имена, безопасное формирование SQL, сохранность baseline checksum и игнорирование параметра в SQLite. Реальные PostgreSQL-тесты проверяют `planner`, явно выбранную другую схему, имена с экранированием, `public`, ошибку отсутствующей схемы и прав, migration bootstrap, импорт/замену и изоляцию одноимённых объектов.

Fixtures, integration-тесты и UI-harness получают тот же параметр схемы. Тестовая инфраструктура заранее создаёт схемы в отдельной БД; продуктовые команды их не создают. Нельзя подменять реальную PostgreSQL-проверку моками или SQLite. PostgreSQL запускается отдельным pytest-процессом только с `SUPPORT_PLANNER_TEST_DATABASE_URL`; недоступность тестовой БД фиксируется как невыполненная приёмка.

UI-harness сохраняет backup/restore всей отдельной тестовой PostgreSQL БД и правила SQLite backup. При production UI-прогоне обязательны свежая сборка frontend, реальный вход, порт 5093 и остановка только созданного тестом backend.

### 6. Default задаётся приложением

Значение `planner` определяется в Python-конфигурации. Для контейнера используется обычная переменная окружения без отдельного поведения Dockerfile или build argument: это сохраняет одинаковый default в локальном процессе и контейнере. `.env.example`, README и `POSTGRESQL.md` показывают параметр и последовательность действий администратора/мигратора.

## Risks / Trade-offs

- Остаточный `public` в одной служебной операции → поиск всех квалификаторов и integration-тесты с одноимёнными таблицами в разных схемах.
- Некорректное экранирование имени → общий способ формирования идентификаторов и тесты имён с кавычками/дефисом/регистром.
- Повреждение migration checksum → исходный baseline остаётся неизменным; проверяется существующий журнал при явном `public` и повторный запуск в `planner`.
- Схема существует, но недоступна роли → отдельная ранняя проверка USAGE и инструкция выдачи прав; runtime сохраняет запрет DDL.
- Отсутствует PostgreSQL для приёмки → отчёт разделяет пройденные unit/SQLite-проверки и невыполненные PostgreSQL-сценарии.

## Migration Plan

1. Администратор создаёт `planner` либо другую выбранную схему. Migration-роль получает необходимые права на объекты, runtime — USAGE и прикладные DML-права согласно инструкции.
2. В окружениях приложения, мигратора и импортера задаётся одинаковый параметр; если он отсутствует, используется `planner`.
3. Для новой пустой установки запускается штатный мигратор. Для переноса SQLite выполняется подготовка таблиц `--schema-only`, предварительная проверка и импорт; возможная автоматическая подготовка таблиц обычным импортом остаётся доступной.
4. После подготовки и сверки приложение запускается с той же схемой. Существующие PostgreSQL-объекты никуда автоматически не переносятся; явный `public` поддерживается настройкой.
5. Реальная миграция пользовательских данных и переключение рабочей эксплуатации требуют отдельного согласованного действия. До такого переключения сохраняется существующая возможность продолжать работу с SQLite.
