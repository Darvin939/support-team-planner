## Purpose

Определяет единый выбор заранее созданной PostgreSQL-схемы для приложения, миграций и переноса из SQLite через параметры экземпляра, с `planner` по умолчанию.

## ADDED Requirements

### Requirement: Схема выбирается параметром экземпляра
Система SHALL использовать `SUPPORT_PLANNER_DATABASE_SCHEMA` из окружения/`.env` с приоритетом окружения. При отсутствии параметра PostgreSQL SHALL использовать `planner`. Один параметр SHALL определять схему приложения, мигратора и импорта SQLite. При работе с SQLite этот параметр SHALL NOT менять поведение хранилища.

#### Scenario: Параметр не задан
- **WHEN** PostgreSQL URL задан, а `SUPPORT_PLANNER_DATABASE_SCHEMA` отсутствует
- **THEN** приложение, мигратор и импорт выбирают `planner`

#### Scenario: Окружение переопределяет файл
- **WHEN** в `.env` указана одна схема, а переменная окружения содержит другое имя
- **THEN** все PostgreSQL-команды используют значение окружения

#### Scenario: Явно выбрана public
- **WHEN** `SUPPORT_PLANNER_DATABASE_SCHEMA=public`
- **THEN** все PostgreSQL-операции используют `public` без автоматического перемещения таблиц

#### Scenario: Выбран SQLite
- **WHEN** PostgreSQL URL отсутствует либо CLI явно выбирает SQLite
- **THEN** наличие или значение параметра схемы не меняет выбор БД и выполнение SQLite-операций

### Requirement: Параметр задаёт одно точное имя схемы
Значение параметра SHALL трактоваться как одно имя PostgreSQL-схемы, а не SQL или список поиска. Система MUST безопасно обрабатывать специальные символы идентификатора и отклонять пустое или недопустимое имя без молчаливого перехода на `planner` либо `public`.

#### Scenario: Значение явно пустое
- **WHEN** параметр задан пустой строкой либо содержит только пробелы
- **THEN** PostgreSQL-команда завершается с ошибкой конфигурации до изменения БД

#### Scenario: Имя требует экранирования
- **WHEN** администратор создал схему с допустимым именем, содержащим заглавные буквы, дефис или кавычку
- **THEN** операции обращаются именно к этой схеме, не интерпретируя её имя как SQL

### Requirement: Схему заранее предоставляет администратор БД
Приложение, мигратор и импорт SHALL использовать заранее созданную схему и SHALL NOT автоматически выполнять её создание. При отсутствии выбранной схемы или права USAGE команды MUST завершаться с понятной диагностикой до изменения PostgreSQL. Подготовка прикладных таблиц и журналов внутри существующей схемы остаётся задачей мигратора.

#### Scenario: Схема отсутствует
- **WHEN** приложение, мигратор либо импорт, включая `--dry-run`, обращается к отсутствующей схеме
- **THEN** команда сообщает её имя и необходимость создания администратором; схема и прикладные объекты не создаются

#### Scenario: Нет доступа к схеме
- **WHEN** выбранная схема существует, но роль не имеет USAGE
- **THEN** команда сообщает о недостаточных правах без перехода к другой схеме и без раскрытия строки подключения

#### Scenario: Есть схема без прикладных таблиц
- **WHEN** мигратор с необходимыми правами запускается для заранее созданной пустой схемы
- **THEN** прикладные таблицы и журнал создаются внутри выбранной схемы

### Requirement: Все прикладные объекты относятся к выбранной схеме
Runtime-запросы, проверки структуры, миграции, bootstrap и импорт SHALL обращаться к таблицам, индексам, связям, журналу и последовательностям выбранной схемы. Наличие одноимённых объектов в `public` либо другой схеме SHALL NOT подменять отсутствующие объекты выбранной схемы.

#### Scenario: Одноимённые таблицы находятся в другой схеме
- **WHEN** выбранная схема и `public` содержат таблицы с одинаковыми именами и разными данными
- **THEN** приложение читает и изменяет только объекты выбранной схемы

#### Scenario: В выбранной схеме нет журнала
- **WHEN** журнал есть в `public`, но отсутствует в выбранной схеме
- **THEN** startup сообщает о необходимости миграции выбранной схемы и не принимает чужой журнал за актуальный

### Requirement: Журнал миграций сохраняет совместимость
Выбор схемы SHALL NOT изменять опубликованные номера, имена и checksum PostgreSQL-миграций. Повторный запуск мигратора SHALL проверять журнал выбранной схемы и сохранять уже применённые шаги и данные. Смена параметра SHALL NOT автоматически переносить объекты или записи между схемами.

#### Scenario: Сохранён ранее применённый baseline
- **WHEN** мигратор повторно запускается в явно выбранной `public` с совместимым журналом
- **THEN** исходный baseline принимается без изменения checksum, повторного bootstrap и переноса данных

#### Scenario: Новая установка в planner
- **WHEN** baseline применяется к заранее созданной пустой `planner`
- **THEN** журнал и все прикладные объекты находятся в `planner`, а повторный запуск не меняет данные

### Requirement: Перенос SQLite использует выбранную схему
Импорт SHALL сохранять существующие режимы обычного переноса, `--dry-run` и `--replace-target` в выбранной схеме, включая WAL-безопасный снимок SQLite, полную сверку, сохранение ID и связей и настройку последовательностей. Отчёт SHALL указывать фактическую целевую схему. Подготовка таблиц для переноса SHALL выполняться без bootstrap-администратора.

#### Scenario: Первый перенос без параметра схемы
- **WHEN** администратор создал `planner`, параметр схемы отсутствует и выполняется импорт совместимой SQLite БД
- **THEN** все прикладные данные переносятся в `planner` с прежними ID и учётными данными; после импорта новые ID не конфликтуют с перенесёнными

#### Scenario: Перенос в пользовательскую схему
- **WHEN** оператор явно задаёт другую существующую схему и выполняет импорт
- **THEN** подготовка таблиц, загрузка, сверка и последовательности относятся к ней, а отчёт содержит её имя

#### Scenario: Предварительная проверка
- **WHEN** выполняется `--dry-run` с обычным импортом либо `--replace-target`
- **THEN** отчёт описывает выбранную схему, а PostgreSQL-таблицы, данные и последовательности остаются неизменными

### Requirement: Замена данных ограничена выбранной схемой
Режим `--replace-target` SHALL очищать только прикладные таблицы выбранной схемы без CASCADE, сохраняя её журнал и посторонние объекты. Чужие схемы MUST оставаться неизменными. Внешние зависимости SHALL вызывать отказ; ошибка до commit SHALL откатывать очистку, загрузку и изменение последовательностей.

#### Scenario: В двух схемах есть прикладные таблицы
- **WHEN** выполняется разрешённая замена данных в выбранной схеме
- **THEN** только её прикладные данные заменяются снимком; одноимённые таблицы другой схемы и migration journal сохраняются

#### Scenario: На целевую таблицу есть внешняя ссылка
- **WHEN** таблица вне области импорта ссылается на прикладную таблицу выбранной схемы
- **THEN** замена отклоняется без очистки и без расширения области операции

#### Scenario: Импорт завершается ошибкой после очистки
- **WHEN** при замене происходит ошибка загрузки или сверки до commit
- **THEN** прежние данные и последовательности выбранной схемы восстанавливаются откатом
